# H3 prototype: one Worker, one wildcard, five questions

Status: **design and requirements only. Nothing is created, deployed, registered or purchased.** No Cloudflare account was
touched, no zone exists, no DNS record was read or written, no Worker was uploaded. The whole document is a proposal
awaiting authorisation, and §6 is the part that costs money.

The H3 plan (§11 of `h3-staging-readiness.md`) lists five things Cloudflare's documentation does not answer for this
application. This is the smallest experiment that answers all five, in the order that makes a failure cheap: the first
test is "does the route fire at all", because if it does not, nothing after it matters.

## 1. What is being tested, and what is deliberately not

| In scope | Why |
| --- | --- |
| Worker route on a wildcard host | The preview tier cannot exist without it (Pages has no wildcard domains) |
| `assets` binding serving the real build | Confirms the Worker can front the same `dist/browser` H1 already ships |
| `_headers` through the binding | The documented exception is "responses generated by Worker code"; which side a binding response is on is unknown |
| Service-worker registration and control on the proxied host | The harness proves the browser permits it on `.test`; not that a Cloudflare-fronted host behaves the same |
| Host handling and preview-path routing | A silent SPA fallback would break every preview and look like a worker bug |

| Out of scope | Why |
| --- | --- |
| The real editor deployment, custom domain, auth, persistence | Not needed to answer any of the five |
| Production `aporyx.com` / `aporyx-engine.com` | Identities are targets, not purchases (§6) |
| Any change to `src/`, `public/` or the build | The prototype runs the existing artifact; if it needs app changes, the artifact is wrong |

## 2. The prototype as deployed

One Worker, one zone, one wildcard route. No second Worker, no Pages project, no database.

```
zone (throwaway)                  e.g. h3-probe.example
  route                           *.h3-probe.example/*   ->  worker aporyx-h3-probe
  DNS                             *.h3-probe.example     ->  AAAA 100::  (proxied, placeholder origin)
  worker config                   assets.directory = ./dist/browser
                                  assets.binding   = ASSETS
                                  assets.run_worker_first = true
```

Worker logic is short enough to read in one screen:

1. Read `Host`. If it is exactly 32 hex characters followed by the probe suffix, answer with a synthesised preview shell
   that registers `/preview-sw.js` at scope `/` and sets COOP/COEP/CORP in code.
2. Otherwise, `return env.ASSETS.fetch(request)` unchanged, so the asset path stays honest.
3. Echo `Host` and the resolved asset path on a `/__probe` route, so test 4 has something to assert against.

`run_worker_first: true` is deliberate: it forces every request through the Worker, which is the harder path and the one
whose `_headers` behaviour is in question.

**Why a route and not a Worker custom domain:** custom domains are single hostnames. Wildcard hostnames are a route
feature, and the route also keeps the zone's own DNS in one place, which is what teardown has to undo.

## 3. The five tests and their pass criteria

Each test fails loudly or passes with evidence, and none of them is satisfied by "the page loaded".

| # | Test | Pass criterion | Failure means |
| --- | --- | --- | --- |
| 1 | Wildcard serve | `GET https://<32hex>.<probe>/*` returns 200 with the shell; `GET /assets/<hash>.js` returns 200 with `content-type: text/javascript`; `GET /__probe` returns JSON naming the same `Host` | Route is not firing, or the DNS record is not proxied, or the asset manifest does not match the wildcard host |
| 2 | Headers | Asset response carries `cross-origin-opener-policy: same-origin`, `cross-origin-embedder-policy: require-corp`, `cross-origin-resource-policy: cross-origin`, `x-content-type-options: nosniff`, `referrer-policy: no-referrer` from `_headers`; the synthesised shell carries the same five sent by the Worker; `/assets/*` is `immutable` and `/preview-sw.js` is `no-store` | `_headers` does not survive the binding, so the Worker must attach headers itself and §5's table becomes mandatory code rather than configuration |
| 3 | Service worker | In all three engines, the shell registers `/preview-sw.js` at scope `/`, reaches `controller === true`, and a request to `/preview/<port>/` is answered **by the worker** (not the network) | Cloudflare's path or cookie behaviour breaks registration, and the preview tier needs a different transport |
| 4 | Host handling | `/__probe` reports `Host == <32hex>.<probe>` from the client, and the asset it served is the same file the non-rewritten and URL-rewritten variants return | The Worker must rewrite `request.url` before `ASSETS.fetch()`, which is an extra failure mode to carry everywhere |
| 5 | No SPA fallback | `GET /preview/3200/` with no service worker returns the Worker's explicit 503 and **not** `index.html`; response body and `content-type` prove which one | A catch-all fallback is swallowing preview paths, which silently breaks every preview (`deployment.contract.test.ts` forbids exactly this) |

Test 3 is run by the existing harness rather than by hand: the cross-site runner already drives Chromium, Firefox and
WebKit with pinned versions, real trusted certificates and no bypasses, and it already distinguishes registration,
control, a worker-served request and an infrastructure failure. Pointing it at the probe zone is the cheapest way to get a
three-engine answer that is comparable with what is already recorded.

## 4. How it is isolated

- **Separate zone.** The probe never touches a domain the product uses. Nothing in the repository's deploy config points
  at it.
- **Separate Worker name.** `aporyx-h3-probe`, so teardown cannot accidentally delete anything real.
- **Random 32-hex labels.** Hosts are generated per run and are not discoverable or enumerable in practice.
- **No secrets, no API keys, no user data.** The artifact has no backend; the app persists to `localStorage` per origin.
- **Time-boxed.** The window is measured in hours, not days. Teardown (§7) runs even if the tests fail.

## 5. What becomes publicly reachable, stated plainly

For the duration of the test, `https://<32hex>.<probe>/` serves the real application shell to anyone who knows the
hostname: an editor UI that runs JavaScript locally in the browser. There is no server-side data, no credentials, no
session, no upload path and no API. The exposure is a public copy of a static application, which is the same exposure as
any deployed build — but it is public, and that is the honest description.

The one thing genuinely new in public: a hostname pattern that registers a service worker at scope `/`. On a throwaway
zone with nothing else on it, a visitor cannot reach anything of ours through it.

## 6. Requirements, resources and cost

### Can an existing domain be used?

Only if the owner has a domain whose DNS is already on Cloudflare (or is willing to move it), and is willing to add a
`*.h3-probe` wildcard record and route to it. **Nothing in this repository names such a domain, and the Vercel account
owns none.** Reusing a domain that carries email, a site or anything else is not recommended here: teardown has to delete
a wildcard record and a route, and a mistake on a live zone is a real outage.

`*.workers.dev` cannot substitute. Routes are a zone feature: they match on a hostname the account controls, so no route
and no wildcard host exists without a zone.

### Is a separate throwaway domain required?

Yes, for tests 1 and 4. Tests 2, 3 and 5 could run on a single `*.workers.dev` host, which is free, but that proves the
Worker and the assets, not the wildcard — and the wildcard is the thing the whole preview tier depends on.

### Account and zone requirements

- Cloudflare account (free tier is fine).
- One domain registered and **its nameservers pointed at Cloudflare** (Cloudflare Registrar does both in one step).
- Workers enabled on the zone (free plan is enough for a prototype: the limits are requests per day, not routes).
- A proxied wildcard DNS record. A route only matches a hostname Cloudflare is already proxying, and a grey-clouded record
  is the most common reason a route "does nothing" — which is exactly why test 1 exists.

### Certificate behaviour

The wildcard `*.<probe>` is first-level, and Universal SSL covers the apex plus first-level subdomains on a full setup.
So the certificate is free and automatic, and issuance for a brand-new hostname takes minutes rather than being instant.
No Advanced Certificate Manager, no Total TLS, no paid certificate.

### Expected cost

| Item | Cost | Avoidable? |
| --- | --- | --- |
| Domain registration | roughly $10-12 for the first year at cost (Cloudflare Registrar sells at wholesale; renewals similar) | Only by reusing a domain the owner already has on Cloudflare |
| DNS | free | — |
| Universal SSL certificate | free | — |
| Workers (free plan) | free at a prototype's request volume | — |
| Pages | not used | — |

**One unavoidable cost if no existing domain is available: a single domain registration, roughly $10-12.** Everything
else in the prototype is inside the free tier. No plan upgrade, no paid certificate, no paid Pages/Vercel tier is needed
for any of the five tests.

## 7. Teardown

Ordered, and every step is verified by the step after it:

1. Delete the route `*.h3-probe.<zone>/*`.
2. Delete the Worker `aporyx-h3-probe` (and its assets).
3. Delete the wildcard DNS record.
4. Confirm `https://<32hex>.<probe>/` no longer resolves to us (expect 522/530/404 from Cloudflare, **not** the shell).
5. If the domain was bought for this and nothing else uses the zone, either delete the zone or leave it inert with no
   records; the domain can be left to lapse rather than renewed.
6. Record in the PR: what was created, what was deleted, timestamps, and the last response code observed after teardown.

The teardown is written before the deployment, not after: the failure this prevents is a probe that quietly stays up
because the tests "worked".

## 8. Risks

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Route never fires (DNS not proxied, zone not fully active) | Medium — the most commonly reported Workers failure | Test 1 is first and its failure message names this cause |
| `_headers` does not apply to binding responses with `run_worker_first` | Medium — the docs exclude Worker-generated responses | Test 2 measures it; if it fails, headers move into code and `headers:check` gains a second consumer |
| Service-worker registration behaves differently on a proxied zone | Low-medium | Test 3 runs in three engines through the harness, and an infrastructure failure stays distinguishable from a refusal |
| Wildcard certificate issuance delays the run | Low | Test 1 tolerates a minutes-long issuance window; the run is time-boxed, not scheduled |
| The probe stays publicly reachable after the test | Low but the worst outcome | Teardown is ordered and verified in step 4, and it is not optional |
| Cost creep (accidental paid add-on) | Low | Nothing in the design needs a paid feature; the only spend is the registration itself |

## 9. What authorisation would have to cover

1. Registering one throwaway domain (or naming an existing Cloudflare-hosted domain to use instead).
2. Creating that zone and moving its nameservers to Cloudflare.
3. Uploading the `aporyx-h3-probe` Worker with the existing build artifact.
4. Creating the wildcard DNS record and route.
5. Leaving it up for the length of the test window, then tearing it down per §7.

Nothing else. No change to `aporyx.com`, `aporyx-engine.com`, the repository's deploy configuration, or the application.
