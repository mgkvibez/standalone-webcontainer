# ADR-0011 — Fixture Project Files

**Date:** 2026-11-04
**Status:** Proposed — provisional, written by the implementer for the month-long expert audit
**Deciders:** Implementation decisions recorded here so the audit can accept or overturn them; the charter reserves
architecture to the human expert, and this addition is a format change to data the expert has not yet reviewed.

## Context

A definition was a list of steps and assertions with nothing underneath them. `npm install` had no `package.json` to
read, `npm run dev` had no sources to serve, `file-exists` had no files to find and `http-body-contains` had no text to
expect. Nineteen of twenty definitions were describing a project that did not exist, so no fixture in the corpus could
produce a scoreable result no matter how complete the runtime became.

This was recorded as a deviation rather than a bug because the corpus was specified from published evidence in an
earlier slice: the scenarios, not their file trees. The gap was found by asking what the first step would actually read
from disk.

The constraint that shapes the answer is provenance. If a fixture ships `node_modules`, it will assert against files it
shipped itself and a broken resolver will pass, which is the one result this harness exists to prevent.

## Decision

A definition may carry a `files` map: relative POSIX path to text contents. Files are validated when the definition is
parsed and staged into the runtime's VFS before step 0 by `materializeProject`.

1. **Paths are validated, not trusted.** Absolute paths, `..` segments, `.` segments, empty segments, backslashes and
   NUL bytes are refused, because the map decides where files are written inside the VFS and a definition is data.
2. **`node_modules` is refused outright.** The installer must produce it, or the install assertion is measuring the
   fixture's own handwriting.
3. **Validation happens at parse time.** A path that could only fail during staging would fail halfway through a run and
   be misreported as the runtime's fault. A corpus that loads is a corpus that can be staged.
4. **Staging order is sorted**, so two runs perform the same operations in the same order and failures stay comparable.
5. **Contents are text only.** A binary asset would need an encoding decision (base64 inflates, and the VFS accepts
   `Uint8Array`), which is deferred rather than guessed.
6. **`files` is covered by the freeze pin** (ADR-0007): canonical JSON includes every field except `status`, so once a
   definition is frozen its project is frozen with it.

## Consequences

- A fixture is now self-contained: one file describes a project, the commands to run against it, and what must be true
  afterwards. Nothing is inherited from an ambient directory, which is what makes isolated runs real.
- The corpus can be staged incrementally: fixture 1 ships a Vite project as the reference, and the remaining
  definitions are unaffected until given files of their own.
- A new offline check now runs over the shipped corpus: every `npm run <script>` step must name a script the definition's
  own `package.json` defines, and every `http-body-contains` string must appear in some shipped file. Both classes of
  mistake previously surfaced only as a run failure blamed on the runtime.
- Definitions get larger and their freezes become more consequential. Editing a fixture's HTML now breaks a pin, which
  is correct but makes late content fixes a deliberate act.

## Open Questions

1. **Binary assets.** Deferred. The first fixture needing an image or a `.wasm` file decides the encoding, and that
   decision should be made with the fixture in hand rather than in advance.
2. **`formatVersion`.** Left at 1 because `files` is optional and every existing definition still parses. Whether an
   optional field warrants a version bump is the expert's call; the alternative is that version numbers mean nothing.
3. **Size ceiling.** None is imposed. A definition could ship an enormous tree and slow every run; whether that needs a
   limit or just review discipline is unproven without real fixtures.
4. **Staging the rest of the corpus.** Nineteen definitions still ship no project. This is content work, not
   implementation, and it is the next thing standing between the corpus and a gate number.
5. **Assertion reachability.** The offline check proves text appears somewhere; it does not prove the runtime will serve
   it. Only a real run does that, so this check removes a class of nonsense, not the need for the run.
