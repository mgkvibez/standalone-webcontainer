# ADR-0017: Preview origins and the supervisor transport boundary

**Date:** 2026-11-05  
**Status:** Accepted direction from the owner: previews must be origin-separated; same-origin previews are rejected.  

**P0 extension (proposed 2026-11-08):** kept. Preview origin separation stands and is extended to cover the runtime itself by ADR-0019. See P0-rulings.md R-8.
**Deciders:** Product owner; implementation recorded by the agent.

## Context

The existing `/preview/<port>/` gateway, fetch handler and service-worker bridge are tested components, but there is no
browser service-worker registration. The current runtime Worker also creates a fresh VFS and runtime for each command.
Neither piece is yet a live preview system.

ADR-0002 #5 chose path-scoped routing, which by itself places previews on the host application's origin. That conflicts
with ADR-0002 #8's deny-by-default security direction. A preview running on the host origin could reach host-origin
storage and endpoints, and would have the same origin privileges as the application. The discovery audit recorded this as
R-1 and recommended deciding it before previews are offered.

## Decision

1. **Every preview is served from an origin distinct from the host application.** Preview addresses use a project-scoped
   hostname, for example `<opaque-project-id>.preview.<configured-domain>`. Same-origin preview URLs are rejected. This
   amends ADR-0002 #5: `/preview/<port>/` may remain as an internal port/path discriminator, but it is not an isolation
   boundary and must not be mounted on the host application's origin.
2. **A service worker that handles preview requests is registered on the preview origin only.** The host application's
   service worker must never receive or route user preview traffic.
3. **The Worker supervisor transport is origin-agnostic.** It owns the active project's VFS and runtime, tracks execution
   processes, and answers bounded request/reply envelopes over transferable `MessagePort`s. The supervisor protocol
   carries request identity, method, path/query, headers and bytes; it does not encode an origin, preview hostname, URL
   prefix or service-worker scope. A later preview adapter owns those details.
4. **Build order:** first implement the persistent Worker supervisor and its generic transport port; next design and
   implement the origin-separated preview shell and service-worker registration on top. Do not ship or expose browser
   previews before the separate-origin routing and hosting checks pass.

## Deployment constraints and open implementation details

- Production needs project-scoped preview hostnames backed by wildcard DNS and TLS, or an equivalent routing mechanism.
- Local development needs a distinct secure-context origin per project (for example, a `<project>.localhost` hostname)
  and a development server that routes those hosts correctly.
- Project IDs placed in a hostname must be opaque or strictly validated and encoded; arbitrary project names are not
  hostname labels.
- Host and preview iframe interaction must be tested under the eventual COOP/COEP policy. SharedArrayBuffer is not used by
  the current runtime, so cross-origin isolation headers are not required solely by this ADR; if a future sync bridge uses
  SharedArrayBuffer, ADR-0003's hosting constraints apply. The iframe's credentialless/CORP/CORS behavior remains a
  deployment decision to validate before preview shipping.
- The host-to-preview bootstrap must transfer an explicit `MessagePort`, validate the exact preview origin and source
  window, and avoid ambient origin-wide message handlers. A port is a capability: bind it to one project and close it on
  project switch, Worker reset, or preview teardown.
- Internal port addressing, path rewriting, multiple simultaneous servers and service-worker scope remain to be
  implemented and tested; they do not change the origin-separation requirement.

## Consequences

- A same-origin `/preview/<port>/` path is not an acceptable shipping preview route.
- The Worker supervisor can be implemented before hostnames or a service worker exist, provided its request transport
  stays origin-neutral and can be attached through a transferred `MessagePort`.
- Preview hosting now has real DNS, TLS, browser-policy and local-development requirements; those must be proven before
  the feature is enabled.
- This ADR does not claim that an origin boundary is a complete sandbox. The runtime's capability surface and any
  cross-origin message handlers still require explicit limits and validation.
