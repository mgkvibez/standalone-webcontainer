# ADR-0001 — Architecture baseline and open decisions

**Date:** 2026-10-23
**Status:** Accepted, and amended 2026-11-12 (see *Amendment: the claim boundary*). The runtime substrate is now a decided
question, not an open one: native V8 plus custom shims, retained deliberately, with the compatibility claims narrowed to what
has been measured.
**Deciders:** Human expert (architect) via the project charter; recorded by the implementer.

## RATIFIED (charter-decided; do not re-litigate)

- **Runtime:** Browser-native V8 executing JavaScript-shimmed Node.js APIs.
  NOT a WASI-compiled Node.js binary.
- **VFS:** In-memory POSIX-compliant file system with persistence for session
  continuity. The persistence mechanism is UNDECIDED (see open questions).
- **Networking:** A service worker intercepts fetch requests and routes them to
  the in-browser Node.js server. The routing design is UNDECIDED.
- **Threading:** COOP/COEP headers required for SharedArrayBuffer.
- **Terminal:** xterm.js over a PTY bridge to the runtime's
  stdin/stdout/stderr.
- **Hybrid runtime:** Browser lane for zero-compute-cost previews; server
  sandbox fallback for native modules, Python, and heavy builds. Both lanes
  behind one unified `Runtime` interface.
- **Licensing allowlist:** MIT, Apache-2.0, BSD, ISC only.
- **Explicitly forbidden:** `@webcontainer/api`, the StackBlitz WebContainers
  runtime, Nodebox, anything under Commons Clause / Sustainable Use License /
  Business Source License, and any dependency that is secretly a proprietary
  wrapper.
- **Reference, not seed:** The archived `mgkvibez/webcontainer` wrapper is a
  reference only. It is NOT a seed and no code is to be copied from it.
- **almostnode:** REFERENCE ONLY. No dependency, no fork, no upstream issues.

## OPEN — expert decision required; the implementer must not choose

1. **VFS data structure** (flat Map vs tree/Trie) and the path normalization
   contract. Determines lookup cost, directory semantics, and rename/move
   complexity for every API built above it.
2. **Async-first vs sync API surface**; how `readFileSync` is handled without
   blocking the main thread. Determines whether POSIX sync semantics are
   emulated, approximated, or rejected.
3. **Persistence mechanism:** IndexedDB vs OPFS; cache invalidation and session
   restore. Determines cold-start cost, storage quotas, and durability.
4. **Large-file representation and memory ceiling / eviction policy.**
   Determines whether large fixtures hit OOM in the browser lane.
5. **Service worker routing:** URL scheme, request/response framing,
   backpressure, WebSocket plan. Determines what servers users can actually
   run and how previews are addressed.
6. **Worker isolation model and bidirectional VFS sync.** Reference bug from
   the almostnode audit: one-way sync made worker writes invisible to the main
   thread. Our design must decide the sync protocol explicitly.
7. **Shim priority order and Node version target.** Determines fixture scope
   and the compatibility surface we claim.
8. **Security boundary.** Trusted opt-in modes (e.g. same-origin flags) are
   harness-only and must never ship in the product path; the expert decides the
   isolation model that makes that enforceable.

## Known hazards (from the almostnode reference audit — risks, not prescriptions)

- Semver range grammar: failures on `>= 2.1.2 < 3` and exact `=x.y.z` pins.
- npm lifecycle / postinstall scripts never executing.
- URL-protocol dynamic imports breaking Vite builds
  ("Unsupported URL protocol: http:").
- Worker -> main VFS writes not syncing back (one-way sync).

## Gate (pre-registered; do not adjust after results)

- **Lane gate:** >=90% full pass on the front-end-only fixture subset in a
  SHIPPABLE isolation mode.
- **Boundary fixtures** (Next.js, SvelteKit, monorepo, large bundles,
  concurrent HMR) reported separately as server-lane candidates.
- **Overall rate** reported for reference only.
- **Trusted-mode and isolation-mode pass rates reported separately.** Only the
  isolation-mode rate justifies shipping user code in the browser.

## Approval

Ratified items: human expert, project charter, 2026-10-23.
Open items: awaiting ADR-0002+ from the expert.

## Amendment 2026-11-12 — the claim boundary (substrate decided, claims narrowed)

**Decider:** the project owner, in writing, on 2026-11-12, after reviewing `docs/audit/baseline-nov-12.md` §6 (the three
options, their costs and the recommendation). **Recorded by:** the implementer. This amendment does not touch any ratified
item above; it settles one that the register had left open ("stay on native V8 + shims, swap the substrate, or narrow the
claim") and it fixes the words the project is allowed to use about itself.

### The decision

1. **Native V8 plus custom shims remains the chosen architecture.** No migration to a WASI-compiled Node.js binary, and no
   redesign or replacement of the execution substrate.
2. **What this product is:** a *browser-based Node-compatible execution environment*.
3. **Full Node.js compatibility is not claimed.**
4. **StackBlitz-level compatibility is the long-term target, not an achieved status.** Not abandoning the ambition; choosing a
   different route to it.
5. **Native addons remain unsupported by design** unless separately approved.
6. **Reconsidering the substrate is not forbidden, it is gated:** a future proposal to replace it must bring concrete
   compatibility evidence showing the existing architecture has reached a meaningful limitation — not an expectation that a
   different substrate would be easier.

### The claim table (this is the vocabulary, and the boundary of it)

| Claim | Status |
| --- | --- |
| Browser-based JavaScript execution | **Supported** |
| Custom Node-compatible runtime | **Accurate description** |
| Full Node.js compatibility | **Not claimed** |
| StackBlitz-level compatibility | **Target, not achieved** |
| Native addons | **Unsupported by design** unless separately approved |
| Compatibility improvements | **Must be demonstrated through real fixtures** |

Consequences that follow from the table rather than from taste:

- A sentence in the README, a doc or a commit that asserts or implies full Node compatibility is a defect, in the same way a
  failing test is. The measured position on 2026-11-12 is recorded in `docs/audit/baseline-nov-12.md`: **5 of 15 front-end
  fixtures verified (33%)**, twelve definitions still holding no project files, none frozen, and the gate's 90% threshold unmet.
- "Works" means a fixture's assertions passed in a named registry lane, with provenance. A package that installs, a server that
  prints a URL, a bundle that completes — each is a step, not a verdict.
- The office of the decision is the *substrate*. Everything measured since it was taken — the process model, the kernel and its
  filesystem, the loaders, streams, the scheduler, the preview gateway, the service-worker routing, HMR through the product —
  stays exactly as it is and is the reason the answer was "stay".

### Why "stay" rather than "swap" or "narrow only"

Recorded so the next reader can weigh the same evidence rather than re-argue the conclusion:

- The measured trajectory is real and arrived gap by gap: real Vite 5.4.21 boots and serves inside this runtime
  (`SERVING +5241ms url=http://127.0.0.1:3300/`), real express 5 serves a body through the real preview gateway from 68 real
  packages, `vite build` completes, and an edit made in the editor reaches a running dev server and lands in the open page
  without a reload (ADR-0034).
- The failures that prompted the question were **measurement and harness-integration defects**, not substrate limits: evidence
  that did not name its lane (W-27) and a harness that could not observe a held-open server (W-28). A different substrate would
  have inherited both.
- A WASI build would spend the next month re-earning process integration, filesystem behaviour and the differential evidence
  that makes this repository's claims checkable, for a ceiling that is not higher on the axis that matters here: native addons
  are absent there too.

### What this amendment does not do

It does not declare compatibility. It does not lower the gate, freeze a fixture, or convert a proposed definition into a
scored one. It does not authorise compatibility expansion: the order of work after it is measurement first (W-27, W-28), then a
reproducible baseline, then an architectural review before any new build.
