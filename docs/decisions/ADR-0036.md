# ADR-0036: A Worker that closes itself reports before it stops

**Status:** accepted, 2026-11-19
**Relates to:** ADR-0018 (real processes), ADR-0019 (the runtime origin), ADR-0035 (a run ends through one path), the
W-19 P3-2 closeout note, register item W-42.

## Context

W-19 P3-2 measured a lifecycle defect and left it open. `DedicatedWorkerGlobalScope.close()` stops the Worker without
sending the host a trusted `exit` or `failed` control message and without firing an error event. Measured in Chromium: the
process stays `running`, `settled()` stays pending, and its slot in a table whose limit counts live processes stays
occupied, until someone calls `kill()` or disposes the kernel.

The host learns about termination in exactly two ways, and both are reports. The platform offers no termination event and
no channel-closure event, so a dead Worker is not observable, only inferable from silence, and silence is indistinguishable
from an idle process.

## Decision

Instrument the one path that can be reported deterministically: the own `close` property on the Worker global is replaced,
before user code runs, by a wrapper that sends `{type: "failed", reason: "worker closed itself"}` on the private control
port and then calls the original. The host's existing `failed` handling performs the transition, so no new state, no new
message type and no second settlement path are introduced.

Four properties the wrapper must keep:

1. **Termination is unconditional.** The report is attempted inside its own `try`/`catch`; native close runs outside it.
   A reporter that throws is swallowed, and a native close that throws is not, because failing to terminate matters more
   than failing to describe it.
2. **One attempt, not one success.** The "already reported" flag is set before the attempt, so a second `close()` never
   sends a second report.
3. **No patchable invocation.** The wrapper runs after user code may have replaced `Function.prototype.call`, so it invokes
   native close through an invocation intrinsic captured before user code (the `Reflect` reference P3-0 already captures),
   never through a method read off a prototype at call time.
4. **Installation may fail, and boot continues.** An absent, non-configurable or un-redefinable `close` returns
   `{installed: false, reason}` and the worker logs it once. Refusing to boot would turn a bookkeeping gap into an outage.

## What this does NOT guarantee

This is not detection of silent Worker termination, and it must not be described as such. Still unobserved: an out-of-memory
kill, a browser- or devtools-initiated termination, a crash that never reaches `worker.onerror`, a program that overwrites
or deletes `close`, a program blocked forever in one synchronous stretch, and any engine where installation fails.

A general liveness mechanism (heartbeat with a deadline) was designed and rejected for this phase: a synchronous Worker
answers a ping late rather than never, so a missed heartbeat proves unresponsiveness, not death. Defaulting such a timeout
would silently reclassify a legitimate long compile as a failure. It is recorded as undecided, not implemented.

## Consequences

- A program that closes itself now ends `failed` with a reason instead of stranding its process, its caller and its slot.
- `close` stays writable and configurable by design. This is instrumentation, not a lockdown, and it does not make the
  Process Worker a sandbox.
- A held-open process that closes after exiting shows `failed` in the table while its settlement reports the earlier exit,
  because settlement is first-wins and the program did exit. Two facts, one answer.
- The syscall serve loop still cannot distinguish a dead peer from an idle one. That remains a separate follow-up.
