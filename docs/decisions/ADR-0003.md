# ADR-0003 — Shim Layer & Persistence Integration Strategy

**Date:** 2026-10-26
**Status:** Proposed — Decisions 1–4 are expert-endorsed (relayed by the
product owner, Oct 26); both open questions ruled on by the expert the same day (see Rulings).
Nothing in this ADR authorizes implementation or installation yet. **Ruling 2 reconciled with ADR-0018 on 2026-11-13** (see
*Reconciliation*, at the end of this file): the typed refusal it required is no longer the rule at the process boundary.
**Deciders:** Human expert (architect), relayed by the product owner;
recorded by the implementer.

## Context

PR #4 (clean-room abstracts, expert-approved) extracted the concept layer
from lifo, wanix, and browsix; PR #3 (landscape) verified licenses for the
candidate substrate libraries. This ADR binds those findings into the
integration strategy for Phase 2: how the Node API shims sit on top of the
ADR-0002 VFS, how the Runtime ↔ Worker boundary is shaped, how the service
worker routes, and what persistence must never serialize. Every mechanism
below is informed ONLY by the abstracts in `docs/references/` — no
restricted source was read or copied for this document (Clean Room
Protocol).

## Decision

### 1. Shim substrate: `unenv` presets + `memfs` reference, on top of OUR VFS

> **Superseded in part, 2026-11-13 (P0-6, ADR-0004 D-1).** The `unenv` half of this decision is retired: `src/shims/presets.ts`
> was deleted along with the `unenv` dependency (PR #92). What survives is the `memfs` half, and it survives as a **reference**,
> never as an import: `memfs` stays a `devDependency` API-shape oracle, while the differential that measures the shims compares
> against **real Node** (`npm run diff:api`, 30/30 cases), which is a better oracle than a library that shares the shims'
> assumptions. The substrate shipped as hand-written shims on our own VFS, exactly as ADR-0004 D-1 argued: five presets would
> have brought five packages and a second timers clock into a tree whose timers are scheduler-backed (`src/shims/timers.ts`).
> Recorded here rather than rewritten, because the reasoning that chose `unenv` in Phase 2 is still the record of what was known.

- `unenv` (v1 stable, MIT — verified in PR #3 audit) provides the
  `path`, `process`, `buffer`, `events`, and `timers` presets.
  `path`, `process`, `buffer`, `events`, and `timers` are provided via
  unenv presets. The `crypto` preset is explicitly deferred to a future
  phase (see in-code documentation for rationale), and will not be
  initialized in Phase 2.
- `memfs` (Apache-2.0 — verified in PR #3 audit) serves as the `fs`
  API-shape reference and adapter.
- Both sit ON TOP of the custom ADR-0002 VFS; neither replaces it. The
  VFS remains the single owner of file state (ADR-0002 #1, #6). The
  shims translate Node-shaped calls into VFS operations — the inverted
  dependency direction documented in the lifo abstract.
- Constraint (standing until the expert merges this ADR): `unenv` and
  `memfs` are NOT installed. License verification stands from the PR #3
  audit; installation happens in the first implementation PR after
  approval, with the lockfile committed for the license audit surface.

### 2. Typed syscall envelope over the Runtime ↔ Worker boundary

From the browsix abstract (`docs/references/browsix-syscall-boundary.md`):

- Every shim operation crossing the Runtime ↔ Worker boundary is
  serialized through a single typed request/reply envelope.
- Each request carries a monotonically increasing `msgId`; the caller
  holds an outstanding-calls map keyed by that id and resolves the
  matching reply.
- Kernel-side operations are continuation-based: the owner thread is
  never blocked (ADR-0002 #2).
- Errors cross the boundary as structured-cloneable records (code +
  message) and are rehydrated into typed JS errors on the caller side —
  the contract that lets shims surface Node-faithful errors.

### 3. Service-worker routing with early ACK (expert refinement of the wanix pattern)

From the wanix abstract (`docs/references/wanix-sw-routing-pattern.md`),
as refined by the expert:

- Per-request `MessageChannel` with a transferred reply port; the SW
  stays a stateless relay; handler registration happens at runtime boot.
- Sentinel "not mine" replies fall through to the real network, and the
  dead-kernel case still degrades to the network — never a hung page.
- **Expert refinement:** the timeout bypass will NOT be a hard one-second
  fail. Cold dev-server compilation can legitimately take far longer
  than a second. Instead the kernel issues an **early ACK** (immediate
  receipt confirmation) followed by a **streamed keepalive** while
  compilation runs. The bypass triggers only when no ACK and no
  keepalive arrive within the liveness window — long compiles stay
  connected, a dead kernel still trips the bypass. Exact constants
  (ACK deadline, keepalive cadence, liveness window) are implementation
  tuning to be set in the implementation PR and calibrated against the
  fixture suite; they are not architectural choices.

### 4. Persistence exclusion policy (non-negotiable)

From the lifo abstract (`docs/references/lifo-persistence-pattern.md`):

- `node_modules` is explicitly and non-negotiably excluded from any
  Phase 2/3 persistence layer (IndexedDB or OPFS).
- It is treated as regenerable state: reinstall after reload, or an
  explicit opt-in snapshot.
- Rationale (paraphrased in the lifo abstract): serializing tens of
  thousands of installed files freezes the main thread for seconds;
  the exclusion prevents that hazard by construction.

## Consequences

- The shim layer has a defined substrate and a single boundary protocol;
  Phase 2 implementation can begin as a series of small, reviewable PRs
  (envelope first, then presets, then fs adapter) once the expert merges
  this ADR.
- The early-ACK routing keeps the preview lane usable during slow first
  builds without weakening dead-kernel detection.
- The exclusion policy fixes the persistence scope: sessions persist
  user-authored files and project sources, never dependency trees —
  which also caps snapshot size regardless of install size.
- No code, no dependencies, and no lockfile changes are authorized by
  this document.

## Rulings (expert, final and binding — Oct 26)

1. **`memfs` integration shape — DECIDED: WRAP, never extend.**
   `memfs` will be installed as a `devDependency` ONLY. It serves as an
   API-shape reference and a CI conformance oracle (diffing our `fs`
   shim against `memfs`). The custom ADR-0002 VFS remains the single
   owner of file state.
2. **Synchronous `fs` methods — DECIDED: Both, phased.** Phase 2 will
   return an explicit typed error via the Decision-2 error-rehydration
   contract. SAB+Atomics parking is deferred to a future phase,
   worker-side only, behind a feature flag.
   > **SUPERSEDED IN PART 2026-11-13:** the deferred phase arrived as ADR-0018, so the typed refusal no longer applies at the
   > process boundary. Ruling 1 and the worker-side-only requirement are untouched. See *Reconciliation* below.

### Implementation clarification (2026-11-05)

The typed-error rule above applies when a synchronous filesystem operation
would have to cross the Runtime ↔ Worker boundary. When the runtime and its
VFS are co-located inside the execution Worker, the shim may call the VFS's
worker-local synchronous methods directly; this does not block the page and
does not require SAB. Any future split-worker design must preserve the typed
error behavior until an explicitly approved synchronous bridge exists.

## Hosting Constraints

Future SAB+Atomics sync support will require COOP/COEP headers. This is
a new hosting constraint introduced by this ADR, not a requirement of
the current async-first VFS.

## Reconciliation 2026-11-13 — ruling 2 and ADR-0018

**Decider:** the project owner, in writing, on 2026-11-13, reconciling this record with ADR-0018 (accepted 2026-11-09 as
P0-1) and closing ADR-0001's open question 2. **Recorded by:** the implementer. Nothing above has been deleted: the original
ruling stays verbatim so the decision can be read as it was made.

### What ruling 2 said, and what it was for

Ruling 2 decided "both, phased": the sync surface exists, phase 2 answers a synchronous call with an explicit typed error
(`SyncNotSupportedError`, code `ESYNCNOTSUPPORTED`) carried across the typed envelope, and `SAB+Atomics` parking is "deferred
to a future phase, worker-side only, behind a feature flag".

The reasoning was sound and is worth preserving in its own right: at the time, a synchronous call from a Worker into another
Worker had no mechanism. Refusing by name is the correct answer to a boundary that cannot be crossed, and it is the same shape
this project uses elsewhere (ADR-0025's HTTP refusal, ADR-0026's link refusal). PR #7 implemented exactly that.

### Why it no longer applies at the boundary

Three dated steps, in order, each of which narrowed the rule:

1. **2026-11-05, this ADR's own clarification.** The typed error applies only when a synchronous operation "would have to
   cross the Runtime ↔ Worker boundary". Co-located, the shim may call the VFS's own synchronous methods. The clarification
   then set the condition for what would lift it: *"Any future split-worker design must preserve the typed error behavior
   **until an explicitly approved synchronous bridge exists**."*
2. **2026-11-08 → 2026-11-09, ADR-0018.** The split-worker design arrived, and with it the bridge: `SharedArrayBuffer` plus
   `Atomics.wait` in the calling Worker while the kernel answers. It was accepted by the owner on 2026-11-09 as P0-1 and
   implemented (`src/process/syscall-channel.ts`, `src/process/remote-fs.ts`, `src/vfs/port.ts`).
3. **2026-11-13, ADR-0001 open question 2 closed.** The sync surface is ruled emulated, not rejected. The reconciliation here
   follows from that ruling rather than deciding anything new.

So the condition in (1) is met by (2). **The typed-refusal obligation in ruling 2 no longer applies to a synchronous call
crossing the process boundary, because the bridge it was waiting for exists and is approved.**

The implementation confirms it: `ESYNCNOTSUPPORTED` and `SyncNotSupportedError` no longer appear anywhere in `src/`, `tests/`
or `docs/`. A rule whose only implementation has been removed while the text stayed binding is how the contradiction arose, so
the text is annotated here rather than left to be re-read.

### What survives, unchanged

- **Decision 1 (wrapping, never extending)** is untouched: `memfs` remains a devDependency oracle idea, the VFS remains the
  single owner of file state, and the shims translate rather than store.
- **Decision 2's protocol thinking survives in a different mechanism.** Ruling 2 wanted an error that keeps its POSIX code
  across the boundary. That is now satisfied by the channel: the kernel maps a failure to a code, the channel carries it, and
  the shim raises a Node-shaped error. The *requirement* was met; the *envelope* is not the thing that meets it.
- **"Worker-side only" is honoured and is load-bearing.** Only a Worker ever waits. The page's main thread never blocks.
- **Decision 3 (service-worker routing with early ACK)** and **Decision 4 (no `node_modules` in persistence)** are untouched
  and are exercised by the acceptance journey.

### The hosting constraint, now realised

The "Hosting Constraints" note above says future SAB+Atomics support will require COOP/COEP headers. It does, and they now
ship: `vite.config.ts` and `vercel.json` set them, `tests/browser/isolation.spec.ts` proves the editor, the preview origin and
the served documents are isolated, and `SharedArrayBuffer` is what every cross-Worker filesystem call rests on. The note is
left as written because it was correct when written; this paragraph records that it has been paid.

### What this reconciliation does not do

- It does not re-open ruling 1, decisions 3 and 4, or the rulings on `memfs`.
- It does not declare synchronous calls safe. **W-22 stays open**: a synchronous caller plus a kernel serve loop with other
  work is the shape in which one process waited 60 s for an answer its kernel never gave. The bridge existing is not evidence
  that a blocked call will be answered.
- It does not decide *which* calls must be synchronous. That is ADR-0018's open question 2, answered there as an interim
  scope (2026-11-13) and not as a settled subset.
- It does not revive PR #7. It was closed as superseded on 2026-11-13, with its measurements recorded on the PR.

### One thing ruling 2 implied that the implementation does not do

Ruling 2 said the future sync support would be "behind a feature flag". The shipped channel has no flag: cross-origin
isolation is the gate, and it is on by default in the product. That is a real difference between the ruling and the running
system, recorded here rather than quietly reinterpreted. If a non-isolated deployment lane is ever wanted, that is the moment
to introduce the flag, because in a non-isolated document the channel cannot be constructed at all.
