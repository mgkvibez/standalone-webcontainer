# ADR-0029: The product runs processes, and a command's outcome means "settled"

**Status:** accepted, 2026-11-12
**Relates to:** ADR-0018 (real processes), ADR-0028 (the transport seam), register item W-1.

## Context

W-1 said to connect `src/process/*` behind the workspace. ADR-0028 built the one thing that made it impossible: a preview request can now
reach a server that lives inside a process Worker. This record is the switch itself, and the two questions it forces.

`RuntimeSupervisor` held one `FileSystem`, one `InProcessRuntime` and a single `#runQueue`. Its queue was the audit's headline complaint:
`npm run dev` never returns, so the queue never drains and the terminal is dead until the Worker is terminated, taking the server with
it.

The question that actually needed deciding: **what does a `run` resolve with now?** Under a serialised runtime a run resolved when the
*program* was over, because the program was the only thing there was. Under processes a program can be over in one sense and very much
alive in another: `listen(3200)` returns, its body settles, its Worker keeps a live server, and Node keeps that process alive for a ref'd
handle.

## Decision

### A command's outcome means SETTLED, not EXITED

`ProcessHost` reports a settle when the exit message arrives and keeps the process live if `holdOpen(pid)` says it still owns a port
(the kernel answers `broker.portsOf(pid).length > 0`). `ProcessKernel.settled(pid)` resolves on either event, because both answer "the
command you typed is done": one says the program finished, the other says it is now a server.

Rejected: resolve only on exit. Then `node server.js` never resolves, the terminal is blocked exactly as under the supervisor, and the
process model buys nothing a user can see. Rejected: resolve right after `start` and never wait. Then `node index.js` would report before
its first line of output and every command would look asynchronous to the terminal.

The consequence is stated rather than hidden: **output a held-open program writes after its settle is not displayed**, because the run
that was rendering it has already reported. Streaming a live server's logs belongs with HMR/streaming (register W-3), not here.

### One kernel per project, one Worker per process, page protocol unchanged

`src/browser/runtime.worker.ts` holds a `ProcessKernel` (filesystem, process table, one serve loop per process, transport broker) and
disposes it on a project switch, which is where project isolation is enforced: switching projects kills its processes and drops its
files. The page still sends `run` and receives `chunk`s then one `result`, so `worker-client.ts`, the container and the terminal pane are
untouched. What changed is where the command runs.

`RuntimeSupervisor` is deleted rather than kept for the harness. The fixture harness gets `tools/harness/in-process-client.ts`, which
says in one sentence what it gives up (one thread, no Worker, a `while (true)` blocks it) and reuses the same `InProcessRuntime`,
`FileSystem` and gateway. The snapshot diff moved to `src/process/project-mirror.ts`, where its three rules live with tests: a path the
page deleted is removed, an unchanged text file is skipped, and a byte file is always written because a decode is not an equality test.

## What the switch broke, and what pins it

Two defects, both reachable only once commands stopped being serialised, both covered by `tests/browser/p1b.spec.ts` (start a server,
stop it, run the starter file, require its output):

1. **Terminal dimensions were not forwarded.** `ProcessHost.start` posted argv, env, cwd, buffer, sizes and the transport port, but not
   the terminal size, so the Worker built no terminal: `process.stdout.columns` was `undefined` and `isTTY` false. A program run from a
   terminal has to see the terminal it is in.
2. **Output was routed by PROCESS id while the page addresses RUNS.** The Worker kept one map from page process id to kernel pid and used
   it in both directions. For the first run the two numbers coincide (both `1`), so it looked correct; for the second, stdout was posted
   with the process id as the message id, the client had no pending entry for it, and the chunk was dropped in silence. The run then
   reported an empty `stdout` with exit code 0, the worst shape a bug can take: it looks like a program that printed nothing. There are
   now two maps, one per question, with a comment saying they are not interchangeable.

## Consequences

- A server can idle while the terminal runs a second command. The browser test asserts it with a real `listen(3200)` in a real Worker, a
  second command completing while it idles, and a kill that turns the next preview request into a 503.
- Timeouts are per process and enforced by terminating that Worker, so a `while (true)` blocks its own thread instead of the runtime's.
- The kernel is per project, so `node_modules` from an install survives into the next command instead of being re-seeded from a page
  snapshot that never contained it.
- `processByRun` entries are removed when a run settles, so a keystroke aimed at a finished program is a no-op rather than an error.
- The fixture harness no longer exercises a Worker at all. Fixtures measure Node compatibility, not the thread model, and the class says so.
