# ADR-0028: A preview request reaches a server that lives in another Worker

**Status:** accepted, 2026-11-12
**Relates to:** ADR-0018 (real processes), ADR-0002 #5 (the preview model), ADR-0019 (the runtime origin), ADR-0025/0026 (replacing
silence with a decision), register item W-1.

## Context

The November audit's single largest finding is a description rather than a bug:

> **Process model in the product** — library and browser tests only. Nothing in `src/browser`, `src/container` or the supervisor
> imports `process-host`, and `RuntimeSupervisor` still has a single `#runQueue`. A user running `npm run dev` still goes through the
> serialized lane, so a running server can't coexist with other commands.

Connecting it turns out to need one thing that does not exist, and it is not a call site. In the current design `InProcessRuntime`
owns the `PortRegistry` and the `PreviewGateway` in the same Worker that runs the program, so a request for `/preview/3200/` is
answered by a direct function call to a handler in the same thread. Under ADR-0018 each program runs in its own Worker and calls
`listen(3200)` there, so the `Server` object, its request listener closure and its port registry are all inside that Worker, while the
request arrives at the **kernel** (the Worker that owns the filesystem, the preview transport and, later, the runtime origin). There
is no handler to call across the boundary.

Four shapes were considered.

**A. Keep the servers in the kernel.** A program would ask the kernel to listen on its behalf and register its listener there. Rejected:
the listener is a JavaScript closure the program wrote. Sending it means serialising functions; keeping it means every `req` method,
`res.write` and the streaming semantics of a real `ServerResponse` become remote procedure calls, and `Server` would stop being the
object `require("http")` returns. It also puts the program's own code back in the kernel thread, which is the serialisation ADR-0018
exists to end.

**B. Route preview requests over the syscall channel.** One channel already exists per process, and it carries arbitrary JSON bodies.
Rejected: the channel is a single-slot shared buffer with **one in-flight call**. A preview request can take seconds (a dev server
rebuilding), and every filesystem call that process needs to do the work would queue behind it. It is also binary-hostile: the
framing base64s a body, which the syscall-metadata measurement already priced at 33% on every byte.

**C. A second `MessagePort` per process, correlated by id, with its own deadline.** Taken.

**D. Refuse previews for process-owned servers until the runtime origin lands.** Rejected: it is the refusal shape ADR-0025 rejected
for `http.request`. A dev server that cannot be previewed is the feature missing, not a boundary documented.

## Decision

1. **A process gets a dedicated reply port.** `ProcessHost.start` accepts `transport`, transfers it to the Worker, and the kernel keeps
   the other end. Transport requests never share the syscall channel.
2. **Headers cross as `Record<string, string>` and bodies as `Uint8Array`.** Structured clone carries binary for free; the page-to-runtime
   transport already made the same choice, and two wire shapes for one concept is how a header gets dropped on one path only.
3. **The process answers with its own gateway.** The routing decision stays inside the serving Worker, because that is the only place
   that owns both the port registry and the loader, and because the gateway already holds the request deadline and the queue pump that
   lets a handler awaiting `setTimeout` answer at all. A kernel-side second gateway would see a different registry.
4. **The kernel routes by port, and the port is authoritative because the serving Worker says so.** `PortRegistry` in the process Worker
   is subclassed so `bind`/`release` report the current list; the kernel cannot poll another thread's registry, and a timer-based diff
   would make the preview list lag a `listen()`, which reads as flake in any test that asserts on a served request.
5. **Every failure is a status code, never a rejection.** 400 for a URL that addresses no port, 503 for a port nobody serves, 504 for a
   process that accepted and did not answer in time, 500 for a handler that threw. The caller is a service worker answering a browser;
   a rejection there becomes a network error with no explanation.
6. **A process that still owns a port is held open.** The runtime returns as soon as the program body settles, which is right for a
   script and wrong for a server: Node keeps the process alive for a ref'd handle. `ProcessHost` asks `holdOpen` at exit time and leaves
   the process live if it still owns a port, so its Worker, its closure and its reply port survive. Killing it is then the only way to
   stop it, which matches what terminating a Worker means here.
7. **First pid wins a duplicate port.** A duplicate binding is a bug in the binder, not a tie to break.

## Consequences

- **A preview request now crosses a thread boundary**, so its latency includes one structured clone each way. Measured cost is not in
  this ADR: the bodies are the same bytes the gateway already buffered, and the alternative in B was worse by construction.
- **A listening process consumes a Worker and a channel** until it is killed. That is the real cost of the model and the reason
  `maxProcesses` exists (8 by default); a tab that starts twenty dev servers should hit a wall, not the tab's memory.
- **Ports are lost when a Worker dies**, and the broker treats a dead process as "nothing is listening" immediately rather than waiting
  for a deadline. A preview therefore fails fast after a crash, which is the behaviour a user can act on.
- **This is not the sandbox.** Every Worker is still on the page origin; ADR-0019's runtime origin and the Worker hardening (register
  W-19) are what make a hostile program containable.
- **The product is not switched over yet.** This ADR settles the seam; register W-1 keeps the wiring (runtime worker holds a
  `ProcessKernel` instead of the serialised `RuntimeSupervisor`) as the open item, because that change moves terminals, transport,
  `previewPorts`, `readRuntimeFile` and `stopServers`, and it should land as one verified step rather than two half-switched lanes.

## Evidence

- `src/process/process-transport.ts` — the broker, the mount-path parser, the id correlation and the four status codes.
- `src/process/process-kernel.ts` — filesystem + process table + serve loops + broker; the class the runtime worker will hold.
- `src/process/process-worker.ts` — the reply port, the reporting registry, and `attachTransport` answering through the runtime's gateway.
- `tests/unit/process-transport.test.ts` — 15 tests over **real** `MessageChannel`s: routing, 400/503/504/500, a late reply finding
  nothing, detach failing its own pending request, http/https kept apart, malformed port reports ignored.
- `tests/browser/process-transport.spec.ts` — one real Worker per process, a program that calls `listen(3200)`, a request answered by
  the kernel, a second command finishing while the server idles, and a kill that turns the next request into a 503.
- Mutation checks: with `attachTransport` disabled the request never answers (504 on the deadline); with `holdOpen` removed the process
  is retired at exit and the first request 503s. Both fail the browser test, which is the only reason to trust it.
