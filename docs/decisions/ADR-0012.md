# ADR-0012 — ES Modules Through the CommonJS Loader

**Date:** 2026-11-04
**Status:** Proposed — implemented to keep building; every decision below is provisional and listed for the

**P0 supersession (proposed 2026-11-08):** proposed for supersession by native ESM with live bindings and top-level await (Phase 5); the current acorn transform to CommonJS is a compatibility stopgap. See P0-rulings.md P0-4.
single end-of-project audit. Nothing here authorises a change to the ratified charter or ADR-0001/0002.
**Deciders:** Implementer (provisional), for the human expert to ratify or overturn.

## Context

The corpus is written as ES modules, and rightly so: `node core.mjs` is what an ordinary modern Node program is. The
loader was CommonJS-only by design (ADR-0004), which made the fixture set unrunnable in a way that no amount of corpus
work could fix. Fixture 1 calls `vite`, fixtures 5/6 call `next`/`nuxt`, and the two shadcn fixtures call CLIs that ship
ESM. ESM was therefore not a nicety but the thing standing between the project and its first real gate number.

Two routes were available. Native `import()` of `blob:`/`data:` URLs needs no parser, but bare specifiers inside would
resolve against the browser's rules rather than our VFS, so the same source would resolve differently in a test and in a
preview — the one thing a conformance harness cannot afford. Transforming to the CommonJS shape keeps a single
resolution path: every specifier goes through the loader that already walks `node_modules` in our VFS.

## Decision

1. **Transform, do not re-dispatch.** `transformEsm` rewrites module syntax to the CJS shape the existing factory
   already compiles, so ESM and CJS share resolution, caching, shims and error handling.
2. **acorn 8 (MIT) parses.** Regex rewriting of `import`/`export` is not a transform, it is a guess. acorn is a runtime
   dependency, not a dev one, because the loader ships to the browser.
3. **Format by extension, then nearest `package.json` `type`,** walking up and stopping at the filesystem root: Node's
   rule, cached per directory because it reads a file on every `require` otherwise.
4. **Interop both directions.** `__esmInterop` returns `module.exports` for CJS and `exports.default` for a transformed
   module, matching Node's default-import behaviour for each.
5. **Top-level await is supported in the ENTRY module and refused elsewhere, each by its own named code.** Amended
   2026-11-10; see "Amendment: top-level await, scoped by measurement" below.
6. **`import.meta.url` is a `file://` URL**, matching Node, not a bare VFS path.

## Consequences

Easier: the corpus can now be written the way its tools are actually written, and fixtures 5, 6, 12 and 18 stop being
blocked on syntax alone.

Harder, and recorded rather than hidden:

- **No live bindings.** `export let x` snapshots at export time; a mutation is not seen by importers. Bundlers pay for
  this; we do not yet.
- **No async module records.** Top-level await works in the entry module (the process is waiting for it anyway) and is refused
  in every other module with `TLA_IN_NON_ENTRY`, naming the module and its importer. Node supports the general case; this
  runtime does not, and says so in the message instead of looking like a syntax error.
- **Transform cost per module** at load time, and stack traces that point at generated column offsets.

## Open Questions

1. Is the transform the right long-term answer, or does the worker lane need real ESM so that live bindings exist?
2. Do we accept no-live-bindings, or emit getters (`Object.defineProperty(exports, name, { get })`) so mutations are
   visible? The second is cheap for plain `let` exports and would remove a whole class of subtle wrongness.
3. Top-level await: settled for the entry module and refused elsewhere, by measurement (see the amendment). The general case
   stays refused until something the corpus runs has a library module that awaits at its top level.
4. Should `import.meta.dirname`/`filename` exist, given Node now ships them?

## Deviations Recorded

`__esmInterop`, `__dynamicImport` and `__importMeta` are injected into module scope. A user module declaring one of
those names would collide. Prefixed names make that improbable rather than impossible; a symbol-based injection would
remove it entirely.

## Approval

Not approved. Written by the implementer under the owner's instruction to build to completion and the expert's
single end-of-project audit.

## Amendment: top-level await, scoped by measurement (2026-11-10)

**What was measured first.** The earlier diagnosis was "Vite's own ESM with top-level await", which sounds like a property of the
codebase. `tools/scan-tla.ts` counts it instead: every module parsed with acorn, distinguishing a real top-level `await` from one
inside a function, then listing each module's importers. For the frozen `vite@5.4.21` snapshot the answer is **one module out of
fourteen, `bin/vite.js`, with two awaits and no importers**. Both are inert in practice: line 7 is `await import('source-map-support')`
behind a `!import.meta.url.includes('node_modules')` guard, line 53 is `await import('node:inspector')` behind `--profile`. The heavy
files are clean: `dist/node/cli.js` (30 kB) and `dist/node/module-runner.js` (54 kB) have no top-level await at all.

**Why that decides the design.** The expensive part of top-level await is not the `await`, it is async module records: a module whose
evaluation is async makes every importer's evaluation async, transitively, with a new linkage algorithm. An entry module has no
importers, so none of that applies. What is needed instead is one boundary: evaluate the entry as an async body and await it before the
program counts as started, which is Node's own model.

**The three rows, and who owns each code.**

| Situation | Node | This runtime |
|---|---|---|
| top-level `await` in the entry module | runs | **runs**; the runner pumps the timer queue while the body is suspended, then awaits the evaluation before judging the process |
| static `import` of a module with top-level await | runs, via async module records | refused as **`TLA_IN_NON_ENTRY`**, naming the module and the importing file |
| `require()` of a module with top-level await | `ERR_REQUIRE_ASYNC_MODULE` | the same code and message shape, because Node throws it for the same program |

The split matters: row two is a scope limit, row three is a language rule. Borrowing Node's code for row two would tell an author their
program is wrong when it is this runtime that is narrower. Row two also refuses *before* the module evaluates, because a module that
cannot be waited for must not run its first statements and then fail.

**One bug this exposed.** An entry whose body was `await new Promise((resolve) => setTimeout(resolve, 5))` deadlocked: the body was
suspended on a scheduler timer, the runner was awaiting the promise, so nothing ran the timer, and the run ended at its timeout having
printed nothing. `Scheduler.drainWhile` pumps the queue until the body settles and then hands back to the ordinary `drain` for the
accounting. An entry awaiting only a microtask never showed it, which is exactly why the first top-level-await test passed while the real
shape hung.

**What would change this.** A library module that awaits at its top level, in something the corpus actually runs. Then async module
records stop being theoretical, the general case gets built, and the differential harness becomes the oracle for the transitive
ordering. Until that measurement exists the closed set stays closed: `TLA_IN_NON_ENTRY` is the answer, and reading this section is how
the next person gets it.
