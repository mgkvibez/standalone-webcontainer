# ADR-0012 — ES Modules Through the CommonJS Loader

**Date:** 2026-11-04
**Status:** Proposed — implemented to keep building; every decision below is provisional and listed for the

**P0 supersession (proposed 2026-11-08):** proposed for supersession by native ESM with live bindings and top-level await (Phase 5); the current acorn transform to CommonJS is a compatibility stopgap. See P0-rulings.md P0-4.
single end-of-project audit. Nothing here authorises a change to the ratified charter or ADR-0001/0002.
**Deciders:** Implementer (provisional), for the human expert to ratify or overturn.

## Context

The corpus is written as ES modules, and rightly so: `node core.mjs` is what an ordinary modern Node program is. The
loader was CommonJS-only by design (ADR-0004), which made the fixture set unrunnable in a way that no amount of corpus
work could fix. Fixture 1 calls `vite`, fixtures 5/6 call `next`/`nuxt`, and the two shadcn fixtures call CLIs that ship
ESM. ESM was therefore not a nicety but the thing standing between the project and its first real gate number.

Two routes were available. Native `import()` of `blob:`/`data:` URLs needs no parser, but bare specifiers inside would
resolve against the browser's rules rather than our VFS, so the same source would resolve differently in a test and in a
preview — the one thing a conformance harness cannot afford. Transforming to the CommonJS shape keeps a single
resolution path: every specifier goes through the loader that already walks `node_modules` in our VFS.

## Decision

1. **Transform, do not re-dispatch.** `transformEsm` rewrites module syntax to the CJS shape the existing factory
   already compiles, so ESM and CJS share resolution, caching, shims and error handling.
2. **acorn 8 (MIT) parses.** Regex rewriting of `import`/`export` is not a transform, it is a guess. acorn is a runtime
   dependency, not a dev one, because the loader ships to the browser.
3. **Format by extension, then nearest `package.json` `type`,** walking up and stopping at the filesystem root: Node's
   rule, cached per directory because it reads a file on every `require` otherwise.
4. **Interop both directions.** `__esmInterop` returns `module.exports` for CJS and `exports.default` for a transformed
   module, matching Node's default-import behaviour for each.
5. **Refuse top-level await explicitly.** A named `EsmSyntaxError` tells the author to move the await into an async
   function. Silently mis-executing it would be worse than refusing.
6. **`import.meta.url` is a `file://` URL**, matching Node, not a bare VFS path.

## Consequences

Easier: the corpus can now be written the way its tools are actually written, and fixtures 5, 6, 12 and 18 stop being
blocked on syntax alone.

Harder, and recorded rather than hidden:

- **No live bindings.** `export let x` snapshots at export time; a mutation is not seen by importers. Bundlers pay for
  this; we do not yet.
- **No top-level await.** Real `vite` and `next` bins may need it, which would move them from "works" to a specific,
  named refusal.
- **Transform cost per module** at load time, and stack traces that point at generated column offsets.

## Open Questions

1. Is the transform the right long-term answer, or does the worker lane need real ESM so that live bindings exist?
2. Do we accept no-live-bindings, or emit getters (`Object.defineProperty(exports, name, { get })`) so mutations are
   visible? The second is cheap for plain `let` exports and would remove a whole class of subtle wrongness.
3. Top-level await: refuse permanently, or implement by making module evaluation async (which changes every caller)?
4. Should `import.meta.dirname`/`filename` exist, given Node now ships them?

## Deviations Recorded

`__esmInterop`, `__dynamicImport` and `__importMeta` are injected into module scope. A user module declaring one of
those names would collide. Prefixed names make that improbable rather than impossible; a symbol-based injection would
remove it entirely.
