# ADR-0018: Real processes with a real event loop

**Date:** 2026-11-08
**Status:** Accepted. Process model accepted by the owner on 2026-11-09 (P0-1); implementation is Phase 1+ and lands incrementally.
**Open question 2 (sync channel scope) is answered on an interim basis on 2026-11-13** (see *Scope ruling*, at the end of this
file). Questions 1, 3, 4 and 5 remain open.
**Deciders:** Expert (architecture is reserved to the human expert per the charter); drafted by the agent from the
P0 review plan and the current source.

## Context

Execution today is a one-shot script run, not a process. `InProcessRuntime.run()` loads the entry module, drains
continuations until the microtask/timer queues are quiet, then snapshots stdout and stderr into an
`ExecutionResult`. Three consequences decide most of the remaining roadmap:

1. **A program cannot stay alive.** A development server that listens on a port has no reason to keep running once the
   scheduler is quiet, so the run ends and the "server" disappears. Nothing in the model can express "still running".
2. **`process.exit()` does not exit.** It throws `ProcessExit`, which the scheduler surfaces as
   `Uncaught ProcessExit` and then continues draining. The status reported to the caller is not derived from a process
   state machine.
3. **Time is virtual.** ADR-0013 gives each execution a 1,000 virtual ms budget and caps `setInterval` at 100 firings.
   That bought determinism for the fixture gate, and it also makes real elapsed time meaningless. The plan records the
   same finding as "process lifecycle: broken".

`process.on` is a no-op, `process.nextTick` is `queueMicrotask` (so it interleaves with promise jobs in the wrong
order), and there is no `setImmediate`. Terminating a run means terminating the one Worker, which kills every process in
it — accurate today because there is never more than one.

The target is contract-level parity with StackBlitz's WebContainer, whose public description has each process in its own
Worker with a synchronous channel to a single-owner kernel.

## Decision

Replace the one-shot run with real processes.

- **One Worker per process.** A `spawn` creates a process Worker. A process owns its event loop and its own globals.
- **A kernel that stays single-owner.** The VFS, the process table and the port registry live in a kernel Worker. No
  process ever holds the filesystem directly.
- **A real event loop** (`src/runtime/event-loop.ts`) that tracks active handles — timers, listening servers, pending
  I/O — each `ref`/`unref`-able as in Node. The loop is empty when the handle count is zero and no microtasks are
  pending, and an empty loop is what ends the process.
- **A process state machine**: `starting → running → exiting → exited`. `process.exit(code)` sets `exiting`, emits
  `exit` synchronously, records the code, then throws a sentinel. Every shim entry point and timer wrapper rethrows that
  sentinel once the state is `exiting`, so a callback cannot log and carry on. Because user code can still swallow the
  sentinel in a bare `catch`, the supervisor also terminates the Worker as soon as it observes the exit message.
- **Real process events**: `on`/`once` for `exit`, `beforeExit`, `uncaughtException`, `unhandledRejection`, `SIGINT`,
  `SIGTERM`, with the Worker's `error`/`unhandledrejection` hooked in. An uncaught error with no listener prints Node's
  format to stderr and exits 1.
- **Correct callback ordering**: a `nextTick` queue that drains before promise jobs, and `setImmediate`/`clearImmediate`
  that run after I/O and before later timers.
- **Cross-process synchronous calls** use `SharedArrayBuffer` plus `Atomics.wait` in the calling Worker while the kernel
  answers — the shape StackBlitz describes publicly. Async calls reuse the same channel without blocking.
- **The virtual clock is demoted**, not deleted: `virtualClock: true` remains an opt-in for deterministic unit tests.
  The 1,000 virtual ms budget and the 100-firing interval cap leave the default path.

## Consequences

- ADR-0013 is superseded (see ADR-0013's status line). Fixtures that relied on virtual time must either run under real
  time or opt into the virtual clock explicitly; this must be settled before the fixture gate is re-frozen.
- `process.kill` and per-run timeouts become `Worker.terminate()` on that one process. ADR-0004 D-5 ("a `while (true)`
  loop cannot be stopped") is resolved for the process lane; it stays true inside `run()` used as a library.
- `SharedArrayBuffer` requires cross-origin isolation, so this ADR depends on ADR-0019 being accepted first. That
  ordering is why Phase 2 is held.
- One Worker per process costs startup latency and memory per process, and makes the current serialised executor
  concurrent. The P1b container's documented "one run at a time" limit ends here, which also means the container layer
  needs a scheduler that did not exist before.
- Determinism gets harder before it gets easier: real timers mean the differential suite in Phase 1 must compare against
  real Node under real time, and any flake is a finding rather than something to be smoothed away.
- Nothing in the VFS, the loader or the npm resolver has to change for this ADR. It replaces the scheduler and the
  lifecycle, not the substrate.

## Open questions — for the decider

1. **Kernel placement.** Does the kernel Worker own the process table, or does the *frame's* main thread own it and the
   kernel stay purely a filesystem server? The plan says kernel Worker; the difference is who enforces kill and
   timeouts.
2. **Sync channel wording.** `Atomics.wait` blocks the calling Worker. Do we accept that for every fs call, or route only
   a named set of synchronous operations (`readFileSync`, `statSync`, `spawnSync`) through it and make the rest async?
   > **INTERIM ANSWER 2026-11-13:** every operation on the filesystem port blocks, because the named set the loaders need is
   > already the whole port. Recorded with its limits in *Scope ruling* at the end of this file. Still open as a question of
   > contract, and revisited on any measured latency or liveness finding (W-22 is the standing one).
3. **Fixture replay.** With real timers, fixture 4's 25 ms chain and any `setInterval` fixture become wall-clock bound.
   Do fixtures run under real time (flaky-proofing via generous thresholds), or does the gate standardise on
   `virtualClock: true` and accept that it does not prove real-time behaviour?
4. **Signal semantics.** `SIGINT`/`SIGTERM` map to `Worker.terminate()` with no chance to run a handler, or to a
   message the process may handle before termination? The second is closer to Node and lets a dev server flush.
5. **Scope of "process".** Does `node -e "..."` or a `spawn` from inside user code create a nested process Worker, and
   is there a cap on total Workers?

## Implementation note (2026-11-09): where the filesystem lives

The process model is now real: a `ProcessTable`, one Worker per process, and a `ProcessHost` that gives every process its
own syscall channel. The filesystem did not move with it immediately, so this note records how it did.

The kernel owns the VFS. A process cannot reach it, so `src/vfs/port.ts` describes the eight synchronous calls the shims
and loader make, and two implementations satisfy it: the real `FileSystem` (in-process, in tests) and
`createRemoteFileSystem` (inside a Worker, over the channel). The port's shapes are copied from the VFS rather than
invented for it, so the shim adapter that turns a stat into Node's `Stats` is untouched and there is one description of a
stat in the codebase.

Three consequences worth stating:

- **Errors keep their POSIX identity across the boundary.** `ENOENT` reaching user code as a generic failure would turn
  "the file is missing" into "the runtime is broken", so the kernel maps failures to codes and the channel preserves them.
- **Requests are untrusted.** The kernel validates operation, path and options before touching the VFS. An unknown
  operation is a refusal (`EINVAL`), not a default branch.
- **Binary travels base64 inside JSON**, a documented cost of the JSON payload format. A binary side-channel would remove
  the overhead of it and is not part of this step.

Verified end to end in a browser: a real program running in its own Worker reads two files, every read crossing to a
different Worker that owns the VFS, with unchanged output (`tests/browser/kernel-fs.spec.ts`).

## Implementation note (2026-11-09): one serve path, not two

The first end-to-end run of the process host failed, and the reason is worth recording because the code looked correct on
both sides in isolation.

The kernel was answering the same request twice. After `Atomics.wait` returned, the server assumed the wake-up meant "a
request is pending" and served whatever the sequence number pointed at. But a wait also ends when the state moves
somewhere the server cannot serve, such as an answer the caller has not consumed yet. In that case it re-answered the
previous request, overwrote the state with `responsePending` for an older sequence, and the pair desynchronised: the caller
waited for an answer the server had already thrown away, and the server waited for a caller that had given up.

The cause was duplication. The blocking and async serve paths were written separately, so a fix applied to one did not
reach the other. They now share one state machine (`createServerCore`), and both loops re-read the state on every
iteration instead of trusting the wake-up.

Two rules follow, and they apply to any future channel work:

- A wake-up is not evidence of work. Re-read the state, then act.
- Duplicated concurrency logic rots asymmetrically. If two paths differ only in how they wait, share everything else.

## Implementation note (2026-11-09): the clock does not advance while a program holds the thread

While writing the end-to-end test, a program that busy-waited on `Date.now()` never finished. That is not a channel bug:
the runtime hands each program a *virtual* clock (ADR-0013), and it advances between turns, so a program that spins waiting
for it to move waits forever. In Node the same loop also hangs; the difference is what can end it.

The process model is the answer: `kill` terminates the Worker, and the host keeps working. That is now tested with a
deliberate `while (true) {}`, because a hazard that can only be escaped by termination deserves a test that proves
termination works.

It also changed how concurrency is measured. Test programs are CPU-bound with fixed iteration counts, never clock-bound,
and the assertion compares a two-process run against a one-process baseline on the same machine rather than an absolute
duration, which would only measure the machine.

## Scope ruling (2026-11-13): the synchronous surface, call by call

**Decider:** the project owner, in writing, on 2026-11-13, as part of closing ADR-0001's open question 2. **Recorded by:** the
implementer, from the code rather than from the design notes. This answers open question 2 on an **interim** basis. It does not
settle the remaining open questions above, and it makes no claim of safety.

### The ruling

**Every operation on the filesystem port blocks.** There is no named subset, and not because a subset was rejected: the set the
loaders and npm need is already the whole port. Module resolution probes with `statSync` in a batch, `require` reads with
`readFileSync`, and the packer writes with `writeFileSync`; routing "the rest" async would leave nothing in that rest that any
caller uses.

The promise forms do **not** add a second blocking path. In a Worker the sync call has already blocked, so `readFile` calls
`readFileSync` and resolves the moment it returns (`src/process/remote-fs.ts`). There is one implementation per operation, as
ADR-0004 D-2 intended.

### The eight calls, and the two optional ones

The port is `src/vfs/port.ts`; the channel implementation is `src/process/remote-fs.ts`; the shim that turns these into Node's
surface is `src/shims/fs.ts`. "Blocks" means the **calling Worker** stops in `Atomics.wait` on a shared buffer while the kernel
Worker answers. The page never blocks.

| Port member | Required | Blocks in the process lane | What it actually does |
| --- | --- | --- | --- |
| `readFileSync(path, encoding?)` | yes | yes | One request frame; returns text or bytes. If the answer does not fit the response region it re-reads in ranges and joins them, decoding text **once** at the end so a slice boundary inside a multi-byte character cannot corrupt it |
| `writeFileSync(path, data, options?)` | yes | yes | Strings travel as UTF-8, bytes as binary. Up to 128 KiB is one frame; larger payloads are split into 128 KiB pieces where the **first replaces and the rest append**, so a half-written file is never visible as a whole one |
| `mkdirSync(path, options?)` | yes | yes | `recursive` is passed through; the kernel validates path and options before touching the VFS |
| `readdirSync(path)` | yes | yes | Returns names only. `withFileTypes` is the shim's business, built from a stat per entry |
| `statSync(path)` | yes | yes | Returns `{kind, size, modifiedAt, createdAt}`; the shim adapts it to Node's `Stats`. One description of a stat in the codebase, shared by both lanes |
| `statManySync(paths)` | **optional** | yes, as one batch | One round trip for N stats where the transport can batch (`callMany`), otherwise the same answers one call at a time. A missing path answers `null` instead of throwing, and a failed entry costs only itself |
| `unlinkSync(path)` | yes | yes | Kernel maps the VFS outcome to a POSIX code. The shim remaps directory-unlink to `EPERM` because that is what Node reports there |
| `rmdirSync(path)` | yes | yes | Strict POSIX: `ENOTDIR` on a file, `ENOTEMPTY` on a non-empty directory, `EINVAL` on the root |
| `renameSync(from, to)` | yes | yes | Prefix-scan rename in the VFS |
| `utimesSync(path, modifiedAt)` | **optional** | **no: refused** | Real in-process. `createRemoteFileSystem` does not implement it, so in a process Worker the shim throws `ERR_NOT_SUPPORTED` rather than pretending. A named refusal, which is the project's preferred shape for a boundary (ADR-0025, ADR-0026) |

Two things follow that are easy to state wrongly:

- **The port is not the `fs` surface.** The shim declares 53 sync members, and most of them are compositions over these ten
  (for example `existsSync` is a `statSync` that answers a boolean, and `lstatSync` is documented as `statSync` because this
  VFS has no links: ADR-0026). What crosses the boundary is the port, not the surface.
- **`utimesSync` is the one dated divergence between the lanes.** In-process it sets a modification time; in a process Worker
  it refuses by name. Its message says the filesystem "does not store timestamps", which is true of a substrate that lacks the
  capability but not of this VFS, which does store them and simply is not asked over the channel. Recording the wording here
  rather than fixing it in this change: it is a one-line message change and belongs to whoever next touches the shim.

### Frames, deadlines and capacities

| Limit | Value | Where |
| --- | --- | --- |
| Caller's default deadline per call | 5,000 ms, and a caller may choose its own | `src/process/remote-fs.ts:101,107` |
| Kernel poll interval per channel | 250 ms | `src/process/process-kernel.ts:132` |
| Request region | 512 KiB | `src/process/process-host.ts:112` |
| Response region | 256 KiB | `src/process/process-host.ts:112` |
| Write chunking threshold | 128 KiB, first piece replaces, rest append | `src/process/remote-fs.ts:49` |
| Oversize read | re-read in ranges (`ERESPTOOLARGE` triggers it) | `src/process/remote-fs.ts` `readInRanges` |
| Binary cost | base64 inside JSON, roughly +33% on every binary byte | `src/process/syscall-channel.ts` header |

Neither an oversized payload nor an oversized answer is ever truncated: a short response is worse than a failure, so the
channel refuses (`SyscallCapacityError`) and the callers that can chunk do so deliberately.

### The failure modes, as a caller experiences them

| Failure | Class | What the caller sees |
| --- | --- | --- |
| No answer within the deadline | `SyscallTimeoutError` | A throw from the sync call, and the channel is left usable rather than wedged |
| Kernel refused the operation | `SyscallRejectedError` | Carries the POSIX `code`, so `err.code === "ENOENT"` works as in Node |
| Frame too large | `SyscallCapacityError` | A throw, never a truncated value |
| Channel closed (process killed) | `SyscallChannelClosedError` | A throw naming the condition |

### What is explicitly NOT claimed: W-22

**A blocked call is not guaranteed to be answered.** This is not a theoretical caveat; it is an open defect.

In a full single-worker browser lane, one process waited **60 seconds** for a syscall its own kernel never answered
(`Syscall 696 did not answer within 60000 ms`). The same spec passes alone in about 13 seconds, and the same failure was
reproduced on `origin/main` in a full lane before the streaming work that discovered it, so it is not a regression from any
single change. The suspected shape is exactly the one this ruling creates: a caller parked in `Atomics.wait` while the kernel's
per-channel serve loop has other work. The cause is **not established**, the item is **open as W-22**, and the only escape from
a parked caller is terminating its Worker.

So the interim scope is: *these calls exist and block only their caller, and each carries a deadline; they are not proven
live under load.* Any future claim that the synchronous surface is "safe" needs W-22 closed with a measurement, not with this
paragraph.

### Remaining limitations of the channel

1. **Liveness (W-22)**, above. The only standing measurement is the quarantined benchmark in
   `tests/browser/bench-scaling.spec.ts`, and how to run it reliably is documented in `docs/bench/process-scaling.md`.
2. **One call in flight per channel.** A blocked Worker can wait on one thing. Parallel work is parallel channels; there is no
   queue, and adding one would not help a blocked caller.
3. **One kernel for every process.** All processes' synchronous calls are answered by a single kernel Worker, which is the
   design (single-owner VFS) and also the throughput ceiling.
4. **Binary costs a third more than its bytes** while the payload format is JSON. A binary side-channel is named in the code as
   the later step and is not part of this scope.
5. **Cross-origin isolation is mandatory.** No COOP/COEP means no `SharedArrayBuffer`, which means no process lane at all.
6. **`utimesSync` does not cross the boundary** (above).

### What stays open

Open questions 1 (kernel placement), 3 (fixture replay under real time), 4 (signal semantics) and 5 (scope of "process") are
untouched by this ruling. Question 2 is answered **interim**: all port calls block; revisit on a measured latency or liveness
finding, with W-22 as the standing trigger. This is recorded as an interim scope rather than a settled subset on purpose, so
that closing W-22 can change the answer without contradicting a decision record.
