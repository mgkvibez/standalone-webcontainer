# ADR-0022: Batched syscalls, so independent calls cost one wake-up

**Status:** accepted, 2026-11-09
**Supersedes:** nothing. **Relates to:** ADR-0018 (the synchronous syscall channel), ADR-0021 (body-only framing).

## Context

ADR-0018 gave each process a blocking channel: a call is a request region write, an `Atomics.notify`, and an
`Atomics.wait` until the kernel answers. The metadata instrument says a boot makes 96 calls and that 78.8% of the traffic is
envelope, which is another way of saying the payload was never the problem. The scaling bench put a small call at roughly
150 µs and a 4 KiB read at ~120 µs. Both numbers are round trips, not bytes.

ADR-0021 removed the bytes that did not need to be sent. It did not touch this: sixteen small calls still stop the caller
sixteen times, and the caller is a Worker that can only wait on one thing.

Some of those calls are genuinely sequential (`read` depends on `stat`). Many are not. Module resolution is the clearest
case: for one specifier the resolver asks "does this exact file exist", then up to three extension guesses, then "is this a
directory", then "is there a manifest", then the index files. Those probes do not depend on each other. Their ORDER decides
which one wins, not whether they can be asked together.

## Decision

**A batch is a request that carries requests, answered in one wake-up.**

1. A request of the shape `{ "@batch": [req, …] }` is expanded by the channel's server core, not by the handler. The
   handler stays a function from one request to one answer, so the filesystem, and anything else behind the channel, is
   unchanged and unaware.
2. The kernel answers every entry while it already holds the thread, and publishes ONE response frame whose value is
   `{ "@batch": [outcome, …] }`. Each outcome is the same `ok`/`value`/`error` shape a single call returns.
3. `SyscallClient.callMany(requests, options)` sends one message and returns the outcomes in request order. The caller is
   stopped once.
4. `@batch` is reserved. `call` refuses a request carrying it, and a nested batch is refused, because the distinction
   between "one call" and "several" is lost at the kernel and a caller that trips over it would otherwise get an array back
   from a call it thought was singular.

**Where it is used.** `FileSystemPort.statManySync` is an optional capability (a substrate that cannot batch is still a
filesystem) and the module resolver is its first caller. Resolution now asks its file candidates and the candidate's
manifest in one probe, and its index candidates in a second. The local VFS answers by looping, which is what the caller
would have written; the channel-backed port answers in one round trip.

## Consequences

**What the numbers say.** `tests/browser/batch-roundtrips.spec.ts` runs two real Workers over a real channel. Sixteen stats
sequentially: 16 request frames, 0.84 ms. The same sixteen batched: 1 frame, 0.19 ms, a 4.4x improvement on a workload whose
handler does nothing. The mechanism is asserted as a count (`sequentialEncodes === 16`, `batchEncodes === 1`), because a
timing assertion on a shared machine can pass for the wrong reason; the 3x timing bound is only there to catch batching
becoming a pessimisation.

**What resolution saves.** `tests/unit/resolver-batch.test.ts` counts probes through a port that records how it was asked:
one probe for a specifier that resolves by exact name or extension (was up to four), two for a directory (was up to five,
because the manifest question now rides in the first message). At ~50 µs per avoided round trip, a specifier that needs an
extension saves ~100–150 µs of boot.

**Accepted limits, stated rather than discovered later.**

- A batch shares ONE deadline and ONE response region. A batch too large to fit fails as a batch (`ERESPTOOLARGE`); the
  caller's recourse is to send it in pieces. Nothing splits a batch automatically, because that would hide the cost.
- Entries fail independently by design. A caller that needs all-or-nothing gets that by inspecting the outcomes, not from
  the primitive.
- There is no automatic batching. The client does not collect calls in a microtask and ship them together, tempting as that
  is: it would change when a side effect happens, and this runtime's whole argument is that timing semantics are Node's.
- The kernel still serves one batch at a time per channel, which is unchanged from ADR-0018: parallelism is more channels,
  one per process.
- The end-to-end boot effect is not claimed. Resolution is not the boot's only cost, and the boot benchmark was not re-run
  against a like-for-like baseline; the per-call and per-probe numbers are what this decision rests on.

## Verification

- `tests/unit/channel-batch.test.ts` (7 tests): a batch answered in one wake-up, in order, with a missing file isolated as
  one failed entry; binary bodies inside a batch in both directions; a single call answered exactly as before; the reserved
  key and nesting refused; an empty batch not transmitted.
- `tests/unit/resolver-batch.test.ts` (9 tests): exact file, extension guess, `.js` over `.json`, directory index,
  `package.json` main, a miss reported as a miss, the `node_modules` walk asking nothing twice, and the seam itself: the
  channel-backed port spends ONE batched call for a resolution and zero single calls, while a transport without the
  capability falls back to one call at a time and still resolves correctly. Without that last pair, a port that quietly
  stopped passing the capability through would still return right answers and the round trips would come back unnoticed.
- `tests/browser/batch-roundtrips.spec.ts`: the mechanism and cost claims above, through the real client.
- Mutation-checked: making the resolver pick the LAST hit instead of the first fails exactly the two order tests, so the
  order contract is not decoration. Restored byte-identical.
- The transport conformance suite from ADR-0021 still passes untouched, which is the check that the single-call path did not
  move.
