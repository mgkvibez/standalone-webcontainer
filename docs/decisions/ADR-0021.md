# ADR-0021: Frame binary bodies, and only messages that carry one

**Status:** Accepted
**Date:** 2026-11-09

## Context

Every syscall crossed the channel as JSON. File contents could not be JSON, so they were base64-encoded first: a 64 KiB read
travelled as ~87 KiB of text, and the client decoded it back into bytes. The metadata measurement (PR #29) put the envelope
at 78.8% of all syscall bytes on a toolchain boot, but that figure was about *small* calls; this ADR is about what happens
when the payload is the point.

Two costs were on the table. Base64 inflates a binary by 33% before any copying, and both ends paid CPU to encode and decode
it. The shared buffer makes neither necessary: it is already raw memory, and a length-prefixed blob can sit in it directly.

## Decision

A new codec (`src/process/frame.ts`) frames messages that contain a `Uint8Array`:

```
0        magic 'F' (0x46)
1        version 1
2..5     header length, uint32 little-endian
10..     header JSON (structure, with each body replaced by an index), then the bodies concatenated
```

**A message with no binary body is not framed at all: it is plain JSON, byte for byte what the previous codec produced.**
Decoding sniffs the first byte: `F` means frame, anything else is parsed as JSON.

Binary bodies are carried as raw bytes end to end. A response body is `{kind: "bytes", bytes: Uint8Array}`, a write request
carries `data: Uint8Array` with `dataEncoding: "binary"`, and the client returns a `Uint8Array`. Base64 no longer appears on
the wire.

## Why the two-form wire, and not framing everything

The first implementation framed every message, which was simpler and wrong. Measured through the real client against the
real handler (`npm run bench:syscall-metadata`), a frame costs a constant **~46 bytes per message**, and a toolchain boot is
96 small calls that mostly carry no binary at all:

| workload | calls | bytes/call, framed | bytes/call, base64 | change |
| --- | ---: | ---: | ---: | ---: |
| toolchain boot (text, stats, readdir) | 96 | 215.2 | 169.2 | **+27.2%** |
| binaries (4 KiB + two 64 KiB maps) | 5 | 40,286 | 53,638 | **-24.9%** |

Framing everything made the boot 27% bigger to help a case the boot does not have. One branch fixed it: with the two-form
wire the boot mix is 169.2 bytes/call, identical to base64 (0.0% change), while the binary mix keeps its 24.9% saving.

## Consequences

**Measured A/B** (`tests/browser/tmp-probe`, deleted after the run; 100 reads, one process, production-shaped serve loop,
median of a batch, same probe on both commits):

| payload | base64 wire | framed wire | gain |
| --- | ---: | ---: | ---: |
| 4 KiB | 289 us (13.5 MB/s) | 152 us (25.7 MB/s) | 1.9x |
| 64 KiB | 1,496 us (41.8 MB/s) | 296 us (211 MB/s) | 5.1x |
| 256 KiB | 6,345 us (39.4 MB/s) | 628 us (398 MB/s) | 10.1x |

And the same bench that produced the table in `docs/bench/process-scaling.md` now reports 64 KiB at 260 us (240 MB/s) and
256 KiB at 555 us (450 MB/s).

Codec CPU, measured in Node on identical values: at 256 KiB, encode is 100 us versus 932 us for base64-in-JSON (9x cheaper)
and decode is 1 us versus 497 us, because a framed decode returns a view of the shared buffer instead of materialising a
string and decoding it.

The small-call path pays nothing. A `stat` request is the same bytes it always was.

**Accepted trade-offs:**

- Two message forms instead of one. Sniffing the first byte is the whole cost, and the two cannot collide: a frame starts
  with `F`, and every JSON value a syscall carries starts with `{`.
- A corrupted magic byte no longer reports "not a frame". It is parsed as JSON, fails, and reports `EFRAMEJSON`. Still loud,
  but it names the wrong thing. Pinned by a test so the wording cannot drift silently.
- Framing is not free for small binaries: below ~128 bytes base64 is smaller, which is why framing is not applied to
  messages that carry no body at all and why call batching remains the answer for small-call latency (ADR-0020).

**Known gap, closed:** no test previously proved a binary payload survives a real process boundary.
`tests/browser/binary-payload.spec.ts` now writes 4 KiB from one process Worker, verifies it from a second, and checks the
kernel's own file size, so the bytes are witnessed three ways.

**How the contract is pinned.** `tests/browser/transport-conformance.spec.ts` runs a real client against a real kernel with
both ends recording every message that crosses, and asserts on the recorded bytes rather than on decoded values: a call with
no body starts with `{` and is byte-identical to plain JSON, a call with a body starts with `F` and stays under base64's
size, all 256 byte values survive a write and an echo, a text answer stays text, a kernel throw arrives as
`SyscallRejectedError`, and an 8 KiB answer refused by a 4 KiB region arrives as `ERESPTOOLARGE` instead of truncating or
hanging. The suite was mutation-checked: forcing the codec to frame bodyless messages makes it fail on the first record
(`{` becomes `F`), which is the regression that would otherwise cost boot size silently.

## Alternatives rejected

- **Base64 everywhere (status quo).** 33% more bytes and a decode that cost more CPU than the whole framed channel costs now.
- **Framing every message.** Measured at +27% on the boot mix; falsified by its own instrument before shipping.
- **Binary-only side channel outside the syscall message.** A second protocol to keep in sync, for no gain over one codec
  that already knows which messages need it.
