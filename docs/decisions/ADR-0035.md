# ADR-0035: An uncaught asynchronous exception ends the run with status 1, through one shared path

**Status:** Accepted, implemented 2026-11-14 (W-40).
**Depends on:** ADR-0013 (the scheduler and its virtual clock), ADR-0014 (declared refusals), ADR-0029 (a run is a process).
**Supersedes:** the "reporting on stderr and continuing" decision recorded in the `Scheduler` error callback, and ADR-0013
amendment 3's note that a throw inside a tick "escapes the microtask ... Recorded as a gap, not hidden".

## The problem

Four asynchronous routes each answered an uncaught exception differently, and one of them answered with success:

| route | before | Node v20.20.2 (measured) |
| --- | --- | --- |
| synchronous body throw | exit 1 | exit 1 |
| unhandled rejection | exit 1, `Uncaught …` on stderr | exit 1, reason printed |
| `setTimeout` callback throw | `Uncaught …` on stderr, **exit 0** | exit 1, later timers never run |
| `process.nextTick` callback throw | **`run()` rejected**: no result, no status | exit 1 |

The consequence of the `setTimeout` row is the severe one, and it is why this was W-40 rather than a nit: a fixture whose last
assertion is "the program exited zero" **passed on a crashed program**. The consequence of the `nextTick` row is different and
worse in kind: `run()` rejected, so a caller received no `ExecutionResult` at all. In the harness that rejection killed the
process; in a process Worker it surfaced as a transport-level `failed` with a bare message, which is indistinguishable from a
harness fault and carries no exit status, no scheduler evidence and no attribution.

## The decision

**One path, four records, and an exit status that is never 0.** `InProcessRuntime` owns a single reporter,
`reportAsyncFailure(source, error)`, and every route above calls it:

- `ProcessExit` keeps its own branch. It is the program *choosing* a status, so it sets the code and is neither printed as
  uncaught nor recorded as a failure. That is what keeps `process.exit(3)` at 3 and keeps a `SIGWINCH` handler's exit from
  looking like a crash.
- Anything else is: printed in Node's shape (`Uncaught <stack>`), recorded as an `AsyncFailure`
  (`source`, `phase`, `name`, `message`), and the run is ended with **status 1** by `requestExit(1)`, which aborts the
  scheduler so the callbacks queued behind the throwing one do not run. Node does the same thing for the same reason.
- `source` distinguishes `"timer"`, `"tick"`, `"callback"` (a throw the post-evaluation drain caught) and `"rejection"`.
  The four outcomes this runtime was already careful about - uncaught exception, unhandled rejection, explicit non-zero
  exit, declared refusal - stay distinguishable afterwards, as data, rather than being flattened into stderr prose.
- The record and the printed line are the same string, so a supervisor deciding from the record cannot disagree with a
  reader looking at the log. A test pins that equality.

**The tick queue reports instead of throwing.** `TickQueue` takes an optional `onError`. With one, a throwing callback is
reported and the queue *dies*: the callbacks behind it are dropped, `flushNow()` becomes a no-op and `pending` reports false.
Without one it re-raises exactly as before, which is the queue's standalone contract and its existing test. Dropping the rest
is not tidiness - keeping them would let a later flush run them out of order and settle an already-settled run twice
(requirement 7), and a `pending` that stayed true would make a waiter poll for a callback that can never run.

**`run()` never rejects for a program's asynchronous failure.** A settled `ExecutionResult` with status 1 and a record is
strictly more informative than a rejection, and it is the only shape the harness and the supervisor can classify.

## Where the process cannot be settled: `phase: "after-run"`

A program that keeps something open (a listening server, a live timer) has already handed back its result, so a later
callback throw cannot change its exit status. Killing it silently - which is what aborting the scheduler does now - would be
exactly the "unresolved" state this ADR is meant to remove. Those failures are therefore recorded on the **runtime**
(`InProcessRuntime.asyncFailures`), with `phase: "after-run"`, while the run's own records carry `phase: "run"`.

Deliberately **not** in this change: wiring that after-run record into the process lifecycle. A held-open process that throws
after its exit is announced now stops its pump and is attributable on the runtime, but the kernel is not told, because
settling a process twice is the transition W-39's `ProcessHost.#settle` guards, and changing that guard belongs to the
process-host workstream rather than to an exit-status fix. Registered as W-41 with this reasoning.

## What stays untouched

- Scheduler ordering, the virtual clock, `maxCallbacks` / `maxRealMs`, and the resident and per-request pumps: the reporter
  is a change to what happens *after* a callback throws, not to when callbacks run. All of ADR-0013's evidence is unchanged.
- W-22's guards, the 90% frontend gate, ADR-0009, the fixture corpus and the refusal contract: nothing here classifies a
  fixture or touches a threshold.

## Evidence

`tests/unit/runtime.async-failures.test.ts` (19 tests): the exit status and Node's shape for a timer throw, its record and
source, the timers behind it being dropped, `process.exitCode = 3` losing to the throw, the tick throw settling rather than
rejecting, the virtual clock not being left pending, both queues together (one failure, one line, one status, tick wins on
Node's ordering), a tick thrown inside a timer and a timer thrown inside a tick, a nested tick, a second tick queued behind
the throwing one (the duplicate-settlement shape), caught exceptions in both queues staying exit 0, an unhandled rejection
keeping its own source, an explicit exit staying 3, a declared refusal staying a refusal, a matrix proving `run()` never
rejects and never settles 0, and the tick queue's own two contracts.

Three mutations each redden named tests: removing `requestExit(1)` reddens 10; reporting the tick source as `"timer"` reddens
3; keeping the callbacks behind the throwing one reddens 2 (`reports one failure when a second tick was queued behind the
throwing one`, and the queue's own drop test).

`tests/unit/runtime.scheduler.test.ts`'s "keeps a synchronous throw ... without killing the harness" is re-pinned rather than
dropped: it asserted the drain continuing to exit 0, which is the defect. It now asserts Node's measured answer (nothing
printed after the throw, exit 1) and keeps the part that was always true and always mattered - the harness survives, because
the failure arrives as a result instead of an exception.

## Amendment 1: delivering the after-run record across the worker boundary (W-41)

**Status:** Accepted, implemented in W-41.

The decision above is unchanged: the runtime owns the failure record, and `reportAsyncFailure` remains the only
place a failure is recorded and printed. What W-40 left open was delivery. Its wording - the record is on the
runtime "so a supervisor can settle the process from it" - describes the intent but not a usable route, because the
supervisor and the runtime are in different threads: the process Worker holds the runtime, the kernel holds the
table, and nothing can read a getter across that boundary.

So the record is delivered, not re-derived:

- **The runtime owns the failure.** `InProcessRuntime` decides that a throw is a failure, prints it in Node's shape,
  and builds the `AsyncFailure` with `phase: "after-run"`. That logic does not exist anywhere else and is not
  duplicated by this amendment.
- **A callback delivers it.** `RunOptions.onAfterRunFailure` is called from inside `reportAsyncFailure`, in the
  after-run branch only, with a copy of that same record. It is a delivery mechanism with no opinion: it does not
  classify, format, print or decide anything, and it cannot fire for an in-run failure, which stays on the result
  as W-40 defined.
- **The process layer consumes it.** `process-worker` turns the notification into the `{ type: "failed" }` message
  the kernel already accepts from a live row, and `ProcessHost` performs the transition and retires the Worker.
  Settling from that message is the transition W-39's `#settle` guards, so the process is settled once.

`InProcessRuntime.asyncFailures` remains the intra-runtime view of late failures, used by tests that hold the
runtime directly. It is deliberately not the delivery route: a getter cannot cross a Worker boundary, and polling
one from the kernel is not possible at all.

**What this does not authorise:** a second reporter. Anything that decides a failure happened, prints it, or builds
a record must go through `reportAsyncFailure`; the callback is downstream of it and carries its output. A test pins
that the record and the notification are the same failure, so the two halves cannot drift apart.

**Amendment 1, clarification (2026-11-19): settlement is not process state.** A command that settles while holding a
port is settled, and its `SettledOutcome` records `alive: true` at that instant. A later after-run failure transitions
the process to `failed` and retires it, but it does not rewrite that record: settlement is first-wins, so a caller keeps
the outcome of the command it ran. `alive` therefore means "held open by an owned listening server when the body
settled", not "alive now". The process table is authoritative for present-tense lifecycle state. This clarifies the
accepted decision above and changes none of it.
