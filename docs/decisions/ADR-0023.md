# ADR-0023: A terminal programs can trust, and the facts it is allowed to report

**Status:** accepted, 2026-11-09
**Supersedes:** nothing. **Relates to:** ADR-0002 (API target, Node 20 LTS), ADR-0003 (shim family), ADR-0004 (deliberate gaps).

## Context

Every interactive program asks the same five questions before it decides how to behave: is there a terminal
(`process.stdout.isTTY`, `tty.isatty(1)`), how wide is it (`process.stdout.columns`), is input raw
(`process.stdin.isRaw`), what does typed text look like when it arrives, and how is a resize announced (`SIGWINCH`). Until
now this runtime answered none of them: `src/terminal/` did not exist, `process.stdin` was absent, and `process.on` returned the
shim without registering anything, so `process.on("SIGWINCH", …)` was a silent no-op. A TUI would paint at 80 columns forever
while the browser window said otherwise, and `readline` could not run at all.

The audit's fix order puts shell and PTY after the preview and kernel work (`docs/audit/response-nov-08.md`, item 5). Items 3
and 4 are done, so the PTY half lands here. The shell is Phase 6 work and is not in this ADR.

## Decision

**1. The terminal is a model of a pty reduced to what a browser can honour, and it is explicit about the parts it does not have.**

A pty offers two sides. The program side here is `stdin` (a readable with `isTTY: true`) plus the existing stdout/stderr sinks,
now carrying size. The UI side is `write(text)`, `end()`, `resize(columns, rows)` and `interrupt()`. There is **no line
discipline**: no echo, no erase processing, no `^C` byte interpretation, because a real terminal does those in the kernel and
`readline` does its own in userspace. Emulating them would make `readline` behave differently here than in Node, which is the
opposite of the goal.

**2. Every tty fact is derived from whether a terminal is attached, never defaulted.**

`tty.isatty(fd)` is true only for descriptors 0, 1 and 2 when a terminal exists, and `createTtyShim(null)` answers false for
all of them. `process.stdout.isTTY` is `undefined` (not `false`) with no terminal, which is what Node reports for a pipe, so
`if (process.stdout.isTTY)` behaves identically and code that compares against `false` still gets the truth.
`process.stdin` is `null` with no terminal: a pipeline that never delivers would leave a program waiting for input that cannot
arrive, and a program can report "no input" honestly instead. `new tty.WriteStream(7)` throws `ENOTTY` rather than returning a
stream that lies about a descriptor it does not own.

**3. Sizes are live, and a resize that changes nothing emits nothing.**

`process.stdout.columns` and `tty.WriteStream#getWindowSize()` read the terminal at call time; a snapshot taken at construction
would answer 80 forever after the first resize. `resize()` emits `SIGWINCH` only when the size actually changed, matching
`tty`: a terminal that announced every notification would make every full-screen TUI redraw for no reason.

**4. Input typed before anything is listening is buffered and flushed on attach.**

A keystroke typed while a prompt is still starting up is not lost; it is delivered as one chunk on the first `data` listener,
in arrival order. After `end()`, further `write()` calls are dropped rather than delivered to a program that has already seen
end-of-input.

**5. Signal listeners are real, short-lived, and cleaned up by the run that made them.**

`process.on("SIGWINCH" | "SIGINT", …)` registers with the terminal, and `off` removes exactly one listener (the behaviour a
listener that re-registers depends on). Other event names are accepted and never fired: registration cannot throw, because
chaining code is common, but nothing claims to deliver a signal the runtime cannot produce. The terminal outlives the program
(a UI keeps one across many runs), so `InProcessRuntime.run` calls `ProcessShim.dispose()` when the run ends. Without it a
finished program's listener would fire on the next resize and re-enter code whose scheduler had already drained.

## Amendment 1 (2026-11-09): the page can type into a program

The core above answers questions. This amendment is what makes a program reachable from the page, and it crosses a thread
boundary: the page cannot hold a `Terminal`, because the program that reads it runs in the Worker.

Three pieces, each with one rule:

- **The session owns the size.** `Session.columns`/`rows` start at 80x24 and change through `container.resizeSession`, which
  forwards to the running process and keeps the number for the next one. The size outlives the process, because a window does not
  shrink back when a program exits.
- **Keystrokes are addressed to the process actually running.** `container.write(sessionId, text)` finds the running process in
  that session and sends it there; with nothing running it does nothing. A stale pid would be worse than a no-op, since it could
  collide with a later process, so ended processes are never addressed. A size that did not change forwards nothing, matching the
  terminal's own rule.
- **The Worker owns the terminal objects.** `RunRequest` carries plain numbers; the Worker builds the Terminal, keeps it in a map
  keyed by `processId`, routes `input` and `resize` messages to it, and deletes the entry in a `finally` when the run settles.

Deliberately absent: line editing. `write` is a program's stdin, not a prompt, so there is no echo and no partial-command buffer.
A second, worse editor in front of the real one would be a bug you could see.

### What is still missing for an interactive shell

Raw keystrokes need the UI's raw mode (an xterm.js pane or an equivalent), because the current prompt is line-based: it collects
a whole command before anything runs. The runtime side is now complete and pinned; the pane is the remaining piece, alongside the
`SIGINT` default action and piped stdin listed under Limits.

### Amendment 2 (2026-11-10): what an interactive program needs from the loop, and what `process.exit` means

Building the pane (Amendment 3) turned up three runtime defects that made an interactive program impossible, none of which any
earlier test could have seen, because every program so far either finished or was expected to be killed.

**1. A waiting reader is a live handle.** `process.stdin.on("data")` is a ref'd handle in Node, so a program whose only job is to
answer a question stays running. Here the queue was empty and the process exited immediately, before the first question could be
answered. `TerminalInput` now reports `live()`, set by a data listener or `resume()` and cleared by `pause()`, `off()`, end of
input or `destroy()`, and the scheduler's `keepAlive` counts it alongside open watchers. One deliberate difference from Node:
removing the last data listener unrefs. Node keeps flowing with nobody listening, which would leave a program hanging forever.

**2. Waiting is not working.** The real-time guard exists to stop a spinning program, and it measured wall-clock time, so a
program waiting for a keystroke was killed five seconds after asking. The scheduler now accumulates `idleWaitMs` while polling
outstanding handles and excludes it from both real-time checks; `SchedulerEvidence` reports it separately so the exclusion is
visible rather than implied. `RunOptions.workCeilingMs` exposes the ceiling, because the exclusion is only observable with a
small one and a host may want a tighter bound.

**3. `process.exit` is immediate, and only the top-level body was guarded.** `execute()` caught `ProcessExit` during evaluation,
so an exit from a timer callback, a stdin handler or a signal listener escaped instead: the run reported `Uncaught ProcessExit`
with code 1, and in the browser the throw crossed into a worker or page handler that had no idea a program had ended. Two pieces
fix it: `Scheduler.abort()` with a new `aborted` stop reason (nothing queued before the exit may run afterwards), and listeners
wrapped at the point the runtime hands them out, so an exit from a stdin handler (`guardedStdin`) or a terminal signal listener
(`ProcessOptions.onExit`) becomes an exit request instead. Exit codes now come from the program: 7, 4 and 3 are asserted, not 1.

Two smaller findings from the same work, both in the UI: `#raw-pane`'s `display: flex` overrode the `hidden` attribute, so a
"hidden" pane still painted (an assertion of mine had been passing against that), and a stray Enter while a program owns the
keyboard could submit the hidden line prompt and start a second program on top of the first, which presented as a pane that
refused to close.

Every one of these is mutation-checked: removing the idle accounting fails the guard test, removing the stdin liveness fails the
waiting test, removing the signal guard fails the signal-exit test, and removing the container's `terminal` field fails the
end-to-end case.

### Limits this amendment does not remove

- A signal listener is still not a ref'd handle: `process.on("SIGWINCH")` alone does not keep a program alive. Node refs signal
  handlers. Stated here because the pane test has to attach a stdin listener to stay open.
- After an abort, the remaining continuation drains still run, so a `.then` queued before the exit can still observe output that
  Node would not have produced.
- Timers are virtual: an interval burns the virtual budget in milliseconds, which is why no interactive example uses one.

## Verification added by this amendment

`tests/unit/container.test.ts` gains eight cases: default size reaching the program, typing only into a running process, no
typing after exit, a resize carried to the running program while being remembered for the next, silence on an unchanged size, a
refused nonsense size, and session isolation. Mutation-checked by disabling the routing helper: exactly the two positive cases
fail.

`tests/browser/p1b.spec.ts` adds one end-to-end case: a program run from the real page reports `cols=80 rows=24`, `isTTY=true`,
`isatty=true` and a stream on stdin, which exercises page → Worker → runtime → shim. Mutation-checked by removing the `terminal`
field from the container's run request: the test fails.

## Verification

`tests/unit/terminal.test.ts` (19 tests) pins the terminal and both shims: defaults, ordering, early-input buffering,
end-once semantics, `SIGWINCH` on change only and not on an identical size, per-listener unsubscription, raw-mode tracking,
refused sizes, `isatty` for owned and unowned descriptors, live window size, `ENOTTY`, and listener removal.

`tests/unit/terminal-runtime.test.ts` (5 tests) proves the same claims through the real loader: `require("tty")` resolves as a
builtin, `process.stdout.isTTY`/`columns`/`rows` reflect the attached terminal, input written before the run is delivered,
each run sees the size current at its start, and a finished program's listener no longer fires.

That last test is mutation-checked: its listener **throws** rather than logs, because a logging listener would pass even while
still attached (a write into a sink whose run has finished is invisible). Removing `processShim.dispose()` fails exactly that
test and nothing else; the line was then restored byte-identical.

## Limits, stated rather than implied

- **No default `SIGINT` action.** A listener is delivered, but an unhandled `SIGINT` does not terminate the program with exit
  code 130 as Node does. That needs the kill path (the supervisor's termination machinery) and is separate work.
- **No piped stdin.** Only a terminal feeds `process.stdin`; there is no non-TTY readable, so `echo x | node p.js` has no
  equivalent yet.
- **No xterm.js wiring.** This is the runtime side. The browser terminal that calls `write`/`resize` and renders output is a
  UI step that follows, and the shell itself is Phase 6.
- **`setEncoding` accepts and ignores its argument.** Text is already decoded on the way in; decoding to something else would
  be a lie, so only text is supported.
- **A run that throws out of `run()`** (rather than having its error captured) can leave one signal registration attached,
  because the disposal call is at the end of the run body rather than in a `finally` around it.
