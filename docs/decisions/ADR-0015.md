# ADR-0015: stream subsystem contract

Status: **proposed**, written before implementation so the behaviour is decided before it is convenient.
Scope decided by the owner: `Readable`, `Writable`, `Duplex`, `Transform`, `PassThrough`, `pipeline`, with real lifecycle,
error and backpressure behaviour. Import-only stubs are explicitly forbidden.

## Why a contract first

`stream` is the largest single gap in the runtime: fixture 4 fails on the import alone, and fixtures 1, 5, 6 and 8 need it
transitively. A stub would make the import succeed and turn four honest failures into four mysterious ones, so the
contract fixes what each class must actually do.

## Lifecycle

### Readable

| State | Entered by | Events |
|---|---|---|
| readable | construction | — |
| flowing | `on("data")`, `pipe`, `resume` | `data` per chunk |
| ended | `push(null)` or source exhausted | `end`, then `close` |
| errored | source error, or `destroy(err)` | `error` once, then `close` |
| destroyed | `destroy()` | `close` |

Chunks are delivered in order and never after `end`. `read()` returns `null` when nothing is buffered, and the same chunk
is never emitted twice through both `read()` and `data`.

### Writable

| State | Entered by | Events |
|---|---|---|
| writable | construction | — |
| writing | `write(chunk)` | — |
| draining | buffer falls below highWaterMark | `drain` |
| finishing | `end()` | `finish` after the last write completes |
| errored | `_write` callback error, or `destroy(err)` | `error` once, then `close` |

`end()` after `end()` is a no-op rather than an error; `write()` after `end()` emits `error` with `write-after-end`,
because npm's own code relies on that being loud.

### Duplex, Transform, PassThrough

`Duplex` keeps independent read and write states: an error on the write side does not silently stop the read side, but
`destroy(err)` does destroy both. `Transform` is a Duplex whose `_transform(chunk, encoding, callback)` pushes downstream
and calls back; `_flush(callback)` runs once after the last chunk. `PassThrough` is a Transform that pushes its input
unchanged.

## Error semantics

1. `error` is emitted **at most once** per stream, and after it the stream is destroyed. A second error would double-report
   and, in a pipeline, would mask the first.
2. An exception thrown synchronously inside `_read`, `_write`, `_transform` or `_flush` is caught and routed to that
   stream's `error`, never to the run's global error handler: one bad stream must not abort the process.
3. A destination that has already errored un-pipes the source and destroys it, rather than writing into a dead stream.
4. `pipeline(...)` destroys every stream in the chain on the first error, and reports that first error exactly once. With a
   callback it calls `callback(err)`; without one it rejects. It never resolves after an error.
5. An `error` with no listener is not swallowed: it surfaces as an uncaught error through the runtime's `process`
   `uncaughtException` path, because a silently dropped stream error is worse than a loud one.

## Backpressure

- `Writable.write()` returns `false` when the buffered bytes reach the highWaterMark (16384 by default; 16 objects in
  object mode). The data is still accepted: `false` is advice, not rejection.
- `drain` is emitted when the buffer falls below the highWaterMark.
- `Readable.push()` returns `false` when the internal buffer reaches its highWaterMark; a well-behaved source stops
  producing until `_read` is called again.
- `pipe(dest)` pauses the source when `dest.write()` returns `false` and resumes on `drain`. This is the one behaviour that
  must be real rather than approximated, because a pipe that ignores backpressure turns a bounded buffer into unbounded
  memory.
- In object mode the watermark counts objects, not bytes.

## Encoding

`utf8` only for string input and output in this milestone, matching the fs and http shims. `Buffer` chunks pass through
untouched. `setEncoding("utf8")` is supported; any other encoding is refused with a typed error naming it, consistent with
the http shim.

## Regression test plan

Written before the code, so implementation cannot define its own passing bar.

| Area | Cases |
|---|---|
| Readable lifecycle | `Readable.from` array; string chunks; `push(null)` ends; `end` fires once; no chunks after `end` |
| Readable reading | `data` events in order; `read()` returns buffered chunk then `null`; async iteration collects everything |
| Writable lifecycle | single `write` then `end` emits `finish`; `end(chunk)` writes then finishes; double `end` is a no-op |
| Writable errors | `_write` callback error emits `error` once and destroys; `write` after `end` errors with `write-after-end`; synchronous throw in `_write` is routed, not thrown at the caller |
| Backpressure | `write` returns `false` at the watermark and `true` below; `drain` fires when it clears; `pipe` pauses a fast source and resumes on `drain` |
| Transform | upper-casing transform preserves chunk count and order; `_flush` runs once; thrown error in `_transform` reaches the pipeline |
| PassThrough | output equals input byte for byte, including multi-byte characters split across chunks |
| pipeline | collects output; propagates the first error and destroys the chain; callback form and promise form agree |
| Encoding | utf8 round trip; `setEncoding` works; an unsupported encoding is refused by name |
| Integration | a Readable piped into a Writable through `pipeline` produces data observable before the run's snapshot |

## Non-goals for this milestone

`ReadableStream`/WHATWG interop, `cork`/`uncork`, `_read` demand-driven scheduling beyond the watermark, object-mode
`readableObjectMode` on `Writable` beyond counting objects, and `stream/promises` module aliases. Each is recorded as a gap
rather than approximated.

## Open questions for the audit

1. Should `stream` be reachable as `node:stream` and `stream` both? (Proposed: yes, both, for the same reason `node:fs` is.)
2. Should `Readable.from` accept async iterables in this milestone, or arrays and sync iterables only?
3. Is `uncaughtException` the right destination for an unhandled stream error, or should the run fail the step?
