# ADR-0005: Network layer, phase one — ports, requests, and the preview route

**Status:** provisional. Written while the expert is unavailable, in the same spirit as ADR-0004:
each decision below is recorded so the month-long audit has a reviewable list rather than a pile of
comments in source. Nothing here is ratified, and none of it merges to `main` without the owner.

**Scope:** `src/shims/events.ts`, `src/shims/http.ts`, `src/network/port-registry.ts`,
`src/network/request-registry.ts`, `src/network/preview-gateway.ts`, `src/network/service-worker.ts`, `src/network/sw-bridge.ts`.
Tests: 72 across the four network/shim files at the time of writing, plus 6 end-to-end tests in
`tests/unit/runtime.http.test.ts` and 24 more added with the fetch handler and bridge, for 237 in the
suite overall. (An earlier draft of this ADR claimed "116 tests across five files"; that number was wrong
and is corrected here rather than quietly edited, because an audit should not have to distrust the
counts.)

## D-7. Events come first, and `emit("error")` throws

Almost every Node API is an emitter, and `http` cannot be built without one. Three semantics are
faithful rather than simplified, because simplifying any of them changes application behaviour
silently: an unhandled `error` event throws (Node's behaviour, and the reason a crashed server is
visible rather than mute); `once` removes its listener *before* invoking, so a re-emit cannot fire it
twice; and listeners added during an `emit` do not receive that emit.

Deliberately absent: `prependListener`, max-listener warnings, promise-based `events.once()`,
`captureRejections`.

**Audit question:** is omitting the max-listener warning acceptable, given that the warning is how Node
users discover a listener leak?

## D-8. Bodies are bytes, and `content-length` is computed, not trusted

Response bodies are always `Uint8Array`; strings are encoded at `write`/`end` with `utf8` only, and a
non-utf8 encoding is a `TypeError` rather than a silent mis-encode. `setEncoding` affects only what the
reader sees.

`content-length` is **always** overwritten with the real byte length. This deviates from Node, which
trusts the handler. The justification is that responses here are buffered whole, so a wrong hand-written
value can only truncate or stall a response; there is no streaming case that legitimately needs control.
The test that caught this was written expecting Node's behaviour and failed against my own comment
claiming otherwise, which is the version of this I would rather have on record.

**Audit question:** is overriding a handler's `content-length` acceptable, or should it be preserved and
a mismatch rejected loudly on `end()`?

## D-9. The port namespace is protocol plus port, and port 0 is refused

`http:3000` and `https:3000` are different bindings because a browser treats them as different origins;
a shared key would route to the wrong handler. A second bind throws `EADDRINUSE` with the offending key,
matching socket semantics that applications rely on to detect a busy port.

Port 0 is refused with an explanation instead of given an ephemeral number, because Node's real meaning
is "allocate and report through the `listening` event", and that reporting path does not exist yet.
Assigning a number now would leave a server believing it is on one port while the proxy looked for
another.

**Audit question:** what should `listen(0)` do — implement ephemeral allocation properly, or keep failing
until a fixture requires it?

## D-10. Binding is announced synchronously, on purpose

`Server.listen()` emits our own `bind` event synchronously, before returning, and `close()` emits
`unbind`. `listening` and `close` still fire on a later tick, as in Node, for applications that expect
that.

This exists because of a bug the tests caught: the gateway originally learned its routes from the
asynchronous `listening` event, so a request arriving between `listen()` returning and that event firing
was answered 404 for a server that was demonstrably running. Routing must be correct the instant
`listen()` returns, so it cannot depend on an async notification.

**Audit question:** is an extra synchronous event acceptable, or should routing read the port registry
directly and resolve `port → handler` by another means?

## D-11. Every request carries a deadline, enforced by the timer *and* the registry

Every preview request is registered with a deadline and raced against a timer. On expiry the request is
reaped, every waiting caller is rejected with `RequestTimeoutError`, and the browser receives a 504 that
names the port and the timeout. The timer alone would not settle the promise; the registry alone would
never look at the clock. Both are needed, and the tests cover the timer because that is the half that
fails silently.

This closes the hole both reference implementations share: a map from request id to resolver that is
only cleaned up on reply, so a dead worker leaves a promise pending forever and a hung preview is
indistinguishable from a slow one (discovery notes §5). `closeAll()` fails everything at teardown so no
caller can be left waiting.

**Audit question:** is 30s the right default for a cold rebuild, and should the timeout be configurable
per fixture rather than per gateway?

## D-12. The worker and the page talk over messages, not shared memory

A service worker has its own global scope and cannot reach the page's `PreviewGateway`, so every preview
request is a round trip: the worker posts the request, the page answers it, the worker builds the
`Response`. `src/network/sw-bridge.ts` implements both halves against a `send`/`reply` function rather
than a `MessagePort`, so a test can wire them together through a fake bus that delivers out of order.

Correlation uses the id that is actually on the wire (`openWithId`, not `open`). The first version of this
used the registry's private auto-id while sending its own, so every reply settled nothing and each request
timed out while the page was answering correctly. The tests caught it; it is recorded because it is the
kind of mistake that looks like a transport problem, not a bookkeeping one.

Bodies are copied through structured clone rather than transferred. Transfer lists would avoid the copy
but need care around buffer reuse, and this is already the slower path.

**Audit question:** should the bridge transfer bodies instead of copying them, and should it target the
specific client that made the request (the current shape allows any client to answer)?

## D-13. The fetch handler is a pure function, and the worker script is plumbing only

`createPreviewFetchHandler` takes a real `Request` and returns a real `Response`. It is not a `fetch`
listener, because a worker script cannot be unit tested: any line in it is a line that only fails in
production. The listener will be a few lines that decode, call this, and encode.

Two response rules are enforced here because violating them throws rather than degrades: `HEAD`, `204`,
`205` and `304` carry no body, and a handler's `content-length` is dropped so the platform computes the
real one.

**Audit question:** is a page-side responder the right long-term home, or should the runtime move into the
worker itself so the bridge disappears? That is an architectural question this ADR does not answer.

## What this ADR does NOT authorize

- No service worker. The gateway is written to be called by one, but nothing registers a `fetch`
  handler yet, so no request reaches it in a browser.
- No websockets, no chunked transfer encoding, no keep-alive, no TLS, no `upgrade` event. Each is named
  in the source where a reader would look for it.
- No `node:http` module resolution work: the shim is not yet wired into the CommonJS loader, so a
  script that does `require("http")` still cannot reach it. That wiring is the next piece.
- No merge. All of this sits on `integration/build-all`.

## Risk carried forward: P0-1

The preview route is `/preview/<port>/`, a path on the host origin, as ADR-0002 #5 decided. The
consequence, recorded in `docs/references/discovery-stackblitz-public.md`, is that user code runs
same-origin with the host application and can reach its cookies, token storage and DOM. This ADR does
not change that and does not pretend to fix it; it is listed here because the network layer is where the
decision surfaces.
