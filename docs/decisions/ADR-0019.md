# ADR-0019: Cross-origin isolation for the runtime itself

**Date:** 2026-11-08
**Status:** Accepted. Accepted by the owner on 2026-11-09 (P0-8); implementation waits on the runtime origin being purchasable (domain decision).
**Deciders:** Expert (reserved per the charter); drafted by the agent.

## Context

User code runs in a Worker created from the host application's origin. `src/browser/main.ts` constructs
`new Worker(new URL("./runtime.worker.ts", import.meta.url), { type: "module" })`, so the Worker's origin is the host
origin. Inside it, user code is executed with `new Function`, which means the realm it runs in can reach `fetch`,
`postMessage`, `indexedDB` and anything else the host origin can. The host page also holds the project store in
`localStorage`.

ADR-0017 requires previews to be origin-separated and rejects same-origin previews. It does not cover the runtime itself,
so the isolation gap stays open even after previews are fixed. The discovery pass recorded the same asymmetry as risk
P0-1: StackBlitz serves user code from `*.webcontainer.io`, which is why every one of their browser-configuration
documents concerns third-party cookies, storage partitioning and blocked service workers.

Two further facts constrain the design:

- `SharedArrayBuffer` (required by ADR-0018's synchronous syscall channel) is only available to a
  cross-origin-isolated context, so the host page must send COOP/COEP as well.
- Cross-origin isolation changes what the host page can embed: COEP `require-corp` rejects cross-origin subresources
  without CORP headers.

The current deployment state matters: the preview system needs a wildcard domain, and the Vercel account has no custom
domain at all, so the isolation design must state what it requires from DNS rather than assume it exists.

## Decision

Move the whole runtime to its own origin.

- **A runtime origin** serves a small `boot.html` and the runtime bundle: `runtime.<domain>` in production,
  `runtime.localhost:<port>` in development. It holds no cookies, no host storage and no credentials.
- **A boot handshake.** The host embeds the runtime in an iframe and creates a `MessageChannel`. One port is posted to the
  frame with a one-time nonce and an exact `event.origin` check on the receiving side. Afterwards the frame accepts
  commands only through that port; nothing else crosses the boundary.
- **Cross-origin isolation headers on both sides.** The host sends `Cross-Origin-Opener-Policy: same-origin` and
  `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`). The runtime origin sends
  `Cross-Origin-Resource-Policy: cross-origin` and a matching COEP. The runtime frame asserts
  `crossOriginIsolated === true` at boot and refuses to start otherwise.
- **Kernel and processes live inside the frame** (ADR-0018): the kernel Worker owns the VFS, process table and port
  registry; each spawn creates a process Worker.
- **Process Workers are hardened before user code runs.** Capture what the shims need in closures, then remove or replace
  the rest of the surface: `fetch` becomes a shim over the virtual network; `XMLHttpRequest`, `WebSocket`,
  `importScripts`, `indexedDB`, `caches` and `postMessage` are removed from the global.
- **This is defence in depth, not a sandbox.** It reduces what a hostile program can reach; it is not a security boundary
  against a browser exploit, and the documentation must say so in those words.

## Consequences

- ADR-0017 is kept and extended: preview origins become siblings of the runtime origin under the same preview base.
- Deployment now needs **three** origin families: host (`app.<domain>`), runtime (`runtime.<domain>`) and previews
  (`<previewId>.<previewBase>`). That is a wildcard DNS requirement and a wildcard TLS requirement, plus a Pro-plan
  wildcard decision on Vercel — the concrete blocker recorded from the deployment audit.
- COEP `require-corp` on the host page affects every third-party asset the editor loads. Any future CDN font, analytics
  script or embedded video must send CORP or be proxied. This is a permanent product constraint, not a one-off fix.
- Local development on `*.localhost` needs the dev server to serve both host and runtime origins with the isolation
  headers, and browsers differ: Chromium and Firefox support `*.localhost`; Safari needs verification before it can be
  claimed.
- `localStorage` project persistence (P1b) is host-origin state. Once the VFS lives on the runtime origin, persistence must
  move with it (OPFS on the runtime origin, Phase 8) or be explicitly proxied through the port. This ADR forces that
  decision earlier than the current roadmap expects.
- The browser test suite gains a hostile-fixture lane: attempts to reach host storage, cookies, `fetch`, `postMessage` and
  `indexedDB` from user code, each asserted to fail.

## Open questions — for the decider

1. **COEP mode.** `require-corp` (broad compatibility, breaks uncorporated third-party embeds) or `credentialless`
   (fewer embed problems, Chromium-first)? This decides what the editor may load for the rest of the project's life.
2. **Where persistence lives.** OPFS on the runtime origin (natural, but the host editor then cannot read files directly)
   or the host origin with all file traffic over the port (simpler for the editor, more traffic)? Phase 8 depends on this
   answer, and so does the P1b project store.
3. **Kernel placement** — the same question as ADR-0018 Q1; answered once, applied to both.
4. **Nonce lifetime.** Single-use per boot, or rotated per command batch? Single-use is simpler; rotation bounds the
   damage if a port leaks.
5. **Domain.** Which zone hosts `app.`, `runtime.` and `*.preview.`? Nothing can be deployed or even end-to-end tested
   until this exists.
