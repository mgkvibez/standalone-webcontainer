# ADR-0030: A response leaves the process as it is written

**Status:** accepted, 2026-11-12
**Relates to:** ADR-0028 (the transport seam), ADR-0029 (the product runs processes), ADR-0013 (virtual time), ADR-0017 (preview origin), register item W-4.

## Context

Every HTTP body the preview served was buffered. `ServerResponse` collected `write()` output into one `Uint8Array`, the gateway handed
that whole body back across the Worker boundary, and the page received it as a single reply. Two limits made the shape visible: a 16 MiB
cap on request and response bodies, and a 30 second ceiling on a request, after which the caller got a 504 with nothing to show.

That is adequate for a document and wrong for a dev server, which is the thing this project exists to preview. Three consequences:

1. **Nothing can be watched live.** A page that writes its first `<h1>` immediately and takes ten seconds to render the rest arrives in
   one piece at the end, so the preview looks frozen and then appears. A live-reload page never appears at all: its response never ends,
   so the buffered model answers 504 thirty seconds in.
2. **The 16 MiB cap is a real ceiling**, because the whole body has to exist at once before any of it can move.
3. **The seam had no vocabulary for a partial answer.** ADR-0028 defined a request and a captured response, which is a complete
   exchange by construction. Streaming is not a bigger body; it is a different shape.

## Decision

### A response sends its headers on the first byte, and each `write()` leaves as its own chunk

`Server.dispatch(wire, sink)` takes an optional sink. When a sink is installed and the handler writes before it ends, the shim emits
`start` (status, status message, headers) with the first byte and one `chunk` per `write()`, then the ordinary reply carrying
`streamed: true` and an empty body. A handler that writes nothing before it ends behaves exactly as before: one buffered reply with a
computed `content-length`. The buffered path is not a fallback that happens to work; it is the same code with no sink installed, and it
is pinned by its own test.

The sink is installed **before the handler runs**, because a handler's first `write()` can happen inside the same call that dispatched it,
and a sink attached afterwards would see a response whose opening bytes nobody recorded.

### The events are routed per request, and a late chunk is dropped

`start` and `chunk` carry the request id at every hop: process Worker → broker → runtime worker → preview shell → service worker. The
broker keeps one sink per outstanding request and drops events for a request it has already answered, so a chunk written after a response
settled cannot land in the next response that happens to reuse the id. That is the same class of defect as ADR-0029's second bug (output
routed by process id while the page addresses runs), and it gets the same treatment: the id is the address, and it is carried, never
inferred.

At the far end the service worker answers with a `Response` whose body is a `ReadableStream`: `start` resolves `respondWith` so the
headers go out immediately, each `chunk` enqueues, and the final reply closes the stream.

### What this does NOT claim

- **No backpressure.** A handler that writes 200 MiB as fast as it can is not slowed by a client reading slowly; the chunks queue. Real
  `write()` returning `false` needs a credit protocol between the service worker and the process Worker, and that is a separate decision
  with its own ADR. Stated here so nobody reads "streaming" as "flow control".
- **No keep-alive or connection reuse.** Each fetch is still one request over one port pair.
- **No WebSocket.** W-4's second half. Vite's HMR needs it, so a dev server can be previewed but not a *live* one.

### The tests assert causality, not elapsed time

The obvious streaming test writes a chunk, sleeps 800ms, writes another, and asserts the first arrived first. That test measures nothing
in this runtime: ADR-0013 gives the program a virtual clock, and a program whose only remaining work is a pending timer has its time
advanced to that timer immediately. Measured directly: both writes landed in the same millisecond, and a streamed response was
indistinguishable from a buffered one. The plumbing was correct at the time and the instrument said otherwise, which is the same lesson
as the payload benchmark that measured its own scheduling.

So the second half of the response is released by a **second request**. The first chunk must appear before anything releases the rest,
and a buffered implementation has no first chunk to give, so it deadlocks on its own deadline instead of passing slowly. Removing the
sink from the gateway makes both tests fail; that is the only reason to trust them.

## Consequences

- A dev server's document and its streamed responses now reach the page as they are written, which is what makes a previewed HMR-less dev
  server usable and is the prerequisite for HMR itself.
- The 16 MiB response cap no longer bounds a streamed body; a buffered one still has it.
- A handler that writes after the response settled is silently ignored rather than reported. Node raises `ERR_STREAM_WRITE_AFTER_END`;
  matching that is worth doing, and it belongs with the response-state work rather than here.
- `streamed: true` is the flag that stops a consumer reading an empty body as "the handler wrote nothing", the same silent-empty-output
  shape ADR-0029 called the worst bug shape there is.
