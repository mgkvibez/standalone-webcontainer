# ADR-0033: A previewed page opens a socket by asking the shell, and the container's own client does the protocol

**Status:** Accepted, implemented 2026-11-12 (W-25's client half).
**Depends on:** ADR-0032 (an upgrade crosses into a process Worker), ADR-0031 (a websocket is a connection inside the container), ADR-0030 (a
preview response streams).

## The problem

ADR-0031 established that a service worker never sees a handshake, so the preview proxy cannot route one. ADR-0032 carried a connection from
the kernel into the process that owns the port. Between those two there was nobody: a previewed page is a document in another realm with no
`WebSocket` it can use and no channel except `postMessage` to its parent shell.

The temptation is to make the page speak RFC 6455 over the page protocol. That is a second framing implementation, in the one place where a
mistake is invisible (the bytes look fine, the handshake just never completes), and the container already has a tested client.

## Decision

**Relay the page's intent, not its framing.** Four parts:

1. **The page's `WebSocket` is a facade.** `public/preview-ws-client.js` is injected into every HTML document the preview serves. It owns the
   four ready states, `open`/`message`/`error`/`close`, `send`, `close`, `binaryType` and `protocol`, and it keeps an id table. It never frames
   anything: `open`, `send` and `close` cross to the parent as three page messages, and four replies come back (`opened`, `data`, `closed`,
   `failed`).

2. **The shell decides what a page may open, in one testable place.** `src/browser/socket-relay.ts` resolves the page's URL and refuses the rest
   with a sentence: the host must be the shell's own, and the port comes from the URL when it says one and from the preview prefix when it does
   not. Both shapes are real — a URL built from the page's location carries `/preview/5173/`, and Vite's client carries `:5173` from its own
   config — so neither the prefix nor the app origin can be the only source. `wss:` is accepted and travelled as `ws:` inside the already
   encrypted origin, which is a documented difference from a browser rather than a hidden one.

3. **The container's client does the handshake.** The runtime Worker receives the open, asks the kernel (`kernel.upgrade`), and constructs the
   real client against the program. One framing implementation, one place to fix, already covered by ADR-0031's tests.

4. **Injection happens as the document streams.** `src/browser/html-inject.ts` inserts the tag at the first `</head>` while the bytes pass
   through, holding only a tag-length tail so a `</head>` split across chunks still matches, and appending when a document has no head at all.
   The alternative — buffer the response, splice a string, send it — would undo the streaming ADR-0030 exists for.

## The three defects this produced

Each one was found by a real chain and none would have been found by reading:

- **The container's client sent a subprotocol and never recorded the server's choice.** `this.protocol` was a constant `""`. A previewed page
  asking for `echo` got `""` back: the connection worked and only the negotiation was missing, which is why it survived every earlier lane. The
  client now sets `protocol` from the handshake, and **fails the connection** when the server names one that was not offered, because a peer that
  picks its own protocol is a peer the caller did not agree to talk to.
- **A Blob-delivered frame became zero bytes.** The client is a browser `WebSocket` and honours `binaryType`, whose default is `"blob"`. My relay
  read `body.buffer` from it, got `undefined`, and produced an empty `Uint8Array` — a binary message delivered as silence. The runtime now sets
  `binaryType = "arraybuffer"` on every page socket, `socketBytes` accepts a view or a bare buffer, and the page client refuses a body it cannot
  turn into bytes instead of delivering zero.
- **`EventTarget.call(this)` is an illegal constructor.** The facade's first version subclassed `EventTarget` the old ES5 way and threw on
  `new WebSocket(...)` in a modern browser, which surfaced as a page-level `error` and no connection. It owns a plain listener table now, with the
  `on<type>` property running before the listeners added afterwards, which is the order a browser uses.

## What is deliberately not here

- **Vite's HMR loop end to end.** This proves a page can open a socket and exchange frames with a program in a process Worker. It does not prove
  a real dev server's HMR client reconnecting and applying an update, which needs a dev server running inside the container and is now its own
  register row (W-26).
- **Backpressure.** Page messages queue on the port, as in ADR-0032.
- **`permessage-deflate`** stays refused; `wss:` is accepted only as described above.

## Evidence

- `tests/unit/preview-socket-relay.test.ts` (17 tests): the three URL shapes, `wss:` accepted, another host refused by name, `http:` refused as
  the wrong protocol, and every malformed page message refused with a sentence instead of a throw (the caller is a `message` listener in a frame,
  where a throw is the hardest failure to see).
- `tests/unit/html-inject.test.ts` (8 tests): the tag lands immediately before `</head>`, a `</head>` split across chunks still matches, content
  before the head is emitted while the document is still arriving, a document with no head gets the tag appended, bytes after the injection pass
  through untouched, and the marker makes double injection detectable.
- `tests/browser/preview-websocket.spec.ts`: a real iframe in its own realm runs the client the preview serves, a real program in a
  `process-worker.ts` computes its own accept key and echoes, and text, binary, the subprotocol and a clean close all cross. A foreign host is
  refused by name and the page is told as a `1006` close rather than a hang.
- `tests/unit/websocket.test.ts`, four new tests over the subprotocol rules: the chosen one is recorded, an unchosen one fails the connection,
  a chosen one that was not offered fails it, and one of several offered is accepted.
- **Mutation checks:** removing the `binaryType` line makes the browser spec's binary assertion fail with zero bytes; removing the relay's
  `socket-failed` path turns the foreign-host case into a Playwright timeout instead of a `1006`.
