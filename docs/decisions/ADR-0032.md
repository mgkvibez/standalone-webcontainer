# ADR-0032: An upgrade crosses a thread boundary as a relayed connection, not a forwarded request

**Status:** Accepted, implemented 2026-11-12 (W-24's first hop).
**Depends on:** ADR-0031 (a websocket is a connection inside the container), ADR-0029 (a program that owns a port is a process).
**Supersedes:** ADR-0031's note that "the process lane is not switched yet".

## The problem

ADR-0031 landed a connection inside ONE runtime: `http.Server.dispatchUpgrade` hands a listener the parsed request and a duplex `Socket`, and
`src/shims/websocket.ts` speaks RFC 6455 above it. That covers two programs in the same runtime. It does not cover the product's actual case,
because ADR-0029 made every program its own Worker: a program that calls `listen(3200)` owns a real `Server` object whose `upgrade` listener is
a closure in THAT Worker, while a preview request lands in the kernel. A request already crosses that boundary (`transport-request`); a
connection cannot, because a request has one answer and an end, and a connection has neither.

## Decision

**Carry the connection, do not re-implement it on the far side.** Four parts:

1. **A wire protocol of five messages.** `socket-open` carries the id, port, path and headers; the process answers `socket-accepted` or
   `socket-refused`; then `socket-data`, `socket-end` and `socket-close` travel in both directions under the same id. Ids are their own space,
   separate from request ids, so one cannot settle the other.

2. **`relaySocket(end, post, id)` — one function, both sides.** It watches the end it is given (`data`/`end`/`close`) and posts those events,
   and every inbound message is written back INTO that same end. Symmetry is the point: the kernel and the process Worker run identical code,
   which is the only way to be sure they agree about ordering. A second implementation on the far side would be a second opinion.

3. **The socket is created before the open is sent.** On the far side a handler writes its `101` synchronously inside `dispatchUpgrade`, so bytes
   exist before any acceptance can arrive. The kernel therefore links a pair first (`linkSockets`) and relays the LOCAL end while the caller keeps
   the remote one, so those bytes land in a socket that already exists.

4. **The connector may answer asynchronously.** `WebSocketConnector` now returns a result or a promise of one, because across a thread boundary
   the listener's answer IS a message and there is no way to know it synchronously. Both paths converge on one `#adopt`, so acceptance, listener
   wiring and the handshake deadline behave identically whether the answer took a microtask or a message.

## The defect this produced, and why it is the interesting part

The first implementation used a peerless socket plus a transport interface, and it **dropped the handler's handshake**. The bytes a handler
writes during `dispatchUpgrade` arrive at the relay's end while nothing has attached a `data` listener, so they sit in the socket's queue —
correctly, that is Node's buffering — and a transport attached afterwards only captured FUTURE writes. The symptom would have been a connection
that opened and then said nothing, which is the silent-empty shape this project keeps refusing.

The fix is structural rather than a flush: relay the end's EVENTS, and let attaching the `data` listener drain the queue the way
`Socket.on("data")` already does. A queue that is read on attach cannot be forgotten on one side and remembered on the other.

## What is deliberately not here

- **The page half.** A preview page still cannot open a websocket: it cannot use the host `WebSocket` (a service worker never sees a handshake,
  ADR-0031) and the container is in another realm. That needs an injected page-side client speaking over the existing page protocol, and it is
  now its own register row (W-25). This ADR claims only: a client on the KERNEL side reaches a server inside a process Worker.
- **Backpressure.** `socket-data` queues on the message port; nothing tells a fast writer to slow down.
- **`permessage-deflate`, `wss:`** remain refused by name, as in ADR-0031.

## Evidence

- `tests/unit/process-transport.test.ts`, six new tests over real `MessageChannel`s: a port nobody serves refuses in the gateway's words; a
  process's refusal is forwarded verbatim; bytes cross both ways INCLUDING a `101` posted before the acceptance; a half-close passes in both
  directions; an unanswered open refuses at its deadline instead of waiting; and dropping a process fails its open connection immediately
  (`close`, `destroyed`) rather than leaving it idle.
- `tests/browser/process-websocket.spec.ts`, end to end with no fixture: a program inside a `process-worker.ts` does its own handshake
  (`crypto.createHash("sha1")` over the client's key), parses masked client frames by hand and echoes them; the client is the container's own
  `WebSocket` on the KERNEL side, wired through the async connector. It also asserts the two refusals told apart, and that killing the serving
  process closes the connection and leaves the port unserved (503).
- **Mutation checks, each of which fails the browser spec:** removing the relay in the process Worker (the handshake never arrives, so the client
  errors), and removing the destroy-on-detach loop (a connection to a killed process stays open). The queue flush is covered by the unit test's
  "bytes before the acceptance" case, which fails if the acceptance is posted before the data.
