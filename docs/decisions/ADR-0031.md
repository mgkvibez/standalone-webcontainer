# ADR-0031: WebSockets are a connection inside the container, not a request through the proxy

**Status:** Accepted, implemented 2026-11-12 (W-4's second half).
**Supersedes:** the "websockets are a later, separate problem" note in ADR-0030 and the `upgrade`-is-absent boundary note in `src/shims/http.ts`.

## The constraint that decides everything

A browser's WebSocket handshake **is not a fetch event**, so a service worker never sees it. The preview proxy that routes
`/preview/<port>/` is a service worker (`src/browser/preview-sw.ts`), and that is not a gap in its implementation: interception is defined
over requests, and a protocol switch is not one. There is consequently no way to hand a page's `new WebSocket(url)` to a server that lives
inside the container, whatever the URL.

The second constraint is that the server is not on the network at all. Port 3000 belongs to a program in this runtime, so `ws://localhost:3000`
from the host resolves to nothing: no listener, no DNS, no route. Both constraints point the same way.

## Decision

**A websocket is a duplex the runtime owns, opened from inside the container.** Three parts, in dependency order:

1. **`src/shims/socket.ts` — a `Socket` pair.** There are no sockets in a browser, but an upgrade does not need one: it needs two endpoints
   carrying bytes both ways until one closes. The shape is Node's `net.Socket` reduced to what an upgrade handler touches (`write`, `end`,
   `destroy`, `data`/`end`/`close`/`error`, `pause`/`resume`, `setTimeout`), because that is what `ws` and Vite's HMR server touch.

2. **`http.Server` grows `upgrade`.** `dispatchUpgrade(wire)` hands the listener the parsed request and one end of a pair, and the listener
   writes the `101` itself. Framing stays out of the transport: a handler may speak any protocol, which is Node's division and the reason a
   websocket library can sit on top rather than inside. A port with no `upgrade` listener **destroys** the connection and says so by name,
   rather than leaving a client to wait for a handshake nobody will write.

3. **`src/shims/websocket.ts` — the client, RFC 6455 above the socket.** Handshake with the accept-key **verified**, masked client frames,
   continuation frames, ping/pong, close codes. Installed as the program's `WebSocket` global, bound to the gateway, so a client written for a
   browser works unchanged inside the container.

## The one place the model differs, and why it must be stated

On a real socket the client writes `GET … Upgrade: websocket` and the server parses it. Here **no request bytes go on the socket**: the request
travels out of band as the parsed request `dispatchUpgrade` is handed, so the handler already has `request.headers`. This is not a shortcut, it
is what the architecture allows, and it has a sharp edge worth recording: writing the request a second time delivers those bytes to the handler
as *payload*, where a frame parser reads `G` (0x47) as opcode 7 and the handshake never completes. That exact bug was written and found while
building this; the code carries the note at the call site.

## What is deliberately not here

- **`wss:`** refuses by name. TLS is terminated by the gateway; a program that asked for TLS and silently got plaintext would believe it was
  encrypted.
- **`permessage-deflate` is not negotiated.** Asking for it is refused rather than answered with an uncompressed stream that claims otherwise.
- **No backpressure signal.** `send` returns once the bytes are on the socket; `bufferedAmount` reports what the socket still holds instead of a
  number invented here.
- **The process lane was not switched in this ADR.** It is now: ADR-0032 carries the connection across the Worker boundary, so a server inside a
  process Worker can be upgraded. What is still missing is the page half (a preview page has no client, W-25), so the honest statement remains: a
  client INSIDE the runtime reaches a server in a process; a preview page cannot open one yet.

## Evidence

- `tests/unit/websocket.test.ts` (11 tests): handshake against a real upgrade listener with the accept key computed independently; refusals for
  "nothing listening" and "no upgrade listener"; text round trip with the client's frame asserted **masked on the wire**; a fragmented message
  assembled rather than delivered in pieces; a clean close with its code; a 101 bearing a wrong accept key refused; and the 7/16/64-bit length
  forms and the size cap.
- `tests/unit/runtime.http.test.ts` gains a test where nothing is called from the test: user code listens, computes its own accept key with
  `crypto`, parses the client's masked frame by hand, and the client is the container's own `WebSocket` global.
- **Mutation checks, each of which fails a test:** sending client frames unmasked; removing the accept-key comparison; ignoring close frames;
  removing the queue drain that fires when a `data` listener is attached.

## Consequence worth naming

A `Socket` has no address, no fd and no TLS, and is only obtainable from an upgrade. Code that reaches for `net.connect` still cannot be served,
and this ADR does not move that boundary: it makes the one thing an upgraded connection needs available, and says what it is not.
