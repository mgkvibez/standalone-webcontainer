# ADR-0009 — Fixture step interpretation

**Date:** 2026-11-04
**Status:** Proposed — implemented in `src/harness/command.ts` and `src/harness/execute.ts`; awaiting the end-of-project audit
**Deciders:** Implementer, under the owner's instruction to build to completion and record provisional decisions for a single month-long audit (relayed Oct 26 and Nov 3)

## Context

A fixture definition stores the command a user would type (`npm install`, `npm run dev -- --port 3000`,
`node scripts/check.js`). The engine has no shell: there is no `sh`, no `PATH`, and no process table. Something has to
translate those strings into actions, and every translation is a place where a fixture can silently stop testing what
it says it tests.

The pressure is legitimate: fixtures 1, 7, 8, 18 and 20 use `npm run <script>`, and two use bare binaries (`vite`,
`next`). Implementing a shell to serve them would mean quoting, expansions, pipes and redirection, each with its own
subtle failures, in service of fixtures that were written as commands rather than as shell scripts.

## Decision

**Commands are parsed into a closed set of plans, and anything outside the set is refused by name.**

1. **No shell.** `|`, `&&`, `;`, `>`, backticks and `$(...)` make the command invalid. The parser does not honour the
   left-hand side and drop the rest, because scoring part of a command produces a result that looks like a result.
2. **Unknown `npm install` flags are an error, not noise.** `--omit=dev` and `--production` change the tree; a flag we
   do not model would let a fixture claim a production install while installing dev dependencies.
3. **`npm install <spec>` is refused.** npm would add the package to `package.json` and resolve it fresh. We would be
   installing a tree that does not correspond to the definition's project, so the fixture must declare the dependency.
4. **Script arguments are forwarded only after a bare `--`**, matching npm. `npm run build --watch` passes `--watch` to
   npm, not to the script, and pretending otherwise hands scripts arguments npm would have consumed.
5. **Unimplemented capabilities are `harness-fault`, never `unsupported`.** `StepTermination` gained a fifth value for
   this. `unsupported` means the runtime refused on purpose (a native addon); `harness-fault` means we have not built
   the feature. Conflating them would report our gaps as the runtime's design decisions and inflate the
   `UNSUPPORTED_BY_DESIGN` bucket, which fixtures may legitimately expect. The runner maps `harness-fault` to
   `HARNESS_BUG` and ranks it above `TIMEOUT`, because a budget exceeded by a step we could not run is not evidence.
6. **A project's own failures are exit codes, not exceptions.** A missing `package.json`, a refused dependency spec, or
   `npm ci` without a lockfile produce exit code 1 with stderr, as npm does, so exit-code and stderr assertions remain
   exercisable. Only a runtime that cannot load a program at all is an `error`, which the runner reports as
   `RUNTIME_INCOMPATIBILITY`.
7. **`npm ci` requires a lockfile.** To make that checkable, `InstallReport` now reports `usedLockfile`, rather than
   the executor inferring it from whether anything was fetched.

## Consequences

Easier: every executable fixture goes through one reviewable translation, and the set of supported commands is
enumerable. A command we cannot run fails loudly as our bug. Assertions on exit codes and stderr work because failures
are values.

Harder: fixtures cannot use shell idioms (`&&`, pipes, redirects). If the corpus needs them, the definition must either
be rewritten as one command or this ADR must grow a shell.

Known deviations from npm, all deliberate and all visible to a fixture author:

- `npm ci` does not delete `node_modules` first, so it will not remove packages that are no longer in the lockfile.
- `npm install <spec>` and `npm run-script` are refused or unimplemented rather than approximated.
- `npm run <script>` and `node_modules/.bin` execution are not implemented at all yet; both report `harness-fault`.
  The npm script runner and bin resolution are the next slice.

## Open Questions

1. **Does the corpus need a shell?** If any fixture must pipe or chain, that is a product decision about how faithful
   the engine must be, not an implementation detail.
2. **Should `npm ci`'s deletion semantics be implemented?** Without it, ci in a dirty tree can leave stale packages that
   a real `npm ci` would have removed, which changes what a fixture proves.
3. **Is exit code 1 the right mapping for every installer refusal?** `UNSUPPORTED_SPEC`, `MISSING_PACKAGE_JSON` and a
   refused native package all currently exit 1. npm distinguishes some of these; fixtures that assert specific codes
   would care.
4. **`harness-fault` outranks `TIMEOUT` in verdict precedence.** The reasoning is in D-5; the audit should check it
   against a case where the harness fault occurred after a genuine hang.

## Approval

Not yet reviewed. This ADR records implementation choices made under the standing instruction to build to completion
and submit the whole project for one expert audit. Nothing here changes the gate, the thresholds, or a fixture's
declared expectations.
