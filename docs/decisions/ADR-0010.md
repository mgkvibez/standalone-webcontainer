# ADR-0010 — npm scripts and `bin` resolution

**Date:** 2026-11-04
**Status:** Proposed — implemented in `src/harness/scripts.ts`, `src/harness/execute.ts` and the CommonJS loader; awaiting the end-of-project audit
**Deciders:** Implementer, under the owner's standing instruction to build to completion for one expert audit

## Context

Seven of the twenty fixtures run a package.json script or a bare command name: five use `npm run <script>`, two call
`vite` or `next` directly. ADR-0009 shipped the interpreter without either, and reported them as `harness-fault`, which
is honest but blocks the corpus.

Three facts shape this:

- **There is no PATH.** `node_modules/.bin` is a directory of links npm generates so a command name exists on PATH.
  We have no PATH and no links, so a name has to be resolved by reading the installed tree.
- **A bin is a script with a shebang.** Every executable npm installs starts with `#!`, and the loader compiled module
  source with `new Function`, which rejects it. Before any of this could work, the loader had to do what Node does.
- **A script body is a command line.** `"build": "vite build && tsc -p ."` is not one command, and there is no shell
  (ADR-0009 D-1).

## Decision

**The loader strips a UTF-8 BOM and a leading shebang, and the interpreter runs scripts through the same closed set of
plans it already uses for steps.**

1. **Shebang and BOM are removed before compiling.** The shebang line is replaced, not deleted, so nothing below it
   shifts. This is Node parity, not a convenience: without it, no installed tool can start.
2. **A script body is parsed as a command, not executed as a string.** `npm run <script>` looks the script up, parses
   its command with the shared interpreter, and dispatches: `node` → the loader, `exec` → bin resolution, nested
   `run-script` → recursion, `invalid` → `harness-fault` naming both the script and its command. A script containing
   `&&` reports that it *needs a shell*; running its first half would score a command nobody wrote.
3. **Arguments after `--` are appended to the script's command**, matching npm: `npm run dev -- --port 3000` runs
   `vite --port 3000`.
4. **A script that runs `npm install` is a harness fault.** The install and run budgets are different (§4.5), and
   folding an install inside a run step would falsify both.
5. **Bins are resolved by scanning `node_modules` for a `bin` field**, scoped packages included, in sorted order.
   Scanning is required, not optional: `tsc` lives inside `typescript`, so a lookup that assumed bin name equals package
   name would miss the most common case in the ecosystem.
6. **An unreadable package manifest does not abort resolution.** A broken transitive dependency is normal, and letting
   one hide every working command would make a project unrunnable for no useful reason. It contributes no bins and
   scanning continues.
7. **Project faults stay exit codes; harness gaps stay harness faults.** A missing or malformed package.json, a script
   that does not exist, and a command no package provides all exit 1 with npm-shaped stderr, because fixtures assert on
   those. Only "we cannot do this at all" is a harness fault.
8. **Recursion is capped at five levels**, so a script that runs itself reports that, rather than looping until the run
   budget expires.

## Known deviations from npm

Stated here so a fixture author is not surprised, and so the audit can judge each one.

- **No `pre`/`post` lifecycle scripts.** npm runs `predev`, `dev`, then `postdev`. We run only the named script. A
  project whose build depends on a `prebuild` hook will not build here, and will report a plain failure.
- **No `PATH`, and no npm-injected environment.** npm sets `npm_package_version`, `npm_lifecycle_event`, `PATH` with
  `.bin` prepended, and more. Scripts that read those see nothing.
- **Only the project's own `node_modules` is searched** (plus scoped packages). Bins hoisted from nested installs into
  the nearest `.bin` are not found; the result is "command not found", not a wrong file.
- **"command not found" is our wording**, not the shell's `sh: 1: vite: not found`.
- **ESM-only bins cannot run.** `vite` and `next` ship ES modules; the loader is CommonJS only (ADR-0004). Those bins
  resolve, start, and fail with a load error, which the runner reports as `RUNTIME_INCOMPATIBILITY`. That is a true
  finding about the engine, not a defect in this ADR, but it means the fixtures that call them cannot pass yet.

## Consequences

Easier: `npm run <script>` works for CommonJS toolchains end to end, verified by a test that installs a package
declaring a `bin`, runs the project's script, and asserts on the program's output. Bin resolution is deterministic, so
two runs of one tree cannot disagree.

Harder: ESM support is now the gate's real blocker rather than an abstraction. Two fixtures depend on it directly, and
most modern scaffolding produces ESM.

## Open Questions

1. **Should `pre`/`post` scripts run?** npm does. Implementing them is small, but it changes what a fixture's run step
   means, so it belongs in a decision rather than a patch.
2. **Is ESM support the next slice, or is it a lane change?** The loader is CommonJS by design (ADR-0004). Supporting
   `.mjs` and `"type": "module"` affects how the worker lane loads code too, so it looks like an architectural question
   rather than a feature.
3. **Should npm-injected environment variables be provided?** A script reading `npm_lifecycle_event` gets nothing today.
   Cheap to add, and inventing values that differ from npm's would be worse than none.
4. **Nested `.bin` lookup?** Deferred; see deviations. If a fixture needs it, the answer is to search nested
   `node_modules` nearest-first, which is a bounded change to `resolveBin`.
