# ADR-0006: npm — resolution, tarballs, and what is refused

**Status:** provisional, same basis as ADR-0004 and ADR-0005: written while the expert is unavailable, each
decision recorded with an audit question rather than left to be rediscovered in the source.

**Scope:** `src/npm/semver-range.ts`, `src/npm/tarball.ts`, `src/npm/install.ts`. 52 tests across three files
(289 in the suite overall).

## D-14. semver is implemented here, and verified against npm's own

The install flow needs range resolution. `semver` is the obvious dependency and is deliberately **not** one: it
would ship to the browser inside the runtime bundle, and a package manager needs a subset of its behaviour.

Instead `semver` is a **dev** dependency, used only to check our implementation differentially: 1,320 range
comparisons and 900 version pairs, plus named tests for each of four rules. This is the same method that caught
three real deviations in the `path` shim, and it earned its keep again:

- the prerelease exclusion was applied per comparator, so a wildcard (`*` lowers to zero comparators) admitted
  every prerelease. This is exactly the rule that stops `npm install` silently picking an alpha.
- `^0` (major only) spans the whole 0.x line, `<1.0.0`. I had reasoned my way to `<0.1.0`; npm's implementation
  settled it.

**Audit question:** is a dev-only `semver` acceptable as a verification oracle, or should the matrix be
recorded as fixtures so CI does not depend on the package at all?

## D-15. Hoisting is shallow, and says so

A package installs into the top-level `node_modules` unless that name is taken there by a different version, in
which case it nests under the dependent that asked for it. npm additionally *lifts* nested packages upward when
no conflict exists, producing a smaller tree.

Correctness does not depend on lifting, because Node resolves by walking up from the dependent. The cost is
duplicated bytes and deeper paths, not wrong behaviour. This is the one place the implementation is knowingly
less capable than npm, so it is stated here rather than discovered later.

**Audit question:** is shallow hoisting acceptable for the fixture corpus, or does any planned fixture depend on
a hoisted layout (for example a package that requires a peer dependency installed only at the root)?

## D-16. Integrity is fatal; absence is a warning

Every tarball's sha512 is compared to its `dist.integrity` before a single byte reaches the VFS, and a mismatch
throws. The test asserts the package directory is still empty afterwards, because "wrote half of it, then
noticed" is worse than not starting.

A missing integrity field warns instead of failing: very old packages predate it, and refusing them would make
the installer useless on legacy trees. An unsupported algorithm also warns. Neither case is silent.

**Audit question:** should a missing `dist.integrity` be fatal under a strict mode, given that the whole point
of verifying is defeated by a package that simply omits the field?

## D-17. Tarballs are treated as hostile input

Path traversal and absolute paths are **rejected**, not sanitised: the VFS normalises paths, so a sanitised
escape could still land somewhere unexpected. Symlinks, hard links, devices and fifos are refused rather than
skipped, because a package needing them would install and then fail at runtime with a missing file. GNU
base-256 size fields error rather than being misread, since a wrong size shifts every subsequent offset.

Decompression is capped on the output as it streams. The gzip header may claim anything, and 8 MB of zeros
compresses to a few kB; that exact case is a test.

**Audit question:** is refusing symlinks the right call for the fixture corpus, or do any target packages
(`.bin` shims, monorepo workspace links) require them? npm creates its own bins as symlinks or shims, which is
a related problem we have not solved yet.

## D-18. No lockfile, no CLI, and no wiring into the runtime yet

`npm install` here is a library call: `installDependencies(manifest, { registry, vfs, root })`. There is no
`package-lock.json` written, no `npm` command a user can type, and nothing in the runtime invokes it. Those are
three separate pieces of work, and none of them is authorised by this ADR.

A lockfile is the one with a real decision inside it: writing one that npm's own tooling would honour means
reproducing its exact shape.

**Audit question:** should the lockfile be npm-compatible (so the same project installs identically outside the
browser) or our own format? This affects fixture determinism directly.

## What this ADR does NOT authorize

- No CLI, no runtime wiring, no lockfile.
- No `optionalDependencies` or `peerDependencies` handling. A package whose peer is missing installs anyway and
  fails at require time; npm warns. Fixtures may need this; nothing here guesses at it.
- No `.bin` shims, no lifecycle scripts (`postinstall` and friends). Refusing to run lifecycle scripts is a
  security stance, and a deliberate one: it is also why some packages will not work.
- No merge. Everything remains on `integration/build-all`.
