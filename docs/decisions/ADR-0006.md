# ADR-0006: npm — resolution, lockfiles, and what is refused

**Status:** D-14 to D-17 and D-19 are provisional, written while the expert is unavailable, each with an audit
question. **D-18 (lockfile format) and the D-15 rationale were decided by the owner on 2026-11-03** and are no
longer open.

**Scope:** `src/npm/semver-range.ts`, `src/npm/tarball.ts`, `src/npm/install.ts`, `src/npm/lockfile.ts`.
80 tests across five files (317 in the suite overall).

## D-14. semver is implemented here, and verified against npm's own

The install flow needs range resolution. `semver` is the obvious dependency and is deliberately **not** one: it
would ship to the browser inside the runtime bundle, and a package manager needs a subset of its behaviour.

Instead `semver` is a **dev** dependency, used only to check our implementation differentially: 1,320 range
comparisons and 900 version pairs, plus named tests for each of four rules. This is the same method that caught
three real deviations in the `path` shim, and it earned its keep again:

- the prerelease exclusion was applied per comparator, so a wildcard (`*` lowers to zero comparators) admitted
  every prerelease. This is exactly the rule that stops `npm install` silently picking an alpha.
- `^0` (major only) spans the whole 0.x line, `<1.0.0`. I had reasoned my way to `<0.1.0`; npm's implementation
  settled it.

One export exists purely for the lockfile: `isRangeExpression` distinguishes a range from a dist-tag, because a
locked version can be checked against `^1.0.0` offline but not against `latest`.

**Audit question:** is a dev-only `semver` acceptable as a verification oracle, or should the matrix be recorded
as fixtures so CI does not depend on the package at all?

## D-15. Hoisting is shallow — decided, with the rationale the owner gave

A package installs into the top-level `node_modules` unless that name is taken there by a different version, in
which case it nests under the dependent that asked for it. npm additionally *lifts* nested packages upward when
no conflict exists, producing a smaller tree.

**This is a deliberate tradeoff, not a shortcut (owner decision, 2026-11-03):** shallow nesting guarantees
isolation and prevents phantom-dependency bugs. A package that requires something it never declared fails here,
because the undeclared dependency is not sitting at the root by accident. npm's lifting produces smaller trees
at the cost of exactly that class of bug, and in a browser VFS the saving is bytes we never had to spend anyway:
the tree lives in memory, not on a user's disk being billed per gigabyte.

Correctness does not depend on lifting, because Node resolves by walking up from the dependent.

**Audit question:** is there any planned fixture that depends on a *hoisted* layout, for example a package that
requires a peer installed only at the root? That is the one shape where this decision is visible.

## D-16. Integrity is fatal; absence is a warning

Every tarball's sha512 is compared to its `dist.integrity` before a single byte reaches the VFS, and a mismatch
throws. The test asserts the package directory is still empty afterwards, because "wrote half of it, then
noticed" is worse than not starting.

A missing integrity field warns instead of failing: very old packages predate it, and refusing them would make
the installer useless on legacy trees. An unsupported algorithm also warns. Neither case is silent. When a
package publishes no integrity, the installer **computes** one for the lockfile, so the next install can verify
what this one could not.

**Audit question:** should a missing `dist.integrity` be fatal under a strict mode, given that the whole point of
verifying is defeated by a package that simply omits the field?

## D-17. Tarballs are treated as hostile input

Path traversal and absolute paths are **rejected**, not sanitised: the VFS normalises paths, so a sanitised
escape could still land somewhere unexpected. Symlinks, hard links, devices and fifos are refused rather than
skipped, because a package needing them would install and then fail at runtime with a missing file. GNU
base-256 size fields error rather than being misread, since a wrong size shifts every subsequent offset.

Decompression is capped on the output as it streams. The gzip header may claim anything, and 8 MB of zeros
compresses to a few kB; that exact case is a test.

**Audit question:** is refusing symlinks right for the fixture corpus, or do any target packages (`.bin` shims,
monorepo workspace links) require them? npm creates its own bins as symlinks or shims, which is a related
problem we have not solved.

## D-18. npm-compatible `package-lock.json`, v3, written as a documented subset — DECIDED

**Decision (owner, 2026-11-03):** use npm's own format, version 3 with the `packages` dictionary. A custom
format was considered and rejected.

**Why:** the value of a webcontainer is environment parity. A user must be able to run `npm install` locally and
get the same dependency tree the browser produces. A private format breaks that promise at the first handoff and
isolates us from standard tooling (Dependabot, Renovate, `npm ci`, every supply-chain scanner) for no gain.

**What we write.** Only the fields this runtime reads back: `version`, `resolved`, `integrity`, `dependencies`,
and `optional`, plus `name`/`version`/`dependencies`/`devDependencies` on the root entry. Nothing else.

**What we read.** Everything else in a real npm lockfile is ignored rather than rejected: `license`, `engines`,
`bin`, `dev`, `peerDependencies`, `funding`, `hasInstallScript`. Rejecting unknown fields would make the reader
useless on the exact files we claim compatibility with. A test parses a trimmed real npm lockfile to keep that
honest.

**Consequence worth stating plainly:** a lockfile written here and then used by `npm ci` pins versions
correctly, but npm may rewrite it to add the fields it normally records. That is a difference in bookkeeping, not
in resolution. Equally, because we do not write `dev`, a dev/production split cannot be represented: everything
installed is recorded the same way. `includeDev` decides what is *installed*, not how it is *flagged*.

**Reading semantics that matter:**

- A locked version is used directly when the manifest's range is a range expression it satisfies. No packument
  fetch, no resolution: only tarballs are fetched. That is asserted by a registry double that throws if asked to
  resolve.
- If the manifest says a dist-tag (`latest`) the locked version is trusted, because a tag's meaning lives on the
  registry and the lockfile is the only local record of what it meant then. Re-resolving would silently unpin it.
- If a parseable range is no longer satisfied by the pin, that entry is re-resolved and a warning says which pin
  was abandoned and why.
- **An entry with no `dependencies` means a package with none.** That is npm's meaning. An earlier version
  treated absence as "unknown" and fetched the packument for the edge list, which fired for every leaf package
  and defeated the entire point of a lockfile. Caught by the offline-install test.
- Nested placement is recorded by path (`node_modules/two/node_modules/shared`), so a reinstall reproduces the
  duplicate rather than re-deciding where it goes.

**Audit question:** our entries omit `dev`, so a lockfile round-trip through `npm ci` locally will reclassify
everything as production. Should we write `dev: true` for packages reachable only through `devDependencies`,
which requires tracking reachability rather than just placement?

## D-19. Platform-specific optional dependencies are skipped, by declaration

The resolver reads npm's `os` and `cpu` fields. A package that enumerates real operating systems is, by that
declaration, not portable: `fsevents` is darwin-only, and esbuild's platform packages each name one OS and one
architecture because each contains a native binary. **No browser appears in those lists and none ever will**, so
a non-empty positive list without an entry we can honour means "cannot run here".

Details that are easy to get wrong:

- Negations are read in npm's sense. `["!win32"]` is a list of *exclusions* and is portable; treating it as a
  positive requirement would wrongly refuse the package.
- The skip applies to **optional** edges, where a mismatch is expected and is a warning. A *required* dependency
  that declares an incompatible platform throws `PLATFORM_UNSUPPORTED` naming the platform, because installing
  it would produce a package that cannot run and a require-time mystery.
- The skip happens before the tarball is fetched, so `@esbuild/darwin-x64` (about 10 MB) is never downloaded.
- Only optional edges are *discovered* from the registry. With a lockfile the tree is fixed, so re-walking
  optional edges would install packages the lockfile deliberately omits.
- **The filter also runs on locked entries, and reads optionality from the entry.** This was a real bug found
  only by parsing this repository's own `package-lock.json`, written by npm itself: it contains every platform
  variant of esbuild, each marked `optional: true` with `os`/`cpu`. The first version of the filter ran during
  registry resolution only, so a lockfile produced by a local install would have pulled darwin and linux binaries
  into the browser. Optionality comes from `entry.optional`, not from the edge that reached it, because npm
  records it there.

**Audit question:** is `"browser"` the right sentinel to accept in `os`/`cpu`? It is not a value npm defines, so a
package could only ever match it deliberately. The alternative is a deny-list of known OS names, which fails open
for any new or misspelled platform string.

## D-20. Still no CLI and no wiring into the runtime

`npm install` remains a library call: `installDependencies(manifest, { registry, vfs, root, lockfile })`. There
is no `npm` command a user can type, and nothing in the runtime invokes the installer or reads the lockfile at
boot. Those are separate pieces of work and none is authorised by this ADR.

## What this ADR does NOT authorize

- No CLI, no runtime wiring, no automatic lockfile loading at boot.
- No `peerDependencies` handling. A package whose peer is missing installs anyway and fails at require time; npm
  warns. Fixtures may need this; nothing here guesses at it.
- No `.bin` shims, no lifecycle scripts (`postinstall` and friends). Refusing to run lifecycle scripts is a
  deliberate security stance, and it is also why some packages will not work.
- No `dev` reachability tracking (see D-18's audit question).
- No merge. Everything remains on `integration/build-all`.
