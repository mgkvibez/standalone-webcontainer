# ADR-0014 — Refusal Termination and the `UNSUPPORTED_BY_DESIGN` Bucket

**Date:** 2026-11-04
**Status:** Approved by the owner on 2026-11-04, with two final binding conditions (§2 D-10, D-11). Implementation in
progress on `integration/build-all`.
**Deciders:** Owner (decision of 2026-11-04, nine binding refinements) and implementer (design). Expert audit at the
single end-of-project review.
**Supersedes nothing.** Amends nothing in the charter. ADR-0013 is untouched and unrelated (liveness, not classification).

## 1. Context

`StepTermination` already contains `"unsupported"` and `decideVerdict` already maps it to `UNSUPPORTED_BY_DESIGN`, but
nothing emits it. The bucket the gate treats as legitimate outcomes is unreachable. Fixture 15, whose only expected
outcome is `UNSUPPORTED_BY_DESIGN`, therefore cannot score its own expectation.

Two structural facts force a design rather than a patch:

1. `runFixture` breaks on any non-`ok` step and leaves the remaining steps unrecorded, and it gates the whole assertion
   phase on `allStepsRan`. A refusal would silently discard the assertions that describe it.
2. A refusal today surfaces only as exit 1 plus stderr text. Read that way it is an ordinary failure: the assertions
   pass, the verdict is `PASS`, and the surprise-PASS rule rewrites it to `INVALID_BASELINE`.

The owner's decision: refusal is a step-level outcome, assertions must not be blindly skipped, and the classification
must be atomic.

## 2. Decision

**D-1. A refusal is a typed, step-level outcome.** `"unsupported"` becomes live. It is emitted only by the runtime
refusing a capability on purpose, never by the harness mishandling a step; our own gaps remain `"harness-fault"`.

**D-2. The refusing step keeps its evidence.** A refusal terminates the dependent path but the step still carries a
`StepRecord`: exit code, stdout, stderr. Assertions on that step execute normally against it.

**D-3. Sequential dependency, stated rather than inferred.** A terminating step skips every later step, each with an
explicit reason naming the step and the refusal code. No `dependsOn` authoring surface is introduced (owner decision 2).

**D-4. Assertions on skipped steps are `not-evaluated`, never passed and never failed.** They stay visible in the report
and in evidence. A skipped step has no world to assert against, and inventing a failure would misclassify the run as
`RUNTIME_INCOMPATIBILITY` (owner decision 3).

**D-5. Classification is atomic.** `UNSUPPORTED_BY_DESIGN` is returned only when one predicate holds in full: the
refusal is well formed, the fixture declared it, and every assertion on a step that ran passed. Any single failed
condition yields `RUNTIME_INCOMPATIBILITY` with a reason naming that condition. There is no partial credit and no
fallthrough (owner decision 5).

**D-6. Refusal evidence is carried, never reconstructed.** The `Refusal` object travels by reference from the runtime to
the report to disk. No component parses stderr to rebuild it, reformats `message`, rewrites `subject`, or normalises
`code`. What the runtime captured is what lands on disk (owner decision 6).

**D-7. Evidence lands in `steps.json` and `refusals.json`; `steps.json` is authoritative.** `refusals.json` is a
convenience index for a human or a future tool. Any disagreement is resolved in favour of `steps.json` (owner decision 4).

**D-8. Additive migration.** `AssertionResult.passed` is retained and derived, not replaced. New consumers read `state`.
Every production scoring and reporting path is audited so a `not-evaluated` assertion can never be counted as a genuine
failure. Evidence written under this ADR is schema v2, and v2 **requires** state-aware consumers: `passed: false` alone
is ambiguous between "failed" and "not-evaluated", which is why the legacy boolean is documented as insufficient rather
than merely deprecated (owner condition 1).

**D-10. Captured evidence is immutable at runtime.** A `Refusal` is deep-frozen via `createRefusal` before it leaves
the point of capture. No consumer may copy-then-edit it, rebuild it, or attach annotations to it; anything extra belongs
in a sibling field of the evidence record, never inside the refusal (owner condition 2).

**D-11. One capture, two files.** `steps.json` and `refusals.json` are rendered from the *same* captured `Refusal`
instance in a single write pass, so the two files cannot disagree by construction. `steps.json` remains authoritative
(D-7) for consumers that must pick one (owner condition 2).

**D-9. Fixture 15 is out of scope.** Its prerequisite — that `npm install sharp` is refused by ADR-0009 D-3 — is resolved
separately. ADR-0009 is not weakened, the package parser is not relaxed, and fixture 15's expectations are not altered to
make it pass (owner decision 8).

## 3. Type definitions

### 3.1 Refusal (new module `src/runtime/refusal.ts`)

```ts
/** The closed set of capabilities this runtime refuses on purpose. A new entry is a deliberate design act. */
export type RefusalCode = "native-addon";

/**
 * Evidence of a refusal the runtime made on purpose, captured where it happened.
 * Fields are readonly and carried by reference: D-6 forbids any consumer reconstructing or editing them.
 */
export interface Refusal {
  readonly code: RefusalCode;
  readonly capability: string; // "native addon"
  readonly message: string;    // the diagnostic the fixture asserts on, verbatim
  readonly subject: string;    // what was refused, e.g. "/app/node_modules/sharp/build/Release/sharp.node"
}

/** The only way a Refusal is constructed. Freezes before returning (D-10), so no consumer can edit captured evidence. */
export function createRefusal(input: Refusal): Refusal {
  return Object.freeze({ ...input });
}

export class ProcessRefusal extends Error {
  readonly refusal: Refusal; // already frozen by createRefusal
}
```

`readonly` is a compile-time promise only. A consumer that casts, or plain JavaScript, can still write to a `readonly`
field, and evidence that changes between the report and the disk record is not evidence. So the object is frozen at
construction, before it is shared with anything (owner condition 1, D-10).

`ProcessRefusal` replaces the current plain `Error` for the native-addon case. The message text is unchanged from
`429a019` so nothing that currently asserts on it shifts.

### 3.2 Runtime result (additive)

```ts
export interface ExecutionResult {
  // stdout, stderr, exitCode, timedOut: unchanged
  /** Present only when an unhandled refusal ended the program. A program that caught one has none. */
  readonly refusal?: Refusal;
}
```

The discriminator is *unhandled*: a program that catches the refusal and continues produces no `refusal`, stays an
ordinary run, and can legitimately `PASS`. The existing test for that behaviour is unchanged.

### 3.3 Step execution (additive)

```ts
export interface StepExecution {
  readonly termination: StepTermination; // "ok" | "timeout" | "unsupported" | "harness-fault" | "error"
  readonly detail: string;
  readonly record: StepRecord | null;    // present for a refusal: D-2
  readonly refusal?: Refusal;            // required iff termination === "unsupported"
}
```

`StepTermination` itself is **unchanged**. No new member is added; the dormant `"unsupported"` is activated.

### 3.4 Step run (additive, evidence-facing)

```ts
export type StepState = "ran" | "skipped";

export interface StepRun {
  readonly index: number;
  readonly kind: FixtureStep["kind"];
  readonly command: string;
  readonly state: StepState;                       // new
  readonly skipReason?: string;                    // required iff state === "skipped"
  readonly termination: StepTermination | "not-run"; // "not-run" iff state === "skipped"
  readonly detail: string;
  readonly elapsedMs: number;
  readonly record: StepRecord | null;
  readonly refusal?: Refusal;                      // present iff the step was refused
}
```

A skipped step reports `"not-run"` rather than a fabricated termination, so no reader can mistake it for an execution
outcome. `report.steps.length` now always equals `definition.steps.length`.

### 3.5 Assertion result (additive, backward compatible)

```ts
export type AssertionState = "passed" | "failed" | "not-evaluated";

export interface AssertionResult {
  readonly index: number;
  readonly kind: AssertionKind;
  readonly state: AssertionState;   // new, authoritative
  readonly passed: boolean;         // retained, derived: state === "passed"
  readonly stepAvailable: boolean;  // new: did the step this asserts on run?
  readonly detail: string;          // for not-evaluated: names the skipped step and why
}
```

`passed` is now defined as exactly `state === "passed"`. It is **not** a synonym for "failed": `passed: false` means
"did not pass", which covers both `failed` and `not-evaluated`. That asymmetry is deliberate and is the reason the one
production consumer moves to `state` (see §7).

### 3.6 Atomic verification (D-5)

```ts
export type RefusalVerification =
  | { readonly verified: true; readonly refusal: Refusal }
  | {
      readonly verified: false;
      readonly cause: "malformed" | "undeclared" | "assertions-failed";
      readonly detail: string;
    };

/** Total function: every observed refusal resolves to exactly one of the two arms, in one pass. */
export function verifyRefusal(input: {
  readonly steps: readonly StepRun[];
  readonly assertions: readonly AssertionResult[];
  readonly expected: readonly Classification[];
}): RefusalVerification | null; // null when no refusal occurred
```

`verifyRefusal` is pure and is the *only* producer of a `verified: true` value. `decideVerdict` consumes it and returns
`UNSUPPORTED_BY_DESIGN` solely from that arm.

Implementation added one condition that the design had not stated: a refusal whose object is **not frozen** is treated as
malformed. The reasoning is D-10's, applied strictly — evidence that can still be mutated is not evidence — and the check
is on the object, not on the caller's good faith, because an unfrozen refusal can only have been built outside
`createRefusal`. A test that fabricated a plain refusal object caught this: it was being verified happily while remaining
editable.

## 4. State transitions

### 4.1 Per step

```
pending ──execute──┬─ ok            ─→ next step pending
                   ├─ unsupported   ─→ refusal recorded; all later steps → skipped(refused at N: <code>)
                   ├─ error         ─→ record kept;    all later steps → skipped(step N failed)
                   ├─ harness-fault ─→ record kept;    all later steps → skipped(step N could not be run)
                   └─ timeout       ─→ no record;      all later steps → skipped(step N exceeded its budget)
```

No transition is silent: every later step exists in the report with a `state` and a `skipReason`.

### 4.2 Assertion phase

Replaces the `allStepsRan` gate with availability, per assertion:

```
assertion.step → ran   → evaluate against that step's StepRecord → passed | failed
assertion.step → skipped → not-evaluated (detail names the step and the skip reason)
```

The refusal step is `ran`, so refusal-specific assertions execute normally (owner refinement 3).

### 4.3 Verdict precedence

Unchanged order, with refusal handling inserted where `"unsupported"` already sits:

1. `harness-fault` → `HARNESS_BUG`
2. `timeout` → `TIMEOUT`
3. refusal observed → `verifyRefusal`
   - `verified: true` → `UNSUPPORTED_BY_DESIGN`
   - `verified: false` → `RUNTIME_INCOMPATIBILITY`, reason names the cause
4. `error` → `RUNTIME_INCOMPATIBILITY`
5. failed assertion → `RUNTIME_INCOMPATIBILITY`
6. otherwise → `PASS`
7. `PASS` not in `expected` → `INVALID_BASELINE` (unchanged)

## 5. Verdict truth table

| # | Refusal observed | Well formed | Declared in `expected` | Assertions on ran steps | Other | Classification |
|---|---|---|---|---|---|---|
| 1 | any | any | any | any | any `harness-fault` | `HARNESS_BUG` |
| 2 | any | any | any | any | any `timeout` | `TIMEOUT` |
| 3 | yes | **no** | any | any | — | `RUNTIME_INCOMPATIBILITY` (malformed; owner 1) |
| 4 | yes | yes | **no** | any | — | `RUNTIME_INCOMPATIBILITY` (undeclared) |
| 5 | yes | yes | yes | **any failed** | — | `RUNTIME_INCOMPATIBILITY` (assertion detail) |
| 6 | yes | yes | yes | all passed | — | `UNSUPPORTED_BY_DESIGN` |
| 7 | no | — | — | — | any `error` | `RUNTIME_INCOMPATIBILITY` |
| 8 | no | — | — | any failed | — | `RUNTIME_INCOMPATIBILITY` |
| 9 | no | — | — | all passed | — | `PASS` (then row 10 may apply) |
| 10 | no | — | `PASS` absent | — | — | `INVALID_BASELINE` |

Rows 3, 4 and 5 are the atomicity guarantee: a malformed refusal is tested **before** well-formedness can rescue it, and
an undeclared refusal is rejected before assertions are consulted. Row 6 is the only path to `UNSUPPORTED_BY_DESIGN`.

Two consequences worth stating because they are easy to get wrong:

- **Expected refusal, none occurred.** Never `UNSUPPORTED_BY_DESIGN`. A pass becomes `INVALID_BASELINE` (row 10); a
  failure is reported as itself (row 7 or 8). The bucket cannot be earned by absence.
- **`not-evaluated` assertions do not block row 6.** They are on skipped steps, which by definition have no evidence to
  assert against. They are counted in the reason string so the report cannot imply more was verified than was.

## 6. Evidence and report-schema migration

### 6.1 Files

| File | Change | Compatibility |
|---|---|---|
| `steps.json` | adds `state`, `skipReason`, `termination: "not-run"`, and `refusal` on the refusing step | additive; existing fields unchanged |
| `assertions.json` | adds `state`, `stepAvailable`; retains `passed` | additive; `passed` still present so old readers work |
| `refusals.json` | **new**, written only when a refusal occurred: `{ code, capability, message, subject, stepIndex, exitCode }`, verbatim from the carried object | new file; absence is meaningful and must not be read as "no refusal attempt" |
| `verdict.txt` | adds `refusal:` and `skipped steps:` lines | additive text |
| `report.json` (if present) | unchanged | — |

`refusals.json` is rendered from the same captured, frozen object that appears in `steps.json` (D-7, D-11). Both are
written from one in-memory value in one pass, so they cannot disagree; a consumer that finds a disagreement anyway must
prefer `steps.json` and treat the divergence as a harness bug.

### 6.2 Schema version

No evidence file carries a schema version today. `steps.json` and `assertions.json` are **bare arrays**, and wrapping them
to carry a version key would break every existing consumer, which the owner's condition 1 forbids. So the version lives
**beside** them: `schema.json` holds `{"schemaVersion": 2, "fixture": "<slug>"}`, `verdict.txt` carries an
`evidence schema: 2` line, and `refusals.json` — added after this ADR was drafted and therefore not listed in the table
above — carries its own `schemaVersion` for the same reason.

Absence of `schema.json` means version 1. This is a recorded deviation from the wording of this ADR as first drafted,
made deliberately: backward compatibility for report consumers outranks the tidier shape.

### 6.3 Amendment: schema v3, per-step HTTP observation

Found on fixture-13, the first fixture whose assertions name the same URL twice. Assertions are evaluated after every step
has run, and http assertions were answered by a fetch taken at that moment, so the assertion attached to the step that
*starts* a dev server read the page as it was after a later step had edited it. Both of fixture-13's assertions were
therefore answered with the same body: the fixture could not pass, and its failure said nothing about the runtime.

- `steps.json` records gain an optional `http` object, mapping each target URL an assertion names to the
  `{ status, body }` observed **at the end of that step**. Targets no assertion names are never fetched.
- `assertions.json` reads that observation when it exists and says so in `detail` ("as observed at the end of step N"),
  falling back to a live fetch for assertions that name no step. Live fetching is still correct for the final-state
  question, which is what most assertions ask.
- A probe that fails at capture time is left absent rather than failing the step: the step succeeded, and the failure
  belongs to the assertion, which reports it through its own NETWORK fault path.
- Schema version becomes **3**. The change is additive in shape, but `steps.json` is the authoritative file and a
  consumer reading it can now see a field it never saw, which is exactly what the version number exists to announce.
  Absence of `http` on a record means the step asserted on no URL, not that the capture failed silently.

## 8. Fixture 15 prerequisite — resolved separately (owner decision 8)

Fixture 15's step 0 is `npm install sharp`. ADR-0009 D-3 refuses ad-hoc package specs that are not declared in
`package.json`, so that step returns `harness-fault` and the run never reaches the refusal. This ADR does **not** address
it, and explicitly does not:

- weaken or amend ADR-0009,
- relax the parser's spec restrictions,
- alter fixture 15's `expected`, `steps`, or `assertions`.

The prerequisite is one of two separate work items, neither of which changes classification semantics: support a
declared dependency in `package.json` staged with a synthetic registry package that ships a `.node` file, or add ad-hoc
spec support on its own merits. Until then fixture 15 stays `status: proposed` and unscored, and T15 keeps its
definition from being quietly edited to fit.

## 9. Consequences

**Easier.** `UNSUPPORTED_BY_DESIGN` becomes reachable and provable. A refusal is now distinguishable from a crash, from a
timeout, and from our own missing features, which is the distinction the gate depends on. Evidence for a refusal is a
first-class artefact rather than an inference from stderr.

**Harder.** Three states where there was a boolean, in assertions that every report reader touches. The `passed: false`
asymmetry is a permanent sharp edge; it is documented in the type and covered by T8. Skipped steps change the length of
`report.steps`, so any consumer assuming "steps.shorter means earlier break" must read `state`.

**Unchanged on purpose.** Gate threshold, `score.ts`, lane split, lane rates, existing assertions, and every currently
green test's intent.

## 12. Implementation status of the refusal path (2026-11-13)

D-1 says `"unsupported"` is emitted only when the runtime refuses a capability on purpose. That was true of the type and false of the
pipeline: between the runtime and the fixture report the refusal was dropped twice, so a native addon arrived as exit 1 plus a stack
and scored `RUNTIME_INCOMPATIBILITY`. The distinction D-1 rests on was not being measured.

**Carried now, in the harness lane.** `InProcessRuntime` captures an unhandled `ProcessRefusal`; `RuntimeRunOutcome` and
`ProcessRecord` carry it as `refusal`; `Container.execute` returns it on the `CommandOutcome`; `tools/harness/fixture-executor.ts`
maps its presence to `termination: "unsupported"` with the frozen refusal attached by reference (D-6), and leaves the step's `StepRecord`
in place so D-2's assertions are evaluated. `verifyRefusal` is unchanged and still does all the judging: well formed, frozen, declared,
assertions passing (D-5). A refusal the product declined to carry cannot earn the bucket; an undeclared one cannot either.

**Not carried yet, in the product lane.** The process Worker posts `{ type: "exit", code }` to its host
(`src/process/process-worker.ts:196`), so a refusal in a real browser process never reaches `ProcessHost`, the kernel or the container.
Only the harness's in-process client reports it. This is registered as a prerequisite for authoring fixture 15 (W-39) rather than
silently normalised: the fixture lane can measure the refusal today, the user-facing lane cannot yet show it.

## 13. Implementation status of the refusal path (2026-11-14): the product lane carries it too

Section 12's second half is closed. The process Worker now posts the refusal with its exit
(`src/process/process-worker.ts`), and it travels the page's own lifecycle as data rather than as prose:

    process-worker → ProcessHost → ProcessKernel → runtime.worker → worker-client → RuntimeRunOutcome → ProcessRecord

Three properties were required and are pinned by tests:

1. **Validated once, at the first boundary.** `refusalFromWire` (`src/runtime/refusal.ts`) narrows the structured-cloned value: the code must
   be a member of the closed set and the capability and message non-empty, so a malformed or fabricated record becomes "no refusal" and the
   process keeps the ordinary exit status it reported. Junk cannot fill the bucket D-1 reserves for design decisions.
2. **Freeze restored on arrival.** `createRefusal` is still the only constructor, so what the container holds is a frozen refusal on both
   sides of the thread boundary, not a mutable clone. D-10's immutability is a property of the pipeline, not of one lane.
3. **No inference from text.** Nothing in the path reads `stderr` to decide whether a run was refused, and a non-zero status is not evidence
   of one: a program that catches its refusal is an ordinary run (`ProcessRefusal` is catchable by design), and a thrown `Error` is an
   ordinary failure. The four outcomes the pipeline must distinguish are a declared refusal, an undeclared refusal, an ordinary non-zero
   exit, and a worker or harness fault; only the first two can ever be classified.

The evidence schema, D-2's step transitions and `verifyRefusal` are untouched. What changed is where the refusal comes from, not what
`unsupported` means. Fixture 15 is still not authored: this makes the product able to measure the refusal it will assert on.

### 13.1 One settlement per process (2026-11-14, review correction)

Carrying the refusal put two calls on the exit path where there had been one, and the review was right that the settlement callback had to be
invariant under that: `onSettled` fires exactly once per exit message, after the refusal is validated, with the status and the validated refusal
in the same invocation. `ProcessHost.#settle` is now the single gate, and it refuses twice: once for a pid already announced (a Worker that posts
`exit` twice), and once for a pid that is already terminal (an exit report arriving after a worker fault or a kill). The first guard is not
redundant with the second: a HELD-OPEN process is settled and still `running`, so the table cannot be the only answer, and the held-open
duplicate is the case that fails without it.

Checking the neighbouring transitions for the same class of defect found one: `finish` refused the two states it named (`exited`, `failed`) and
so invited a transition OUT OF `killed`, which threw `InvalidTransitionError` from inside the Worker's `onmessage` - a stale report from a dying
Worker took down the host. `finish` now transitions only from a live state. A process that is already over keeps the ending it had.
