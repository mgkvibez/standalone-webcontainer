# ADR-0007 — Fixture Freezing and Gate Integrity

**Date:** 2026-11-03
**Status:** Proposed — implementer-recorded mechanism, awaiting the end-of-project expert audit
**Deciders:** Charter §4.9 and §4.10 state the requirement; the mechanism that satisfies it is recorded here for audit

## Context

The charter's gate is only worth the evidence behind it if the fixtures cannot move after results exist. Two rules
carry that weight:

- §4.9: never redefine the gate after results.
- §4.10: never move the threshold after seeing results.

The harness already does three things correctly. `GATE_THRESHOLD` is a module constant, not a parameter. A definition
in state `proposed` is refused by `isScoreable`. A missing front-end fixture blocks the gate rather than being averaged
away. All 20 slots have definitions written from published evidence (`fixtures/definitions/`), and all 20 are
`proposed`, because sign-off is the owner's act and nobody else's.

What was missing is the case that matters most: a definition that says `frozen` and has been edited since. Nothing
compared a definition's content to anything, so "frozen" was an assertion by whoever last saved the file. A fixture
could fail, be relaxed, and pass, with the gate reporting the higher rate and no trace of the edit. Reading the diff
is not a control: nobody rereads 20 definitions before believing a number.

Options considered:

1. **Trust `status: "frozen"`** (the status quo). Zero cost, and it is precisely the hole described above.
2. **Hash the file bytes.** Detects edits, but treats reformatting as tampering while a reordered semantic change
   passes, because JSON key order is not content.
3. **Hash canonical content, record the digest in the manifest, verify on load.** Chosen.

## Decision

A frozen definition is pinned by the SHA-256 of its canonical content, recorded as `frozenHash` in
`fixtures/manifest.json` and verified before the gate is computed.

Details that follow from it:

- **Canonical JSON, not bytes.** Keys are sorted recursively; array order is preserved because it is semantic. Key
  order and whitespace are not content, so a reformat must not look like an edit.
- **`status` is excluded from the hash.** Freezing is a lifecycle transition, not a content change: the owner approves
  a definition by flipping `proposed` to `frozen`, and that must not invalidate the pin they just approved. Everything
  else is covered, including `knownLimits`, because it informs how a result is read.
- **Four states, one scoreable.** `frozen` (matches the pin) is scoreable. `unfrozen` (`proposed`) is not, and is not
  an integrity problem. `unpinned` (claims frozen, no pin recorded) is not scoreable: an unverifiable claim is worth
  no more than a proposed one. `drifted` (content no longer matches) is not scoreable and fails the run.
- **Withholding is structural.** `scoreVerifiedFixtures` computes the gate from verified fixtures only and lists what
  it withheld, so withholding is the default rather than something a caller remembers. A withheld front-end fixture
  still blocks the gate, because the charter's rate is over all fifteen.
- **Drift fails, it does not merely reduce the rate.** `assertFreezeIntact` throws on drift and on unpinned claims. A
  silently lower rate would hide the edit that caused it.
- **The authoring tool cannot manufacture consent.** `npm run fixtures:freeze` pins only definitions already marked
  `frozen` and reports the rest as awaiting sign-off. `npm run fixtures:check` never writes, and runs as part of
  `npm run verify`, so CI can detect drift but cannot refresh a pin on its way past it.
- **No new dependency.** Hashing uses `crypto.subtle`, the same WebCrypto the installer already uses for tarball
  integrity; the tool runs through `vite-node`, which ships with vitest. License impact: none.
- **No architectural claim about the runtime.** The mechanism lives entirely in the harness and the authoring tool; it
  changes no runtime API and no lane behaviour.

## Consequences

Easier: a claimed rate is reproducible from the repository alone. Editing a frozen fixture is either impossible
without detection or has to be recorded by re-running the freeze tool, which shows up as a manifest diff in review.

Harder: any edit to a frozen definition, including fixing a typo in `knownLimits`, requires a re-freeze and a manifest
change. That friction is deliberate; it is the cost of a fixture being a pre-registered measurement rather than prose.

Foreclosed: hashing raw bytes, and hashing the lifecycle label. Both are ruled out above with reasons.

## Open Questions

1. **Should `status` really be outside the pin?** Keeping it outside is what lets the owner freeze without invalidating
   the hash. The alternative (pin everything, re-freeze on sign-off) is stricter but makes the approval step itself a
   content change. Recorded for the audit rather than decided silently.
2. **What freezes the definitions themselves?** This ADR provides the mechanism, not the approval. All 20 definitions
   remain `proposed`, so the gate can legitimately count none of them yet. Freezing them is the owner's sign-off on
   fixture *content*, which is a product decision and is not taken here.
3. **Should the pin survive a deliberate correction?** Current behaviour: correcting a frozen definition is allowed,
   but requires the owner to re-run `npm run fixtures:freeze`, and the manifest diff is the audit trail. An
   append-only ledger of pins (old hash, new hash, reason) would be stronger and is not implemented.

## Approval

No approval recorded. Charter §4.9/§4.10 require the property this implements; the mechanism is provisional and listed
for the end-of-project audit under the owner's standing decision to build to completion without per-PR gating.
