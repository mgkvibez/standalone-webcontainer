# ADR-0034: A save reaches the live filesystem, a preview is a panel, and a session's clock is off

**Status:** Accepted, implemented 2026-11-12 (W-26).
**Depends on:** ADR-0029 (a run is a process), ADR-0033 (a previewed page opens a socket), ADR-0013 (the scheduler's clock).

## The problem

W-25 proved a previewed page can open a websocket to a program inside a process Worker. W-26 asks the question that matters more: does a
dev server's *own* loop work end to end, meaning a person edits a file and the page already open applies the change without reloading?

Driving Vite's shape through the real product found three defects, none of them in the websocket path. Each was load-bearing: with all three
present the loop cannot happen at all, no matter how correct the framing is.

1. **The kernel only ever learned a project's files as a snapshot at the start of a run.** The editor's save wrote to the page's store. The
   run's request carried that store as a tree, the kernel built its filesystem from it, and after that nothing crossed: an edit made while a
   program ran existed in the page and nowhere else. A dev server's `fs.watch` was therefore perfectly correct and permanently silent, which
   is the worst shape of defect: every part works, the feature does not.
2. **The preview was a modal overlay.** It covered the explorer and the editor, so a person could preview a page or edit a file, never both.
   For a hot-reload loop that is not a cosmetic complaint: the loop *is* the pair.
3. **Every running server was killed five seconds after it appeared.** The run carried a default wall-clock budget. A script needs one; a
   server's body never finishes, so the budget was the only thing ending it, and every previewed server died while it was still being looked
   at.
4. **`fs.watch` was refused by name in the product.** The kernel never constructed the watch registry that the filesystem writes into, so the
   runtime answered "this runtime does not serve filesystem watches". Every watch test passed, because every watch test built its own
   registry: a dev server could be written, started and previewed, and then be told that watches do not exist.
5. **A running server's ports were only reported when its run settled.** The port announcement arrived on the process's own `MessagePort`,
   which bypasses the kernel's `accept` funnel, so the hook that fired for tests never fired for a program. The preview button therefore
   appeared only for servers whose run had finished, which for a server is never.

## Decision

**1. A save is written through to the live project.** `WriteFileMessage` carries a saved path and its text from the page to the runtime
Worker; the worker applies it with the kernel's own `writeFile`, which is the same entry point a program's write uses, so the change
subscription fires and every watcher hears it (ADR-0028's registry). Two properties are deliberate:

- **Nothing is buffered.** A save made before the first run is dropped, not queued. The next run carries the whole snapshot anyway, so a
  queue would exist only to duplicate it. `Container.pushFile` returns early when `#runtimeProjectId` is null, and a worker with no kernel for
  that project ignores the message.
- **Fire and forget.** A save has no reply. The page does not wait, and a lost message is repaired by the same snapshot that would have
  carried it.

`Container.pushFile` is separate from `Container.writeFile` on purpose: `writeFile` stages files for an install, and conflating "the project
changed" with "a program is running and should hear about it" is what made the gap invisible in the first place.

**2. The preview is a panel in the grid, not a dialog over it.** `#preview-overlay` is a grid item at row 2, column 2, and `#app` gains a
second column exactly while it is visible (`#app:has(#preview-overlay:not([hidden]))`). The three workspace regions are placed explicitly
(`#topbar` row 1 spanning both columns, `#body` row 2 column 1, `#bottom` row 3 column 1) because auto-placement with an extra item moved the
terminal into the editor's row and put the explorer under the preview. That was observed, not predicted: the browser lane's tree click was
intercepted by the preview iframe, and measuring the boxes showed `#bottom` at row 2.

**3. The kernel owns one watch registry, and a leaving process takes its watches with it.** It is constructed where the filesystem is
(`new WatchRegistry({ statKind })`) and subscribed to the filesystem's change events, so a write from a program, from the kernel, or from the
page's editor reaches every watcher through one path. The owner of a watch is bound by the kernel when it is created, never sent by the
requester: a process that could name its own identity could drain or cancel another process's watches. When a process retires, its watches
stop.

**4. Ports are announced in the broker's message funnel.** That funnel is the one place a message from a real process and a message from a
test both pass through, so the announcement is validated once and used twice, and the preview list no longer waits for a run that will not
settle.

**5. A session's program has no wall clock by default.** `timeoutMs` defaults to `0`, meaning "no clock; the stop button ends a session's
program", and a caller that awaits a bounded answer (the fixture harness, an invocation) passes a budget explicitly. A program that ends on
its own still ends on its own; the clock never was the mechanism for that.

## Alternatives rejected

- **Poll the store from the kernel.** The kernel has no view of the page's store and inventing one (a fetch, a SharedArrayBuffer mirror)
  gives a second source of truth for the same bytes. The save already knows what changed.
- **Send the whole snapshot on every save.** Correct and simple, but it turns a keystroke into a project's worth of writes and makes every
  watcher fire for files that did not change. A real Vite watches dozens of files.
- **Keep the preview modal and close it to edit.** That tests a loop no user has: they would have to guess when to look.
- **A longer default budget instead of none.** A budget that is merely longer is the same defect with a slower clock. There is no number
  that is right for both `process.exit(0)` and a server.

## What this does not claim

- **Not Vite.** The container has no registry, so a real `vite` cannot be installed in the browser lane. The spec implements the *shape*:
  an upgrade listener that answers with the subprotocol it was offered, a watcher on the module, and a text frame per change. What is proven
  is that this runtime carries that shape across four boundaries; what is not proven is any particular bundler's behaviour inside it.
- **No backpressure and no keep-alive** (ADR-0030's limits stand), and a page's socket still carries one connection at a time.
- **The docked panel is not resizable** and the split is a fraction, not a saved preference.

## Evidence

`tests/browser/dev-server-hmr.spec.ts` drives the real product: the editor creates `/dev-server.js` and `/app.js`, the terminal runs the
server, the origin-separated shell shows it, the socket opens with `vite-hmr`, an edit through the editor reaches the page as a pushed update,
and `__docId` is unchanged across the update, so the realm was never replaced. Mutation-checked: with `pushFile` removed the page stays on the
old text and the spec fails.

Three unit tests cover the save seam from outside the browser: a save reaches the live project with the project id the run started with, a
save before any run is dropped rather than queued, and two saves keep their order. The watch registry's own tests (ownership, retirement,
notify semantics) were already there; what was missing was the kernel constructing one, which is why they passed while the product refused.
