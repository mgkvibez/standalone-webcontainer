# ADR-0004 — Provisional implementation decisions taken while the expert is unavailable

**Date:** 2026-11-03
**Status:** PROVISIONAL — every decision below is flagged for the post-hoc expert audit

**P0 supersession (ruled 2026-11-08, implemented 2026-11-12 as W-17):** D-3 (`process.platform = "browser"`) is amended to `"linux"` because packages branch on it, and D-5 (a `while (true)` loop cannot be stopped) is resolved for the process lane by ADR-0018. D-1 is kept, with the fate of `src/shims/presets.ts` to be decided (wire it in or delete it) rather than left in limbo. See P0-rulings.md P0-5 and P0-6.
**Deciders:** Implementer, acting on the product owner's instruction: "for this time the
expert is unavailable you will have to be the one to do everything then when you're
completely done the expert will do a large scale audit and point out where you need to
work on."

The charter forbids the implementer from making architectural decisions. That rule is not
suspended here. What changes is the review timing: decisions had to be taken to make
progress, so each one is recorded with its reasoning, its blast radius, and the specific
question the audit should answer. Nothing below is silently baked in, and nothing below is
expensive to reverse.

## D-1. Substrate realized as libraries, not as `unenv`/`memfs` packages

ADR-0003 #1 ratifies `unenv` presets for `path`/`process`/`buffer` and `memfs` as the `fs`
API-shape reference. Implemented instead: `pathe` (MIT, zero deps) for `path`, `buffer`
(MIT, with `base64-js` MIT and `ieee754` BSD-3-Clause) for `Buffer`, and a hand-written
`fs` translation onto our VFS.

**Why:** `unenv` pulls `defu`, `mime`, `consola`, `node-fetch-native`; `memfs` pulls
fifteen `@jsonjoy.com` packages plus `tslib`, `thingies`, `tree-dump`, `glob-to-regex.js`.
Those are the exact libraries `unenv`'s presets wrap, so this is not a different choice,
it is the same choice with four auditable dependencies instead of twenty-plus. Adding
twenty dependencies to the lockfile in a week when nobody can audit them is a worse
charter violation than deferring the wrapper.

**Audit question:** accept the library-level substrate permanently, or require the `unenv`
wrapper once the transitive tree can be license-audited line by line?

## D-2. Synchronous seam added to `FileSystem`

`writeFileSync`, `readFileSync`, `mkdirSync`, `readdirSync`, `statSync`, `unlinkSync`,
`rmdirSync`, `renameSync` were added to the ADR-0002 VFS. Each async method now yields and
then delegates to its sync body, so there is one implementation per operation.

**Why it is not a new decision:** ADR-0002 #2 says sync APIs "will block *only* the worker
thread", which presupposes sync entry points exist inside the worker. ADR-0002 #7 makes
`fs` the first shim, and CommonJS `require()` and `fs.readFileSync()` cannot await. The
alternative — an async-only runtime — cannot run the packages the gate is about.

**Audit question:** is a sync seam on the VFS the intended reading of decision #2, or should
sync capability live in a separate worker-side kernel object with the VFS staying async-only?

## D-3. `process.platform` is `"linux"` (amended by P0-5); `process.version` is Node-20-shaped

**Why:** the original ruling was `"browser"`, on the argument that code should see where it actually runs. P0-5 reversed it
on a measured consequence rather than a preference: the packages that branch on platform branch to POSIX paths this runtime
already provides (a `/`-rooted VFS, `/bin/sh`-shaped argv, no drive letters), while `"browser"` sends them down a browser
branch nothing here implements. `esbuild` is the concrete case, since it composes its native-package key from
`process.platform` and `os.arch()`; `os` therefore reads this field instead of deciding for itself, and the pair is asserted
together so the two cannot drift.

The cost, stated rather than hidden: a package that would have printed "unsupported in this environment" now takes the Linux
path and fails where it fails. That is the honest failure, and it is the one a report can name.

Code that gates features on `process.version` should not be lied to about the API level we target (ADR-0002 #7: Node 20 LTS),
so `"v20.0.0"`.

## D-4. Resolution scope for Phase 1

Supported: exact file, `.js`/`.cjs`/`.json` extension guessing, directory `package.json`
`main`, `index.*`, upward `node_modules` walk, `node:` builtin prefixes, circular requires
(cache-before-evaluate, as Node does).

Not supported, and not claimed: `browser` field substitution, `.node` binaries,
dynamic `require(expr)`, `import()` inside a CommonJS module.

**Why:** `exports` maps are the single largest fidelity risk in the whole project and
implementing them from intuition rather than against fixtures is how this class of runtime
loses trust. Recorded as a gap until fixtures can measure it.

**Amended (2026-11-11): `exports` maps are implemented, and the reason is the one this ADR
asked for.** A fixture now demands them: `vite@5.4.21` resolves `rollup/parseAst`, whose map
is `{ types, import: "./dist/es/parseAst.js", require: "./dist/parseAst.js" }`, so the map
decides which file loads rather than whether one exists.

Supported, each verified against node v20.20.2 before it was written:
- subpath keys (`"."`, `"./x"`), pattern keys with `"*"` (longest prefix wins), and `null`
  targets meaning explicitly not exported;
- string, array and condition-object targets, with arrays as fallbacks (first that resolves);
- the condition sets this runtime can answer honestly: `node`, then `require` or `import`
  depending on which edge is resolving, then `default`. `types`, `browser`, `development`
  and `production` are deliberately NOT in the set, so they are skipped rather than guessed;
- `ERR_PACKAGE_PATH_NOT_EXPORTED` as an error rather than a miss, because Node makes the map
  authoritative: a file on disk that the map does not list stays unreachable;
- the `Error [CODE]: message` header Node prints for a coded error, matched in the class that
  raises it rather than in the shared formatter (`MODULE_NOT_FOUND` prints without a bracket).

Still not supported, and still not claimed: `imports` maps (#-specifiers), `browser` field
substitution, the self-reference rule for a package importing its own name, and `import()`
inside a CommonJS module.

**Audit question:** is `exports` map support required before the gate can be measured at all,
and in what condition order?

## D-5. In-process runtime cannot preempt synchronous code

`InProcessRuntime` is the Phase-1 execution engine and is tested in Node. It cannot
interrupt `while (true) {}`; `timeoutMs` bounds awaits only and returns `timedOut: true` with
exit 124. Hard timeout enforcement belongs to the dedicated worker (ADR-0002 #2), where
`terminate()` exists.

**Audit question:** confirm that fixture TIMEOUT classification is expected to be
unmeasurable until the worker lane lands, or require the worker before any gate run.

## D-6. Pre-existing dev-dependency advisories, left alone deliberately

`npm audit` reports moderate advisories in `vitest` (≤4.1.10, path traversal /
mock registration) and `esbuild` (≤0.24.2, dev-server request reflection). Both are
dev-only, neither ships, and both predate this work. The fix is a vitest major bump
("breaking change" per npm), which is the expert's call, not a quiet upgrade.

**Audit question:** upgrade `vitest` to ≥4.1.12 now, or pin and accept the dev-only risk?

## What this ADR does NOT authorize

- No network layer, service worker, terminal, or persistence work.
- No fixture CONTENT. `fixtures/manifest.json` still lists twenty slots with
  `definitionPath: null`; the gate remains unmeasurable until the product owner defines the
  fixtures. That is a product "what", not an implementation detail.
- No merge of PR #8 or this work. Both remain submitted for review.

## Addendum — a fidelity finding worth keeping

The differential test against `node:path.posix` immediately caught three real deviations in
the substrate: leading `//` collapsed by Node but preserved by `pathe`, `extname(".hidden")`
returning `".hidden"` instead of `""`, and `".."` not clamped at the root. Two are corrected
in our wrapper; `normalize` is now implemented directly from POSIX rules because it
underpins module resolution. This is the "package X breaks on call Y" grind in miniature,
and it is the argument for keeping differential tests against Node itself rather than
against our own expectations.
