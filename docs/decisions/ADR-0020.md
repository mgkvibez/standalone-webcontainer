# ADR-0020: `fs.watch` is a pull, not a push

Status: Accepted (2026-11-09). Implementation: `src/process/watch-registry.ts`, `src/process/remote-watch.ts`, watch ops in
`src/process/fs-syscalls.ts`, VFS change notification in `src/vfs/index.ts`.

## The problem

In Node, a watcher is pushed to: libuv holds an inotify/kqueue/FSEvents handle and calls back into the event loop. That shape
cannot be copied here. A process spends most of its life blocked inside `Atomics.wait` waiting for a syscall answer, so a
kernel that wanted to deliver an event would have to write into a channel the process is not reading, and would have to do it
through a process that may already be dead. The push would either be lost or wedge the channel.

## Decision

**The process pulls.** The kernel holds the watches; a process asks for what is queued (`poll`) on a timer.

Consequences, all accepted deliberately:

1. **Delivery latency is up to one poll interval (default 20 ms).** For the intended consumer, an HMR flow whose next step is
   a module reload, that is invisible. For a program measuring nanosecond file timing it is not, and the interval is
   configurable rather than fixed.
2. **Events can be dropped by a watcher that never polls.** The per-watch queue is bounded (`MAX_PENDING_EVENTS`, 512) and
   drops the *oldest*, then reports the count. An unbounded queue is a memory leak wearing the costume of a feature, and a
   silent drop is worse than either.
3. **Coalescing happens kernel-side, per path, and `rename` outranks `change`.** Twenty-five writes to one file between two
   polls arrive as one event, which is what Node does and what a program wants. A creation followed by writes reports
   `rename`, because "it appeared" is news a later content change must not overwrite.
4. **`recursive` is supported everywhere.** Node supports it on macOS and Windows but not natively on Linux, which makes code
   platform-dependent; the VFS is a flat map, so recursion is a prefix test and costs nothing. This is a deliberate widening,
   not parity: a program that relies on `recursive` working here would break on Linux Node.
5. **Watch ownership is bound by the kernel, never sent by the process.** The handler carries an `owner` (the pid whose channel
   is being served). A process that named its own identity could poll or cancel another process's watches.
6. **A process exit releases its watches** (`stopAll(owner)`), and the E2E asserts the registry is empty afterwards. A watch
   feeding a dead channel is the failure this exists to prevent; a phantom watcher looks exactly like a working feature until
   the day memory runs out.

## What the VFS gained

`FileSystem.subscribe(listener)` emits `{ kind: "change" | "rename", path, previousPath? }` from every mutation. Two rules
protect the observed write: a throwing listener is contained (notification observes a write that already succeeded, so a
watcher bug must not fail it), and emitting costs one size check when nobody is watching.

Rename emits **one** event carrying both paths rather than two unrelated ones, so a watcher can tell a move from a delete and a
create that happened to be adjacent.

## Not yet reachable from user code

The `fs` shim does not expose `watch` yet, so a fixture cannot call it. The kernel half is proven — cross-process delivery and
exit cleanup are E2E-tested in `tests/browser/watch-cross-process.spec.ts` — but until the shim and the event loop's liveness
rule (an open watcher keeps the process alive, as in Node) are wired, this is infrastructure, not surface.
