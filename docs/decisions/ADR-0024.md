# ADR-0024: the preview carries no server push, so "edit, then see it" is host-driven

**Status:** accepted, 2026-11-11. **Supersedes nothing.** **Relates to** ADR-0022 (worker transport), ADR-0013 amendment 4 (a served request
keeps the queue running).

## Context

The last front-end path with no measurement on it was Vite's update channel. A dev server's whole editing experience — hot update, error
overlay, full reload — rides on one websocket, and nothing in the corpus ever opened one.

Measured (`tools/probe-vite-hmr.ts`, then a real server for comparison):

| Request | This runtime | Real Vite 7.3.7 |
|---|---|---|
| `GET /` | 200, mentions `/@vite/client` | 200 |
| `GET /@vite/client` | 200, 137 820 bytes, config injected | 200 |
| `GET /` with `Connection: Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Key`, `Sec-WebSocket-Version: 13`, `Sec-WebSocket-Protocol: vite-hmr` | **200, the HTML page** | **101** |

So a handshake is answered like an ordinary GET. `src/shims/http.ts` says as much: request/response and keep-alive, "not TLS/HTTP2 and not
the `upgrade` event, which is why websockets in the browser lane are a later, separate problem". The comment is accurate, and this ADR settles
what "later" means.

The consequence is not a missing log line. From Vite 5.4.21's shipped client (`dist/client/client.mjs:745`): the page dials
`ws://<host>:<port>/?token=…` with subprotocol `vite-hmr`; when that fails and the port is known, `connect()` logs
`[vite] failed to connect to websocket` and **throws** (`:777`). The "server connection lost. Polling for restart..." path at `:865` only runs
for a socket that opened and then closed, which cannot happen here. The result: **no hot update, no error overlay, no reload on edit.** The page
renders and then stays exactly as it was until someone reloads it by hand.

## Why no amount of server-side work fixes it in the browser lane

The runtime is a Worker inside the page, not a port on a network. The preview reaches it through a **Service Worker** that intercepts `fetch`
in an iframe on a separate origin (`src/browser/preview-shell.ts`). A service worker's `fetch` event covers `fetch`/XHR; it does not cover a
websocket handshake, by specification. There is therefore no transport to carry a socket, and no network endpoint to dial around it: the
server does not exist outside the page.

Implementing `upgrade` and WebSocket framing in the http shim would make an in-runtime client able to talk to an in-runtime server, which is a
Node-compatibility item in its own right (a project depending on `ws` cannot work today). It would **not** give the browser preview live
updates. The two questions are separate and are now recorded as such.

## Decision

1. **Server push over the preview is out of scope**, and no work is planned for it. Vite's HMR, error overlay and full-reload-on-edit are
   unavailable in the browser preview, and that is a documented property rather than a bug.
2. **"Edit, then see it" is host-driven.** The editor is the only writer of a project's files, so the host knows when a change happened. The
   preview frame is reloaded by the host when the project changes, using the existing host-to-frame path and its nonce. No new network surface,
   no new protocol beyond a reload message.
3. **The runtime's lack of `upgrade` stays a compatibility gap, not a preview requirement.** Tracked separately; it is the honest reason a
   `ws`-based server does not work in this engine.
4. **The gateway's behaviour is pinned, not assumed.** `tests/unit/network.preview-gateway.test.ts` asserts that an upgrade-shaped request is
   answered like a plain one, so anyone who later implements upgrades meets that test and this ADR together.

## Consequences

- A dev server in the preview is a *serving* dev server: it serves the project, and changes appear on reload.
- Since the preview cannot be told "the file changed", the host must do it. Until that lands, a code change in the editor is visible in the
  preview only after a manual reload, and this ADR says so plainly instead of leaving it to be discovered.
- The CLI/Node lane is unaffected: nothing there depends on the preview transport.
