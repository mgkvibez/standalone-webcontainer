# ADR-0013 — Draining Continuations Before Reading Output

**Date:** 2026-11-04
**Status:** Proposed — implemented to keep building; decisions listed for the single end-of-project audit.

**P0 supersession (proposed 2026-11-08):** proposed for supersession by ADR-0018. Real timers and a real event loop replace the drained virtual clock on the default path; the virtual clock survives only as an opt-in `virtualClock: true` test mode. See P0-rulings.md P0-3.

## Context

ADR-0012 recorded a liveness gap rather than a decision: `run()` snapshotted stdout the moment synchronous evaluation
ended, so `console.log` inside a `.then` wrote into a sink nobody read. The program looked like it printed nothing.

That is not a corner case. Modern Node code logs from continuations constantly, and giving the loader ES modules without
closing this would have produced fixtures that fail for a reason that has nothing to do with the code under test.

## Decisions

**D-1. Drain, then read.** After evaluation ends, the runtime waits one macrotask boundary before snapshotting output.

**D-2. A macrotask boundary, not a microtask hop.** `await Promise.resolve()` only lets the FIRST continuation run: a
`.then` that queues another `.then` is still pending when the awaiting code resumes. The microtask queue is guaranteed
empty when a timer callback runs, and that guarantee is available in both a browser and Node.

**D-3. No drain when the run already timed out.** The budget was exhausted; spending more of it before returning would
misreport how long the run took.

**D-4. Output order is preserved, not reordered.** Synchronous output still comes first, continuations after, because
both write to the same sink as they happen.

## Consequences

Output from continuations is now observed, which is what makes any async program testable. A fixture whose assertion is
"stdout contains X" can now say so about a program that logs from a promise.

The cost is roughly one macrotask per run (a real `setTimeout(…, 0)`), which is immaterial next to an install.

## What this does not fix

**Work scheduled on a real timer is still unobserved.** `setTimeout(() => console.log("late"), 50)` prints into the sink
after the snapshot, because the runtime has no timer queue of its own and cannot know how long to wait for work it did not
schedule. Fixtures that rely on timer output will under-report, and that is a gap, not a policy.

**An exit code or throw inside a continuation is still unattributed.** `process.exit(2)` in a `.then` throws a
`ProcessExit` inside a promise, which surfaces as a host-level unhandled rejection rather than the program's exit code.
Attributing it needs a rejection handler scoped to the run, which is the next slice and is deliberately not guessed at
here.

## Audit questions

Q1. Is one macrotask boundary the right drain, or should the runtime drain until quiescence with a bounded iteration
count? Quiescence cannot be detected from userland, which is why this is bounded by construction.

Q2. Should the timer gap be closed by giving the runtime its own timer queue and a "run until the queue is empty"
contract, which is what Node actually does? That is a real event loop, and it decides when a program is finished.

Q3. Should async exit codes and throws be attributed to the program (scoped rejection handler) or reported as a harness
limitation? Attributing them is more useful and more work to get right.

Q4. Does the extra macrotask per run matter for the memory-ceiling and timeout fixtures, where the harness itself is
inside the budget being measured?

## Ratification

Provisional. The expert owns D-1..D-4 and the four questions above; nothing here is presented as settled.

## Amendment 1: the 1,000 ms virtual scheduling budget (Phase 6, R4 contract)

The owner approved a provisional virtual scheduling budget and required this amendment **before** the scheduler is written,
so the contract is fixed while it is still cheap to argue about. **No scheduler exists yet**: this section is the
specification, not a description of running code. `setTimeout(..., 5)` is still unobserved today.

### Budget

One execution gets **1,000 ms of virtual time**, provisional and subject to the audit. Virtual time advances by jumping to
the next due timer, never by waiting. The wall-clock budgets in §4.5 (install 180 s, build 240 s, run 60 s) are unchanged
and still apply separately: virtual time bounds *what can be scheduled*, wall-clock bounds *how long we wait*.

A timer scheduled beyond the budget is not silently dropped. It is recorded as deferred-beyond-budget in the step evidence,
because a silent drop is indistinguishable from a callback that never fired.

### Ordering

Timers are ordered by `(dueTime, sequence)` as integers: earliest due first, and ties broken by creation order. Never by
callback identity, name, or completion timing. Two runs of the same program therefore fire timers in the same order, which
is what makes a timeout finding reproducible rather than a coin flip.

### Lifecycle

| State | Meaning |
|---|---|
| pending | scheduled, not yet due |
| firing | callback running; the clock does not advance during it |
| fired | one-shot completed |
| cleared | cancelled by `clearTimeout`/`clearInterval` before firing |
| deferred | due after the budget end; recorded, never fired |

`setImmediate` is treated as due at the current virtual time, ordered after everything already due at that instant.

### Continuation draining

After every callback, the scheduler drains microtasks and promise continuations to quiescence before advancing the clock.
Without this, a `setTimeout(() => { Promise.resolve().then(print) }, 0)` would print after the snapshot and the run would
report empty output for a program that worked (the exact failure ADR-0013 was written for).

### Interval protection

An interval fires at most once per virtual instant, and at most `min(ceil(1000 / delay), 100)` times per execution. A
5 ms interval therefore gets 100 fires rather than an unbounded loop, and the truncation is recorded in evidence rather
than passing silently. `clearInterval` removes it from the queue immediately, including from inside its own callback.

### Bounded execution

The scheduler stops when the queue is empty, the budget is exhausted, or the interval cap is reached. In every case the
stop is recorded with the virtual time consumed. A run can never spin: no path exists from "timer fired" to "clock advances
without bound".

### What this amendment does not decide

Whether virtual time should be exposed to programs through `Date.now()` and `performance.now()`. A program that measures
elapsed time across two timers currently sees real time; under a virtual clock the honest answer is virtual time, but that
changes observable behaviour for every fixture, so it is a question for the audit rather than a detail to slip in.

## Amendment 2: the virtual clock and the work safeguard (Phase 6, R4 contract)

Owner decision: **`Date.now()` reports virtual time.** That settles amendment 1's open question, and it is the decision with
the widest blast radius in this project, because it changes what every fixture observes about time. This section is the
contract the scheduler is written against; it is written before the code.

### The clock

| Fact | Rule |
|---|---|
| Baseline | one real wall-clock instant captured **at execution start**, before the first user statement runs |
| `Date.now()` | baseline + virtual elapsed — so a program that measures two timestamps sees the virtual interval |
| `new Date()` | same instant as `Date.now()`, so the two never disagree |
| `performance.now()` | monotonic virtual elapsed since execution start, starting at 0; never decreases, never jumps |
| `performance.timeOrigin` | the baseline, so `timeOrigin + now()` equals `Date.now()` |

**Virtual elapsed is not execution time.** Two runs of the same program report the same virtual elapsed and may take wildly
different real milliseconds. Evidence therefore records both, distinctly, and never presents one as the other: a fixture
that "took 100 ms" took 100 ms of *virtual* time, and the harness reports how long it really took alongside it.

Advancing is a jump: the clock moves to the next due timer, never by waiting. That is why a 900 ms timer costs microseconds
of real time and why the budget below is a budget of *scheduled* time.

### The schedule

| Operation | Due time | Ordering |
|---|---|---|
| `setTimeout(fn, delay)` | virtual now + delay | by `(due, sequence)` |
| `setInterval(fn, delay)` | virtual now + delay, repeating | by `(due, sequence)`, rescheduled after each fire |
| `setImmediate(fn)` | virtual now | after everything already due at that instant |
| `queueMicrotask` | unchanged: the host's microtask queue | runs to quiescence between callbacks |

Equal deadlines fire in creation order, always. Ordering is `(due, sequence)` compared as integers, never by callback
identity or by which finished first: two runs of one program must fire the same callbacks in the same order, or a timeout
finding is a coin flip.

### Cancellation

`clearTimeout`/`clearInterval` remove the pending entry immediately, including from inside its own callback and from inside
another timer's callback. A cleared entry never fires and is not counted as a callback. Clearing an id twice, or an id that
never existed, is a no-op rather than an error, matching Node.

### The 1,000 ms budget

One execution gets 1,000 ms of virtual scheduling time, provisional and subject to audit. A timer due **at or before**
budget end fires. A timer due **after** it is recorded as deferred and never fires; per amendment 1 it is never silently
dropped, because a silent drop is indistinguishable from a callback that failed.

### The work safeguard (separate from the budget)

The budget alone does not bound work: a `setTimeout(fn, 0)` loop never advances virtual time, so it would spin forever
inside a 1,000 ms budget. Two independent guards therefore apply:

| Guard | Default | Defends against |
|---|---|---|
| `maxCallbacks` | 10,000 callbacks per execution | zero-delay loops, and any chain that keeps rescheduling at one instant |
| `maxRealMs` | 5,000 ms of real time | microtask storms and pathological synchronous work inside callbacks |

Interval protection from amendment 1 still applies on top: an interval fires at most `min(ceil(1000 / delay), 100)` times,
and a truncation is recorded rather than passed silently. A 0 ms or 1 ms interval hits both the per-interval cap and the
callback cap, which is deliberate redundancy: either alone would end the run, and belt-and-braces here costs nothing.

### Deterministic termination, and the evidence

Draining ends for exactly one reason, recorded as a stop reason:

| Stop | Meaning |
|---|---|
| `queue-empty` | everything scheduled has fired; the normal end |
| `budget-exhausted` | the next due timer is past the budget; remaining entries are `deferred` |
| `callback-limit` | `maxCallbacks` reached; remaining entries are `truncated` |
| `real-time-limit` | `maxRealMs` exceeded; treated as a harness-bounded stop, not a program result |

Evidence for each execution states `stop`, `virtualElapsedMs`, `callbacks`, `realElapsedMs`, `deferred`, `intervalsTruncated`
and the count of entries never run. The same program run twice must produce identical evidence: that is what makes a
zero-delay loop finding reproducible rather than a race.

A stop caused by a guard is never reported as the program's own behaviour. `callback-limit` and `real-time-limit` are
harness bounds, so they are surfaced as such and must not be scored as the runtime refusing something.

### Addendum after R5: draining means quiescence, not one pass

Staging fixture 4 found two things this amendment under-specified, both fixed in R5's first commit.

**A single pass is not a drain.** A timer scheduled from inside a promise continuation can land after the queue looked
empty. Fixture 4 hit exactly that: its timer was scheduled from a `pipeline` callback, the queue was empty when draining
began, and `timer-ok` never printed while the program was correct. Draining now runs passes until a pass finds nothing
AND a continuation drain adds nothing, with `maxCallbacks` bounding the whole execution rather than one pass, so a
continuation that keeps rescheduling still terminates on the same guard.

**A synchronous throw must belong to its run.** An exception raised inside a timer callback is caught by the scheduler
already. One raised during the post-evaluation drain now cannot escape either: the drain is wrapped, the message goes to
that run's stderr, and the exit code becomes 1.

**Still open, and unchanged by this:** a throw inside a `.then` is an UNHANDLED REJECTION, not a synchronous throw, so
`run()` resolves normally and the failure is unattributed. Capturing unhandled rejections per execution needs interception
that can tell one concurrent run's rejection from another's, which is a decision of its own; this amendment does not
pretend to have made it. It is NOT test-covered: provoking it leaks a real unhandled rejection into the test runner, which counts it as a
suite error, so a passing test and a green suite cannot both be had that way. The gap stays documented and visible in
this amendment instead of being pinned by a test that breaks the run it is part of.

Also corrected in the stream contract (ADR-0015): the canonical `callback(null, value)` form is no longer read as an
error. Treating `null` as an error rejected the idiomatic Node call with `Error: null`, which is how the first harness run
died.

### What this amendment does not do

It does not virtualise `fs.watch`, `process.hrtime`, or `AbortSignal.timeout`. Those either do not exist here yet or are
outside the scheduling question, and pretending otherwise would widen this decision silently.

## Approval

## Amendment 3 (2026-11-09): microtasks run before timers, and nextTick is not a microtask

Amendment 2 required the timer queue to run to termination **before** the continuation drain. Measurement says that is
wrong against Node, so the order is now the other way round: continuations settle, then timers, then continuations again
(the scheduler still drains its own queue to quiescence between passes, so a timer scheduled from a continuation is not
lost either way).

Why the old order failed: Node runs every microtask before the first timer callback. A program that registers a timer and
*then* starts a promise chain therefore prints the chain first. Amendment 2's order printed `m1,timer,m2` where Node
prints `m1,m2,timer` (differential case `microtask-starvation`).

`process.nextTick` also stopped being `queueMicrotask`. A microtask-based flush is too late whenever a promise
continuation was registered before the tick, so `Promise.resolve().then(a); process.nextTick(b)` printed `a` then `b`.
It now has its own queue (`src/runtime/ticks.ts`) drained at the end of the synchronous turn, which is what Node does.

Measured effect: the event-loop differential went from 3 of 7 cases matching Node to 7 of 7. The three fixtures that
depend on this scheduling (4, 7 and the corpus lane) were re-run unchanged and still pass, so no fixture expectation was
rewritten to accommodate the new order.

Still not covered: a tick queued from inside a promise continuation runs at the next flush point rather than ahead of the
remaining continuations, where Node would run it first. Closing that needs ownership of the microtask queue, which is
ADR-0018 work. A throw inside a tick still surfaces as an unhandled rejection rather than killing the process.
