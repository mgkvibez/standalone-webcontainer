# ADR-0008 — Fixture Runner Contract

**Date:** 2026-11-04
**Status:** Proposed — implementer-recorded, awaiting the end-of-project expert audit
**Deciders:** Charter §4.5, §4.6, §4.7 and §4.8 state the requirements; the contract that satisfies them is recorded here

## Context

The gate is computed from `FixtureOutcome`s, and until now only tests produced those. Turning a definition into a run
needs a decision about where each responsibility sits, because the obvious shortcuts each break a charter rule:

- **Let the executor enforce its own timeout.** Then §4.5's budgets are advisory, and an executor that swallows its
  own overrun silently converts a hang into a failure nobody classified.
- **Interpret commands inside the runner.** `npm install` / `npm run dev` are not the runner's vocabulary; a runner
  that parses them couples the fixture format to a shell we do not have yet, and makes every fixture untestable
  without a full toolchain.
- **Treat "anything unexpected" as a bad baseline.** Simple, and wrong: it accuses the fixture of a harness bug.

The runner therefore owns sequencing, budgets, classification and evidence, and nothing else.

## Decision

`runFixture` takes a definition, an injected `executeStep`, an `AssertionEnvironment`, an optional evidence root and
optional budgets. Seven choices are recorded, each with its audit question.

| # | Decision | Reason |
|---|----------|--------|
| D-1 | Step execution is injected; the runner never parses a command | Fixtures stay declarative, and the runner is testable without a shell, npm binary or browser |
| D-2 | The runner holds the clock, wrapping each step in `withTimeout` | §4.5 budgets must not depend on executor discipline; a slow step becomes a TIMEOUT outcome, not a wait |
| D-3 | A step that is not `ok` ends the run, and assertions are not evaluated | Assertions against a world that never got built produce noise, not evidence; `ok` means "ran", so a fixture may legitimately assert a non-zero exit code |
| D-4 | A harness or network fault raises `ProbeFault` carrying the adapter's classification | Only the adapter can distinguish a preview proxy miss (HARNESS_BUG) from an unreachable host (NETWORK); the runner must not guess |
| D-5 | `INVALID_BASELINE` is reserved for a surprise PASS | A failure is reported as itself; relabelling a timeout or a harness bug as a bad baseline erases the diagnosis and accuses the fixture |
| D-6 | Evidence is `steps.json`, `assertions.json`, `verdict.txt`; no evidence root means `outcome: null` | §4.8: no summary without evidence, so an outcome that could not be recorded cannot exist |
| D-7 | `contains` comparisons preserve line order while stripping CRLF, timestamps and temp paths | §4.6 normalization must not defeat a multi-line match, which sorting lines would |

Verdict precedence is fixed so a report is reproducible when several things went wrong: fault (HARNESS_BUG/NETWORK) →
TIMEOUT → UNSUPPORTED_BY_DESIGN → step error → failed assertion → PASS.

## Consequences

Easier: the harness can be exercised completely without a runtime, because execution is a seam. A failing fixture
reports one classification with the evidence that justifies it.

Harder: someone must write the step interpreter (what `npm install` means in our engine) before a fixture can run for
real. That work is now well-defined rather than tangled with sequencing.

Foreclosed: implied defaults such as "retry a timed-out step" or "keep going after a failed install". Both would make
a run's duration depend on how much went wrong.

## Open Questions

1. **Does D-2 belong to the runner or the executor?** The runner now guarantees the budget, but a truly hung
   synchronous call in the in-process lane cannot be preempted (ADR-0004 D-5), so `withTimeout` will return TIMEOUT
   while the executor keeps running. The worker lane is where preemption becomes real; whether the in-process lane
   should refuse run-class steps until then is a question for the audit.
2. **Is a TIMEOUT ever a legitimate expectation?** Currently it is never held back, which assumes no fixture is
   designed to time out. Nothing in the corpus does; a fixture that did would need D-5 revisited.
3. **Should `INVALID_BASELINE` also cover a declared-but-impossible refusal?** A fixture expecting only PASS that ends
   UNSUPPORTED_BY_DESIGN is a genuine incompatibility, so it is reported as one. If the audit reads §4.7 more
   strictly, that case would move.
4. **Evidence format.** JSON files are readable and diffable; a JSONL event log would support streaming runs and is
   not implemented.
