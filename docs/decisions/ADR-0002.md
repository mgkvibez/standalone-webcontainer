# ADR-0002 — VFS and Threading Architecture

**Date:** 2026-10-23
**Status:** Accepted — expert-ratified (relayed by the product owner alongside PR #1 merge approval)
**Deciders:** Human expert (architect); recorded by the implementer.

The following eight decisions are ratified verbatim. They are the law for
Week 1 and are not to be altered by the implementer.

## RATIFIED

1. **VFS Data Structure**: Flat `Map<string, FileNode>` keyed by normalized
   absolute path. Directory entries are derived on demand. O(1) lookup.
   Rename via prefix scan. (Defer complex tree/Trie structures until
   rename-heavy workloads prove otherwise).
2. **Threading Model**: The runtime executes inside a dedicated Web Worker.
   Sync APIs (like `readFileSync`) will block *only* the worker thread. The
   main thread remains strictly async and never freezes.
3. **Persistence**: Phase 1 is in-memory only. Phase 2 will use Origin
   Private File System (OPFS) for file contents (sync access handles pair
   perfectly with the worker model) and IndexedDB for metadata.
4. **Large Files**: Chunked `Uint8Array` with a hard memory cap and LRU
   eviction. Fail with a clear, typed error rather than OOMing the browser.
5. **Service Worker Routing**: Intercept under a `/preview/<port>/` scope.
   Forward to the runtime over `MessageChannel`. Use pull-based streams for
   backpressure. WebSockets are explicitly rejected with an error in Phase 1.
6. **Isolation**: Single-owner VFS. The worker owns it. The main thread never
   touches it directly. This structurally eliminates the "one-way sync"
   hazard observed in other runtimes.
7. **Shim Priority**: `fs` → `path` → `process` → `child_process` (stub) →
   `http`. Target Node 20 LTS API surface.
8. **Security**: Deny-by-default for same-origin/trusted flags. Harness-only
   flags must exist behind a build define absent from the shipping build,
   enforced by a CI grep of `src/` for forbidden identifiers.

## Consequences for Week 1, Phase 1 (implementation notes, not decisions)

- The `FileSystem` class in `src/vfs/` implements exactly decision #1
  (flat `Map`, normalized absolute keys, derived directories, prefix-scan
  rename) and decision #4 (chunked `Uint8Array`, per-file cap
- Phase 1 method surface: writeFile, readFile, mkdir, readdir, stat,
  unlink, rename, and rmdir (added Oct 26 by expert decision: npm
  flows need directory removal). `rmdir` is strict POSIX — ENOTDIR on
  files, ENOTEMPTY on non-empty directories, EINVAL on the root.
  Recursive `rm` is deferred until the expert rules on subtree
  semantics; do not add it speculatively.
  `MAX_FILE_SIZE = 50 * 1024 * 1024`, whole-VFS cap with LRU eviction,
  typed `VFSQuotaExceededError`).
- Per decision #2 and #6, the VFS uses zero main-thread/DOM APIs and is safe
  to instantiate inside the Dedicated Web Worker. Async methods yield once
  before their atomic body; worker-only sync counterparts execute the same
  operations without yielding.
- The VFS itself has no persistence layer. P1b persists project files through
  the browser-owned project store outside the VFS.
- Decisions #5 (service worker) and #7–#8 (shims, security) governed later
  phases when this ADR was written. Subsequent milestones have added partial
  implementations in `src/network/`, `src/shims/`, and `src/runtime/`;
  support remains incomplete and is documented by those milestones.

## Implementation refinements (2026-11-05)

- The flat path map remains the source of truth. A descendant-count index
  serves derived-directory checks in time proportional to path depth rather
  than scanning every stored path on every write. Rename still uses the
  documented prefix scan.
- LRU may reclaim only files explicitly marked regenerable. Ordinary writes
  are protected. Before eviction, the VFS checks that eligible files can free
  enough space; otherwise it raises `ENOSPC` and leaves all stored files
  intact. The npm installer does not opt files in until its installation
  lifecycle can safely manage regenerated packages.
- The async methods yield once and then use the same synchronous core as the
  worker-only sync methods. The main thread remains async and never blocks.
